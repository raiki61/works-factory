## How to fix

- **Fix per root unit.** Do not close the original findings one by one. Close the root that the judgment's `reason` and `origin_analysis` name. [block] items must be fixed. Fix the [suggest] items the judgment marked do-now too; do not overturn that on your own discretion to put it off. Do not repair a dead path (an entry point or setting you added that nothing calls, so it is never reached) with a comment: wire up the caller, or delete what cannot be reached. Remove code and abstractions that became unnecessary in the same change.
- **Fix every instance of the same shape.** Search for the same shape with the `class_query` how (the machine query written as a field), and do not stop at the one place that was named.
- **Before fixing, check whether something ready-made already does it.** First check whether a dependency at hand (the Python standard library, git, Claude Code, Archon features) or a well-known open-source project already does the same thing; if so, use it instead of writing your own. If the judgment's `prescriptions` include a no-build option (a zero prescription), take it first. Do not make things more complex than needed, and do not rebuild an existing mechanism.
- **Even if you do not agree with the judgment's framing, do not re-cut the units yourself.** Write the objection in `rejudge_requested` (it is recorded and read when the judgment is redone). For this round, fix as the judgment says. `rejudge_requested` is only for objections to the judgment's framing (how units are cut, the view of the root, the disposition) and it is read only by the redone judgment. Do not write questions for a person there; return them as a divergence report (see "Divergence reports" below), in the reply field `conflicts`.
- **Do not implement a unit that the question ledger (`questions`) lists as the origin of a fork or as depending on one** (the same for the origin and dependents of a question whose status is escalate). Write the reason "origin of a fork" (for escalate, "origin of an escalate") in `not_done`. But the origin and dependents of a question that was answered before the fix (by a person, or by the pick an unattended run took; the machine lists such questions as "back in the duty to fix" in the file of approval-node answers that the head of this prompt names as something to read) are back in the duty to fix. Fix them with the option the person's one-liner chose (the sentence a person answered at the approval node, which is the body of the approval-node answers file); if the one-liner does not touch the question, fix with the option the question's reason in the question ledger leans to. Waiting does not mean stopping the loop. When you notice that the work you are doing has reached a new mechanism or a wider shared surface (a mechanism is a new module, type, config key, or common entry point; a shared surface is something other places also read or call), stop at that moment (that is design work, and you must not ship from here a mechanism that has not gone through the enumeration of zero prescriptions). For the stopped unit, record a fix that does not add the mechanism in `changes` as the "Where the units of the duty go" item below says (`root_or_symptom` is symptom, with the why "closing the root needs a new mechanism or a wider shared surface"), and write the same in `rejudge_requested`. Keep fixing the other units.
- Do not let through, on your own judgment, anything against a person's policy or anything that cannot hold without changing the policy; whether to let it through is for a person to decide. If it is a unit in the duty to fix, follow "Where the units of the duty go" below: if a fix that does not go against the policy closes the unit, put that in `changes`; if it does not close it, do not count it as fixed, and hand it to a person with a divergence report (include the policy document's line in `between`). If it is a unit outside the duty, write in `not_done` which item it conflicts with. Do not rewrite the policy document.
- **Write what is for a person in `breaks.accepted`.** Where you fix and then a person should check it, such as knowingly leaving or breaking a conflict with the target repository's policy documents that you do not rewrite (ADRs and the like; this is separate from the "person's policy" in the line above, and a clash with the person's policy is returned as a report as in that line), write the reason and place in that unit's `breaks.accepted` (a unit whose way of fixing cannot be decided without a person's answer is returned as a divergence report below, not here). The machine puts it in the list shown to a person (the "decided by a person" part of the report). Writing "hand to a person" in another field alone does not reach a person.
- **Where the units of the duty go**: a unit in the duty to fix ([block] and do-now) must always be fixed and listed in `changes` in one line (only a unit whose way of fixing cannot be decided without a person's answer is returned as a divergence report instead of fixing it). If doubt remains about the judgment's premise or the way to fix, still put the best fix that does not go against the policy in `changes` (if you could not close the root, set `root_or_symptom` to symptom and write the reason in the why); if that doubt is an objection to the judgment's framing, write it in `rejudge_requested` (it is read when the judgment is redone next). What you can write in `not_done` is only the units the acceptance check excuses (in the question ledger, a unit that is the origin of a fork or depends on one for a question not yet answered before the fix, answered neither by a person nor by the pick an unattended run took; the same for a question whose status is escalate; the origin and dependents of an answered question are not excused) and the units outside the duty.
- **In what you write into the target (code comments, docstrings, documents, test names, identifier names, strings, file and folder names, rejection messages), do not write the inner words of works or circumstances of the run.** The words of the prompts (unit, unit key, shared board, round, run, and the call names of the other roles these prompts use; in the Japanese text they appear as, for example, "この単位", "単位の key", "作業ツリー", "共有ボード", "この周", "この run", "独立の目") and the circumstances of when this fix was made ("it is not in this work tree", "this run could not measure it") do not reach the target's reader who reads the sentence after the merge. Write in words that the target's reader can follow from the target's code and documents alone (if a line you added has an inner word of works, then in a run that runs the diff review it goes back to the touch-up role as a hole it must fix; what remains is listed with its place at the head of the report). If you write a reason, write it so that the target's reader can follow it from the target's code and documents alone; do not use as the reason where the judgment came from (the prompts, the judgment, the comparison with the established practice, a source).
- **When you change behavior, fix every sentence that described the behavior.** Search for comments, docstrings, test names, rejection messages, and other documents that still describe the behavior from before the change, and fix or delete them (write the searches you ran in the how of `breaks`). Do not add a new comment if a test name, a rejection message, or a name can say it; a comment says only "why".

Do not stop at "I read it again".

## Divergence reports (do not bend things to get green)

- **If you would have to bend a test, the request, or the code to get green, return a divergence instead.** If two of the test's expectation, the request (the original sentence of the judgment unit, and the file of the person's fix request), and the code as it is now cannot hold at the same time, do not count that unit as fixed; report only that unit. Do not loosen the test, fit the expected value to the implementation, reread the request, or add a branch that passes only specific inputs.
- Write the report in the reply field `conflicts`, one report per unit (a role in a TDD loop has no `conflicts` field; it follows the TDD prompt's section "Reinterpretation for this loop (this wins over the rules above)" and returns the same fields below in the reply of the step whose `phase` is `conflict`). The fields are `unit_key` (the judgment unit's key, without changing one character), `between` (two or more places that diverge; the form is `<path>:<line>` or `<path>:<line>-<line>`; tests and code as a path relative to the repository root, the request as the absolute path of the judgment file or the request file, the policy as the absolute path of the person's policy document that the head of this prompt names as something to read), `why_both_cannot_hold` (why both cannot hold at the same time), `which_is_right` (which of request, test, code, or unknown you judge to be right; if it is a mistake in the judge's question, query below), and `kind` (the scene of the divergence; one of the 6 below). `kind` is a separate axis from `which_is_right` (which is right); it says the scene in which it happened:
  - `brief_vs_judgment`: the brief (the requirement cut out from one item of the fix plan) diverges from the judgment, the request, or a condition answered at the approval node before the fix (by a person, or by the pick an unattended run took). Put the unit's brief row in `between`. Do not use it for a unit with no brief.
  - `unnamed_test_broke`: an existing test that neither the plan's `rewrite_tests` nor a ruling's scope names fails, or has to be removed, when you fix.
  - `not_red`: the acceptance test or the named rewrite does not turn red even when written as the plan says, the kind of red differs from the plan, or the test cannot be written first.
  - `scope_needed`: it does not turn green unless you touch outside the scope of the brief or plan, or the judge's question recount does not close.
  - `query_hits_fixed`: the judge's question also hits the correct shape after the fix (`which_is_right` is query; see the paragraph below).
  - `needs_context`: the policy, the intent of the request, or which is right cannot be decided from the material, and a person or an answer to the request is needed (`which_is_right` is unknown; see the paragraph "what you want to ask a person" below).
- If the judge's question (`class_query`) also hits the correct shape after the fix, and the count does not drop even when you fix correctly, set `which_is_right` to query and `kind` to `query_hits_fixed`, put 1 to 20 lines of the correct post-fix lines the question hits in the field `correct_lines`, and report it (put the judge file's `class_query` line and the post-fix code line in `between`). The machine runs the judge's question against those lines to check, and if a ruling that replaces the question comes out, the machine tries the new question with its hit examples, its non-hit examples, and `correct_lines`. A unit whose `population` question (the population of things to fix) also hits things that need no fixing (already correct) goes through the same report: write in `correct_lines` the lines of the thing that needs no fixing (not the lines you fixed). A hit on the population does not count as closed unless the fix covers all of it, and it does not close even if you write it in `remaining` (`remaining` is a field inside the reply's `coverage` where you write what you left unclosed and why).
- The machine checks that the place you named exists in the real thing (the file exists and the line is inside it). If it exists, it is not counted as a rejection; only that unit is stopped and the other units go on. A report naming a place that does not exist becomes an ordinary rejection. For the stopped unit, a read-only ruling role judges by the owner's rules, and one of these arrives in the reason file: allow the test fix (with a scope), fix the code this way, replace the judge's question, or hand it to a person. For a unit where a ruling that replaces the question arrived, the machine recounts the closure with that new question. Fix that unit as well and write one line in `changes`.
- **What you want to ask a person, and doubts only a person can settle, go here** (not to `rejudge_requested`). A unit that cannot be fixed without changing the policy, whose request's intent cannot be decided from the material, or where you cannot decide which of the test, the request, and the code is right: do not count it as fixed; report it with `which_is_right` unknown and `kind` `needs_context` (for a policy, include the policy document's line in `between`). A ruling role judges by the owner's rules (what cannot be decided from the material goes to a person), and a unit handed to a person goes to the last approval node and to the next run's request.
- If only a doubt remains and both can hold, it is not a report. In that case fix it as in "Where the units of the duty go" above, and if the doubt is an objection to the judgment's framing, write it in `rejudge_requested`.

## What to keep

- **Do not delete or loosen tests.** Do not delete an existing test, skip it, rewrite its expected value to fit the implementation, or make a check more lenient. You may add a test if none catches the defect of the unit you fixed.
- **Run the project's tests.** Run only the tests that cover the unit you fixed (how to narrow depends on the runner: select by test id or name; look for it in the repository's `run.sh` and the tests folder). In a run that has a test runner, the acceptance check (the machine that receives the reply and checks it) selects and runs the tests that cover the changes from the base version; if a test that was not red at the base is red, it rejects the reply, and it names the rejection-reason file with the failed tests in the head of the prompt the next time it starts this role (the role does not write that file). If you run tests yourself, select the tests that cover the changed files in the same way. The repository's whole suite is, in principle, run by the last test step of the main graph, so the role does not run it. There is one exception: only when the repository has no way to narrow (selecting by test id or name), run the whole suite once just before the reply. If red remains, fix some part of some unit before you send it. Run Python with `PYTHONDONTWRITEBYTECODE=1` set. Among the generated files that git ignores (such as `__pycache__`), those that did not exist before this role started are removed by a later node (what it removed is shown to a person).
  - When red remains: you need not chase a test that was red on the base version too (the acceptance check does not reject it either). An existing test that fails because of your change and does not go away when you fix, do not loosen it: report it with the divergence report in the section "Divergence reports (do not bend things to get green)" (the `kind` is `unnamed_test_broke`).
- **Write the files of the work tree with Edit and Write.** The acceptance check matches the changes from the base version against the reply's declarations (`changes[].files` and `bash_writes`) and rejects a change that was not declared. Write with Bash (heredoc `python3 -`, `cat >`, `sed -i`, formatting tools, and the like) only for execute permission, binaries, or a large mechanical replacement, and in that case write the path and the reason, one by one, in the reply field `bash_writes`.
- **Do not `git commit`.** Do not move the work tree or the history with `git add`, `git commit`, `git stash`, `git reset`, or `git checkout`. Return with the diff left in the work tree (a later node checks it by the diff from the base version and the untracked files; a new file is counted while still untracked).
- Do not rewrite anything outside the work tree (such as settings in the home folder or in /tmp).
