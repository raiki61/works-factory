# 変えた手順を、動かして辿る

**芯の決まり: 文書の中の整合だけを見ない。手順は読んでではなく動かして確かめる。動かせない所は、実行を頭の中でなぞる。読んだ事と動かした結果が食い違えば、動かした結果が正。**

前提の物の不在や環境の取り違えは、読んでいると抜ける。手順を実機で動かして初めて見つかることが多い。

## 落とし穴（先に読む）

- **読み手は文脈を持たず、初めの状態から始めると考える。**
- **変わった手順の文書・スクリプト・CI の定義は、全文を読んでから辿る。** 変わった行だけではない。
- **状態を変える物は動かさない。** 既に在る道具（テストの一式・在る確かめのスクリプト）は、ファイルを書き換えない時だけ動かす。自分でファイルを作らない。実機で確かめられなかった物は、実測していない仮説として返す。
- **コマンドが拒まれたか止められたら**、その一歩を実測していない物として、打ったコマンドとどう拒まれたかを付けて返す。通すために綴りを変えて打ち直さない。
- **動かすために入れたり落としたりしない。** 既に在る道具で動かす。

## 手順

### 何を辿るか

- 対象のリポジトリが自分の審査の手引きを持っていれば、それも読む。
- **初めの状態から 1 歩ずつ**: 文脈を持たない初見の読み手が上から順に動かすと考える。コマンドごとに、その前提（物の在ること・道具が入っていること・環境変数・作業のフォルダ）が前の手順で成り立っているかを、状態を追いながら確かめる。
- **暗に頼る環境の状態**: コマンドが黙って頼る状態（クラスタの道具の今の context・ログイン中のアカウント・既定のブランチなど）を洗い出し、想定と違う状態で動いたら何が起きるかを問う。
- **害の届く範囲**: 手順が違う環境で動いた時に害がどこまで届くかと、それを防ぐ守り（動かす前の確かめ・明示した context）が在るか。

## 済んだと言える時

- 変わった手順を全部、初めの状態から 1 歩ずつ、状態を追って辿った。
- どの一歩も、動かしたか、そうでなければ実測していない物として返した。実測していない一歩には、打ったコマンドとどう拒まれたか、または動かさなかった訳を付けた。
- 指摘ごとに次が在る: **仕組み**（因果を 1 文で）・**実測**（動かせる物は動かす。動かせなければ「実測していない」と書き、仮説として出す）・先に済ませた**自分での崩し**（決まりを引くなら、その条件が当たるかを確かめ、周りの実際を読む。崩せなかった物だけを出す）・**誤検出の見積もり**（どんな時にこの指摘が誤りになるかを 1 行）。

## 返し方

指摘を、それぞれ上の 4 つを付けて。実機で確かめられなかった一歩は全部、打ったコマンドとどう拒まれたかを付けて、実測していない仮説として。場所は、今のファイルのパスと行の番号で、読んで確かめた物で指す。パッチの中の行ではない。ファイルを読めないなら、パスと関数の名などで指す。

## 例

入力: 変更が README の準備の手順を直す。手順 3 はデータベースの移行を動かす。データベースを作る手順は、その下の手順 5 へ移された。

返し: 指摘: 上から辿る初見の読み手は手順 3 で落ちる。要るデータベースが手順 5 で初めて作られるので。仕組み: 移しで、作る手順が最初に使う所より後になった。実測: 実測していない（移行は状態を変える）。仮説。誤りになる時: 新しい環境に既定でデータベースが在る時。場所: 今のファイルの README の手順 3 の行。

## 一緒に使うと良いもの

- 一次情報へ行く、読むだけの調べ役の構え（ファイルを書き換えず、元の記録や公式の文書などの一次情報そのものを自分で開いて確かめ、見つからない時はどこを見たかも言う）。
