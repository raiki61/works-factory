# open の pull request がこの変更とぶつからないかを確かめる

**芯の決まり: 信じられない一覧や集合から「ぶつからない」と書かない。代わりに、確かめられなかったと書く。**

## 落とし穴（先に読む）

- **読むだけ。** ファイルを書かず消さず、版の管理の状態を動かさない（checkout・switch・stash・reset をしない）。pull request に投稿しない。下書きは人が読んで渡す。
- **リポジトリは、今のフォルダの既定でなく、上流の remote から決める。** ブランチが追う remote（無ければ主の remote）から owner/repo を取り、後の問い合わせにはどれもはっきり渡す。道具自身の「今のリポジトリ」はフォルダから決まり、確かめがいつも通ってしまう。取れなければ、残りは確かめられない。
- **自分の pull request は、ブランチの名でなく先頭の commit で外す。** 外さないと、審査している変更そのものが範囲の外へ出る、自分を指す誤り。先頭が切り離された状態ではブランチの名は空。
- **切れた一覧は、きれいな一覧ではない。** 返った pull request の数が、並べる時に渡した最大の件数と同じなら、一覧が切れているかもしれない。そう書き、「ぶつからない」と書かない。
- **空の変更の集合は何も確かめない。** 「ぶつからない」と書かず、何が空だったかを書く。
- **代わりの集合は変更ではない。** 変わったファイルの集合が、測れなかった差分の代わり（依頼が名指す場所から取った物など）なら、交わりが空でも本物の変更について何も言わない。訳を添えて人へ渡す。
- **確かめていない結果は、決してきれいではない。** ネットワークや道具が断って確かめられなかったなら、断られたコマンドとその出力を添えてそう書く。
- **ホストが pull request を持つかを自分で決めない。** それは始める前に決まっている。

## 手順

1. 上流の remote から owner/repo を決める。
2. open の pull request を並べ、自分の物を先頭の commit で外す。
3. 一覧が切れていないかを確かめる。
4. 変わったファイルの集合を取り、空でなく代わりでもないことを確かめる。
5. 残った pull request ごとに、変わったファイルを読む。ファイルが集合と交わる物は、同じファイルを触っている。
6. 交わる pull request ごとに hunk を読む。同じファイルを触っていても、hunk が 1 つもぶつからない pull request については、何も範囲から外さない。

## ぶつかった所を渡す

ぶつかりや重なりが見つかった所ごとに、その変更を、相手の pull request が先に持っている物として扱う。

- **この変更を直して確かめる前**: ぶつかる hunk を、この変更の範囲から外す物として挙げる（挙げるだけで、ファイルは書き替えない。変更を作る側がそこに触らない）。hunk 1 つずつ、今の作業ツリーでの行の範囲と、何とぶつかるかを添えて。
- **この変更を直して確かめた後**: 外さない——今 hunk を外すと確かめが無駄になる。残したまま、この変更にまだ入っていることを覚え書きに書く。
- **相手の pull request の持ち主への覚え書き**（下書きで、投稿しない）: どの pull request・どのファイル・どの hunk・この変更のどれとぶつかるか、とどちらを先に入れるかの問い。hunk を外した pull request には覚え書きが要る。

一緒に使うと良いもの（参考。無くてもこの文だけで使える）: 外のサービスへの問い合わせ（Web の検索・開く URL）に対象の名を入れない決まりと、確かめを「回していない」「人が要る」「当てはまらない」と正直に書いてよい場合の決まり。
