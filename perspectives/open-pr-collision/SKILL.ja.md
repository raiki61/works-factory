# open の pull request がこの変更とぶつからないかを確かめる

**芯の決まり: 信じられない一覧や集合から「ぶつからない」と書かない。代わりに、確かめられなかったと書く。**

## 落とし穴（先に読む）

- **読むだけ。** ファイルを書かず消さず、版の管理の状態を動かさない（checkout・switch・stash・reset をしない）。pull request に投稿しない。下書きは人が読んで渡す。
- **リポジトリは、今のフォルダの既定でなく、上流の remote から決める。** ブランチが追う remote（無ければ主の remote）から owner/repo を取り、後の問い合わせにはどれもはっきり渡す。道具自身の「今のリポジトリ」はフォルダから決まり、確かめがいつも通ってしまう。取れなければ、残りは確かめられない。
- **自分の pull request は、ブランチの名でなく先頭の commit で外す。** 外さないと、審査している変更そのものが範囲の外へ出る、自分を指す誤り。先頭が切り離された状態ではブランチの名は空。
- **切れた一覧は、きれいな一覧ではない。** 返った pull request の数が、並べる時に渡した最大の件数と同じなら、一覧が切れているかもしれない。そう書き、「ぶつからない」と書かない。
- **空の変更の集合は何も確かめない。** 「ぶつからない」と書かず、何が空だったかを書く。
- **代わりの集合は変更ではない。** 変わったファイルの集合が、測れなかった差分の代わり（依頼が名指す場所から取った物など）なら、交わりが空でも本物の変更について何も言わない。訳を添えて人へ渡す。
- **確かめていない結果は、決してきれいではない。** ネットワークや道具が断って確かめられなかったなら、断られたコマンドとその出力を添えてそう書く。
- **ホストが pull request を持つかは、何より先に remote だけから確かめる。** remote が無い・remote がローカルのパス・ホストが pull request を持たない時は、この確かめは当てはまらない。当てはまらないことと訳（remote が何だったか）を書く。失敗した問い合わせから推さない。ネットワークに断られた問い合わせは確かめていない物で、「当てはまらない」ではない。

## 手順

この変更を直して確かめる前も後も手順は同じ（どちらの場面かは、確かめを頼む側が言う）。「ぶつかった所を渡す」では、今の場面の項を読む。hunk は、差分の中で続いて変わった行の 1 かたまり。

### ぶつかりを探す

1. 上流の remote から owner/repo を決める。
2. open の pull request を並べ、自分の物を先頭の commit で外す。
3. 一覧が切れていないかを確かめる。
4. 変わったファイルの集合を取り、空でなく代わりでもないことを確かめる（代わりとは、測った差分でなく、依頼が名指す場所などから取った集合）。
5. 残った pull request ごとに、変わったファイルを読む。ファイルが集合と交わる物は、同じファイルを触っている。
6. 交わる pull request ごとに hunk を読む。同じファイルを触っていても、hunk が 1 つもぶつからない pull request については、何も範囲から外さない。

### ぶつかった所を渡す

ぶつかりや重なりが見つかった所ごとに、その変更を、相手の pull request が先に持っている物として扱う。

- **この変更を直して確かめる前**: ぶつかる hunk を、この変更の範囲から外す物として挙げる（挙げるだけで、ファイルは書き替えない。変更を作る側がそこに触らない）。hunk 1 つずつ、今の作業ツリーでの行の範囲と、何とぶつかるかを添えて。
- **この変更を直して確かめた後**: 外さない——今 hunk を外すと確かめが無駄になる。残したまま、この変更にまだ入っていることを覚え書きに書く。
- **相手の pull request の持ち主への覚え書き**（下書きで、投稿しない）: どの pull request・どのファイル・どの hunk・この変更のどれとぶつかるか、とどちらを先に入れるかの問い。hunk を外した pull request には覚え書きが要る。

## 済んだと言える時

- リポジトリを上流の remote から決め、どの問い合わせにもそれをはっきり渡した。
- 自分の pull request を先頭の commit で外した。
- 一覧が切れたかどうかと、変更の集合が空か代わりかが分かっている。
- 交わる pull request はどれも hunk を読み、ぶつかる hunk にはどれも覚え書きを下書きした（変更を直して確かめる前なら、外す物として挙げた）。
- 何も書かず、投稿せず、版の管理を動かしていない。

## 返し方

- **決めたリポジトリ**、**並んだ pull request の数**（自分の物を外す前）、**一覧が切れたかもしれないか**。
- **交わる pull request ごと**: 番号・交わるファイル・下書きした覚え書き。
- **外す hunk ごと**（変更を直して確かめる前だけ）: pull request・ファイル・今の作業ツリーでの行の範囲・何とぶつかるか。
- **結果**は次のどれか:
  - **ぶつかりが在った**: いくつか。詳しくは上の物。
  - **ぶつからない**: 信じられる一覧と、空でない本物の変更の集合からだけ。何を見たかを書く。
  - **当てはまらない**: ホストが pull request を持たない。remote が何だったかを書く。
  - **人を待つ**: リポジトリを決められない・一覧が切れたかもしれない・変更の集合が代わり。訳を書く。
  - **回していない**: 変更の集合が空だった、またはネットワークや道具が断った。何が空だったか、または断られたコマンドとその出力を書く。

## 例

入力: この変更を直して確かめる前。ブランチは、pull request を持つホストの remote を追う。最大 50 件で並べると、open の pull request が 12 件返る。そのうち #41 が設定の読み込みの部品も変えていて、その hunk の 1 つが、この変更が同じ関数に入れた手と重なる。

返し:
- リポジトリ: 追っている remote の owner/repo。並んだ数: 12。切れていない。
- #41——交わるファイル: 設定の読み込みの部品。外す hunk: 今の作業ツリーでのそのファイルの 40〜52 行。この変更の、読み込みの関数への手とぶつかる。
- #41 の持ち主への覚え書き（下書きで、投稿しない）: 両方の pull request が、そのファイルの 40〜52 行の読み込みの関数を変えている。どちらを先に入れるか。
- 結果: ぶつかりが在った、1 つ。

## 一緒に使うと良いもの

- 外のサービスへの問い合わせ（Web の検索・開く URL）に対象の名を入れない決まり。
- 確かめを「回していない」「人が要る」「当てはまらない」と正直に書いてよい場合の決まり。
