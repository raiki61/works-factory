# 戻ってきた読み手が決められる報告を書く

**芯の決まり: 頭（最初の行・平易な要約・決めることの節 1 つ）だけで、文脈の無い読み手が、何の話か・自分に関わるか・急ぐか・何を決めるかを言えるようにする。**

読み手は複数の作業を並行で回し、切り替えの合間に読む。作業を見ておらず、会話も持っていない。いつもその読み手が初めて読む前提で書く。

下で使う語: *run* は作業の 1 回分の実行、*段* はその中の 1 つの工程（確かめ・審査・直し）、*記録* は段が残した物、*依頼* は作業を頼んだ文。

## 落とし穴（先に読む）

- **事実を変えない。** 渡された事実に在る数は、同じ値で書く。自分で数えた数は、どこから数えたかを書く。既に決まった結末を書き換えない。
- **どうせ付く物を繰り返さない。** 事実がそのまま報告に付くなら、本文でもう一度並べない。本文が足すのは、何が起きたかと、人が何を決めるか。
- **新しい選択肢を自分で勧めない。** 記録に既に在る選択肢と推しだけを、訳と出どころつきで出す。記録に無ければ無いと書く。
- **中の語だけで書いた問いは決められない。** ラベル・段の名・中の印・決まった鍵・id は平易な言葉に置き換える。
- **決めることが無い時は、それについて何も書かない。** 決めることは無い、という決まり文句も、空の決めることの節も置かない。何も聞かないことで、入力待ちでないと伝わる。
- 報告を書く間は**読むだけ**。

## 頭

- **平易な要約を 2〜3 行、専門語なしで**: 何の仕事だったか（何が悪かったかを依頼の言葉で）・何が分かり何が変わったか・なぜその終わり方になったかの要点・決めること（複数なら数と、いちばん急ぐ 1 つ）・急ぐかどうか、そして今壊れている物が在るか。機械が組む行は訳を持たないので、要約が補う。
- **危険・失敗の話は、今壊れているのか、壊れる余地だけかを最初に言う。**
- **決まった頭の行が使う、その作業の中だけの語**（段や役の名・依頼の領域の語・差分の識別子）は、出てくる順に平易な一句で言い換える。後ろの節にしか無い言い換えは、頭だけを読む読み手には数えない。

## 決めることの節

決めることは全部、要約の直後の 1 か所に集める。後ろの節に問いを散らさない。終わり切らずに止まった作業の保留や人へ上げた項目もここに入れる。

- 急ぐ物と待てる物を分け、数を先に言う。
- **1 つの点は 1 つの項目。** 同じ点がいくつもの段から届く時（変更の前の版でできていた事が、後でできなくなる点・人が記録した方針とのぶつかり・定石からの外れ）は 1 項目にまとめ、ほかの段はその中で名指す。
- 各項目は単独で読めるように、この順で書く: 何を決めるか（1 文）→ 背景（なぜ出てきたか。関わる PR・issue・ファイルは 1 行ずつ）→ 選択肢ごとに何が起きるか（実際の作業・手間・何が壊れるか）→ 推しとその訳（記録に書かれた物だけ。人の推しか、無人の run が採った推しか、どこまで信じてよいかを添える）→ 答えた後に何が起きるか（記録に在ることだけ）→ 誰も決めないと何が止まるか。
- 作業が止まった時（依頼の文自身が「ここで止める」と置いていた・人が止めた・人の答えを待っている）は、どこで止まったか・訳・答えの無い問いを必ず 1 項目にし、続けるには新しい作業を始めること、止まった後の段は走っていないことを添える。
- 「直しが要る」と「作り直しが要る」は分けて書く。「直しが要る」は変更を捨てる訳にならない。
- 正しい直しが落ちたかもしれない印（確かめ直しでテストが落ちたために外された直しのまとまりなど）も 1 項目にする。
- 項目の中で中身を指さない（`<path>:<line>`・記録の中の位置・単位の鍵・行の id・記録のファイルの名）。その物が何かを平易な言葉で言い、参照は後ろの節に置いて見出しで名指す。
- 「通す」「通さない」の形の選択や、帰結の無いコマンド: 何を通すのか・選んだ後に何が起きるか・誰も選ばないと何が起きるかを書く。
- 裸の参照（issue や PR の番号・ファイルの名・コマンド）: それが何で、人がそれで何をするかを数語で書く。
- 同じ決めかもしれない複数の指摘: 別々か・どれが先か・誰がするか（人か次の run か）を書く。
- 決めることでない知らせ: 読み手にとって何を意味するかを 1 文で、動く必要があれば何をするかを書く。

## 頭の後ろの本文

詳細は見出しの下に短く畳む。途中経過や自分の作業の実況を書かない。頭の後ろに置くと良い節（どれも在る時だけ置く）:

- 作業の入り方と、運んだ依頼の全部（出どころと数）。人の依頼と機械の依頼をまとめない。1 つも落とさない。直す前に依頼の外を見た審査が無かったなら、終わって見えてもそう書く。
- 事実の通りの結末と止まった段。
- 作業の単位ごとに、何をしたか、何も要らなかった訳。後で直すと受け入れた欠陥。
- 独立の審査ごとの判定と訳を変えずに、読み手への説明を添えて。変更が足したコードのコメントを見る審査が、消した物と残した物。走っていない審査は走っていないと書く。
- 開いた問いの状態と、決着の根拠か人へ回した訳。
- 判定の生の答えをそのまま（コードの囲みで）・元の目的の出どころ・直す前の版。
- 主な道の観察: 何をどこで走らせ何を見たか。「テストは緑」は観察ではない。
- 変更が入れた新しい仕組みの目録を、判定せずに（ビルドの設定・環境変数・CI の job・雛形のつまみ・スクリプト）。
- 前提がずれたなら、測り直した制約と、前の制約が偽になった訳。

## 書式

- 記号・略語・パス・自作のラベルは、初出で「中身（記号）」の形に書く。途中から読んだ読み手も解けるように。作業の仕組みの中の物は、依頼の言葉か一般の言葉で名指す。
- 表は数語の短い値（状態・件数・日付）の一覧だけ。**セルに説明の文を入れない**: 端末の表は列ごとに幅を割るので、長いセルは読めない細切れに折り返される。説明が要るなら箇条書きか散文にする。手順は番号付き。
- 報告の言語の IT 業界の定着語を使う。コンサル語・直訳・凝った比喩を避ける。
- 文の外の文脈に頼る参照（「さっきの」「上の節」）を残さない。
- 元の資料が別の言語でも報告の言語で書く。鍵・enum の値・識別子・パス・コマンド・エラー文はそのまま。

## 文脈の無い読み手に頭を確かめさせる

頭だけを、道具も文脈も持たない読み手に渡す。後ろに詳細の節が続くことは伝える。読み手は、意味を追えず止まった所と、推測で埋めた所を行ごとに返し、この文だけで人が決められるかを返す。止まりが 1 つ、推測が 1 つでも在れば書き直す。後ろの節に任せて見出しで名指した詳細は、止まりに数えない。

頭が戻された時:

- 読み手が止まったなら、名指された所が頭だけで分かるように書き直す。
- 表のセルに文が在るか長すぎるなら、表をやめて箇条書きか散文にするか、セルを数語に削って説明を表の外に書く。
- 前の回の分も含めて全部の点を直し、直した所だけでなく本文の全部を返し直す。

一緒に使うと良いもの（任意。このファイルはそれ無しで完結する）: Web 検索など外のサービスに送る語に、報告する対象のプロジェクトの名を入れない観点と、文脈も道具も持たずに文を確かめる読み手の構え。
