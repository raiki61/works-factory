# プロジェクト自身のコマンドなら通るテストを壊す、テストの実行器を直す

**芯の決まり: プロジェクト自身のテストのコマンドは単独で通るのに、同じテストがテストの実行器を通すと中身に届く前に壊れるなら、壊れているのは実行器で、テストではない。**

## 落とし穴（先に読む）

- **テストを触らない。** 壊れているのはそこではない。
- **狭く読む。** 実行器の中身・両方の走りのログ・プロジェクト自身のテストの回し方の宣言（在れば）・CI の定義・それらが名指すテストの設定のファイルを読む。それより先は探さない。
- **見立ての間、テストを走らせない・依存を入れない・ファイルを書かない。** テストの道具の使い方を出す短いコマンドで、JUnit XML を書けるかを見るのは良い。
- **何が壊したか分からなければ、そう言い**、何を読んだかを言う。当て推量で書き直さない。

## 手順

### 何を探すか

ログから、実行器がしていてテストのコマンド単独ではしていないことを見つける。よくある原因: テストが始まる環境を変えている——モジュールの探し道・作業ディレクトリ・インタプリタ・ほかの変数——ので、テストが要る物が見つからなくなる。

### 直し方

実行器がすべきこと——最初の引数が示す所に JUnit XML を書く・その後の引数をテストへ渡す・テストの終わりのコードを保つ——は残し、テストを壊したことをやめる。

## 済んだと言える時

- 実行器がしていてテストのコマンド単独ではしていないことを、ログから見つけた。または、分からないと言った。
- テストに触っておらず、見立ての間にテストを走らせず、何も入れず、ファイルを書いていない。
- 新しい本文が、最初の引数が示す所に JUnit XML を書き、その後の引数を渡し、テストの終わりのコードを保つ。

## 返し方

テストの実行器の新しい本文と、何をやめたか（ログから見つけた原因）。何がテストを壊したか分からなければ、本文を出さず、そう言い、何を読んだかを言う。

## 例

入力: プロジェクト自身のテストのコマンドは単独で通る。テストの実行器を通すと、どのテストも中身の前に「module not found」で誤りになる。実行器の本文は、コマンドを走らせる前に自分のフォルダへ移っている。

返し:

- 原因: 実行器が作業ディレクトリを自分のフォルダに変えるので、そこからはテストのモジュールが見つからない。
- 新しい本文: コマンド単独の時と同じく、対象の根からコマンドを走らせる。最初の引数へ JUnit XML を書き、残りの引数を渡し、終わりのコードを保つのは変えない。
- 読んだ物: 実行器の本文・両方の走りのログ・CI の定義。

## 一緒に使うと良いもの

- 全部のテストの結果を JUnit XML で報告するテストの実行器を書く見方。
