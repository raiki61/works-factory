# プロジェクト自身のコマンドなら通る試験を壊す、試験の包みを直す

**芯の決まり: プロジェクト自身の試験のコマンドは単独で通るのに、同じ試験が包みを通すと中身に届く前に壊れるなら、壊れているのは包みで、試験ではない。**

## 落とし穴（先に読む）

- **試験を触らない。** 壊れているのはそこではない。
- **狭く読む。** 包みの中身・両方の走りのログ・プロジェクトの走らせ方の宣言（在れば）・CI の定義・それらが名指す試験の設定のファイルを読む。それより先は探さない。
- **見立ての間、試験を走らせない・依存を入れない・ファイルを書かない。** 試験の道具の使い方を出す短いコマンドで、JUnit XML を書けるかを見るのは良い。
- **何が壊したか分からなければ、そう言い**、何を読んだかを言う。当て推量で書き直さない。

## 何を探すか

ログから、包みがしていて試験のコマンド単独ではしていないことを見つける。よくある原因: 試験が始まる環境を変えている——モジュールの探し道・作業ディレクトリ・インタプリタ・ほかの変数——ので、試験が要る物が見つからなくなる。

## 直し方

包みがすべきこと——最初の引数が示す所に JUnit XML を書く・その後の引数を試験へ渡す・試験の終わりのコードを保つ——は残し、試験を壊したことをやめる。
