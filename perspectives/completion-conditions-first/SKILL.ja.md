# 計画の前に、済んだと言える条件を書く

**芯の決まり: 計画の前に、仕事が済んだと言えるために成り立つべき物を 1 つずつ書き、それを書いていない目に抜けを探させる。**

訳: 依頼が書いていない条件は修正の計画に入らず、後の審査が穴として挙げた時に初めて表に出る。（一度測った例: 新しい入口を作った run で、依頼は要件を 6 つ並べたが「2 周目からは、最初の確かめをいつも通り回す」が無かった。最初の計画はその確かめを run の終わりまで戻さない形になり、計画の審査が必ず直す物として止めた。）

## 落とし穴（先に読む）

- **まだ修正を書かない。** この段で書いてよいのは試験のファイルだけ。実装は 1 文字も変えない。
- **今赤い試験が正しい。** 修正はまだ入っていない。修正の前から緑の試験は何も示さない。「赤を見なかった」と記録する。
- **条件の字の源は試験のファイル。** 前提・操作・期待を、試験の中に Given / When / Then で書く。ほかの所からは試験を指し、字を写さない。
- **試験は、リポジトリの試験の一式（CI が回す物）が拾う所に置く。** CI が見ない所に置いた試験は何も守らない。
- **試験を回す命令は、回す前にその字のまま人に見せる。** 人がその字を読んで承認し、その後で初めて回して終了コードを記録する。
- **条件を書いた人は中立の目ではない。** 後で修正も書く人は、自分の計画に合う条件だけを書きがちになる。審査は、書いていない目がする。

## 1. 条件を書く

- **要件**: 依頼が済んだと言える条件を 1 件に 1 つ。短く重ならない鍵（R1・R2…）と、1 文ずつ。
- 依頼が書いていなくても、依頼が要る条件は掘り出して足す:
  - 既定の振る舞いが変わらない（その選択をしない時は何も変わらない）。
  - 周や段をまたいだ振る舞い（初回だけでなく、2 回目以降も）。
  - 失敗した時・止めた時・誰も答えない時にどうなるか。
  - 元に戻す方法。
  - 同時に選べるほかの機能との組み合わせ。
- **受け入れ**: 要件ごとに受け入れの条件を少なくとも 1 つ、今この段で、対象に実行できる試験として書く（在る所・試験の名・回す命令）。
- **範囲の外**: 依頼の範囲の外と決めた物（無ければ空）。

## 2. 条件を審査する（別の目）

依頼と、書かれた要件と、受け入れの試験それぞれの字を読む。計画の前に、済んだと言える条件の抜けを探す。穴は 3 種:

1. **足りない**: 依頼が要るのに、要件にも受け入れの条件にも無い条件。特に、既定の振る舞い・周や段をまたいだ振る舞い・終わり方（止めた・失敗した・誰も答えない）・元に戻す方法・同時に選べるほかの機能との組み合わせを見る。
2. **曖昧**: 試験が成り立つ条件 1 つに定まらない文。Then が要件より弱い試験（何が返っても通る）。要件とは別の物を確かめる試験。リポジトリの試験の一式が拾わない所に置いた試験。
3. **範囲の外**: 依頼の範囲を越える要件や受け入れの条件。

穴ごとに、在る所（要件・受け入れの条件・ファイルのどれか）と、穴だと言える筋道を書く。

- 審査する目は読むだけで、作業ツリーを 1 文字も変えない。
- 穴が無い時は、何を確かめたから無いと言えるかを書く。
- **材料が足りない時**（依頼か仕様が読めない、受け入れの条件の試験のファイルが無い）は、穴が無いと言わない。読めない物・無い物ごとに「足りない」の穴を 1 つ挙げ、訳を「足りない:」で始めて、何を確かめられなかったかを書く。

## 3. 審査に答える

- 穴ごとに **ちょうど 1 回** 答える。取り込んだ（足した要件と受け入れの条件を書く）か、残すと言い切る（訳を書く。穴が間違いなら、実際のコードか文書のどこで間違いかを書く）か。答えない穴を残さない。
- 変えた所だけでなく、直した条件の全体を返し、足した受け入れの条件の試験は答える前に書く。
- 書いてよいのはこの時も試験のファイルだけで、実装は触らない。
- その後で人が、条件・穴・答え・試験の命令それぞれの字を見て、条件を承認する。

一緒に使うと良いもの: Web の検索など外のサービスへ送る問い合わせに、直す相手のリポジトリの名やパスを入れない観点と、人に決めてもらう問いを、前の経緯を知らない人がその字だけで決められる形に書く観点。
