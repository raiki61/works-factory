# 人が置いた前提から設計する

**芯の決まり: 仕事の途中の人の答えは、目的の前の書き方に勝つ。答えが変えた後の目的に照らして設計する。**

ここで使う語:

- **対象**: 設計の向かう先のシステム（リポジトリ）。
- **依頼**: 変更を求める人の依頼で、設計の出発点になる文。
- **地図の文書**: 対象の根に在り、全体の構造を書く文書（アーキテクチャの概観・部品とそのつながりの一覧）。

## 落とし穴（先に読む）

- **答えを先に読む。** ほかの材料より前に。
- **取り下げられた要件は、動かせない約束ではない。** 答えが目的や前の要件を取り下げた・変えたなら、取り下げられた・変えられた後の要件を前提にする。
- **取り下げた要件を残しただけでは、前提を破ったと数えない。** 設計が取り下げた要件をまだ持っていても、それだけでは違いでも、前提の破れでもない。答えが変えた後の目的と比べる。
- **無い文書は、空の文書ではない。** 依頼の文が読めなかったなら、依頼が名指す設計の文書の節は渡されていない。無い事を、依頼が何も名指していないと取らない。

## 手順

### 前提として読む物

1. **仕事の途中で人が答えた事**（人が問いに答えるまで仕事が止まった所で）。
2. **依頼が名指す設計の文書の節**（依頼を固めた時の版）。目的と同じく、依頼の一部として読む。
3. **対象の根に在る地図の文書。** 依頼が名指していなくても、設計を、システムに既に在る物から始める: 信頼の根（資格と信頼が始まる所）・外との通い道（システムが外と話す所）・守っている物。

## 済んだと言える時

- 答えを、ほかの材料より前に読んだ。
- 答えが取り下げた・変えた要件は、どれも取り下げられた・変えられた物として採った。
- 設計が、システムが既に持つ信頼の根・外との通い道・守っている物から始まっている。
- 依頼の文が読めなかったなら、名指す節を「無し」と取っていない。

## 返し方

答えが変えた後の目的に照らした設計を返す。設計を答えと比べる時は、その変わった後の目的に照らして判じ、取り下げた要件を残しただけの事を違いと数えない。

## 例

入力: 依頼は「報告をファイルに書き出し、メールで送る」だった。仕事の途中で人が「メールの所は取り下げる。ファイルで足りる」と答えた。設計の下書きにはまだメールの段取りが在る。

返し:
- 前提: 目的は今は「報告をファイルに書き出す」。メールの要件は取り下げられた。
- 下書きのメールの段取りは、それだけでは前提の破れではない。変わった後の目的と比べると、ファイルの書き出しで満たしている。
- 設計は既に在る物から始める: 書き出しは、システムが既に守っている置き場に書き、外への新しい通い道を足さない。

## 一緒に使うと良いもの

- 計画やコードを見る前に、目的だけから設計する事。
- 触るシステムを、同じ種類のシステムの一般の構造と比べる事。
