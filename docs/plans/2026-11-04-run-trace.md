## 0 語

- トレース・span: OpenTelemetry（処理の記録を送る標準の形。略 OTel）の記録の単位。span は始めと終わりの時刻と親の span を持つ 1 区間で、1 本のトレースは span の木。
- OTLP: OpenTelemetry の記録を送る口の形。Phoenix は HTTP の `/v1/traces` で protobuf の形だけを受ける（JSON は 415 で断る。https://arize.com/docs/phoenix/integrations/llm-providers/cloudflare-ai-gateway/cloudflare-ai-gateway-tracing）。
- OpenInference: Phoenix の作り手が決めた、AI の処理の span の属性の名の取り決め（https://github.com/Arize-ai/openinference/blob/main/spec/semantic_conventions.md）。span の種類 `openinference.span.kind`（`AGENT`・`LLM`・`TOOL`・`CHAIN` ほか）と、模型の名・トークン・入出力の名を持つ。
- GenAI の取り決め: OpenTelemetry が決める同じ種類の取り決め（`gen_ai.*`）。状態は Development（https://github.com/open-telemetry/semantic-conventions-genai）。
- 往復: AI の会話の 1 回の頼みと返事（LLM の 1 回の呼び出し）。
- 下請け: AI が Agent の道具で起こす別の AI の会話（subagent）。Claude Code は `<会話の id>/subagents/agent-<id>.jsonl` に記録する。
- 見本の run: run `a474928e`（2026-11-04、line、29.87 USD、完了）。計画を審査するノード `review-tree` の周 1 が 9.32 USD で、その下請け 2 つが 35 往復と 61 往復、1 往復の入力が最大 19.9 万トークン。

## 2 置き場と層

### 2.1 案

- L1（推し）: 見る道具の層 `viewer/` に足す。読む部品（Archon の名を 1 か所に持つ `src/runread.py`・会話の読み `src/session.py`・段の表 `stages.json`）をそのまま使え、層の地図の `may_use`（`shell`・`shared`・`lib`）も「どの層からも頼られない」向きも変わらない。
- L2: 新しい層（例 `trace/`）を切る。`viewer/` の読む部品を使うには、どの層からも頼られない `viewer/` に頼るか、部品を `lib/` へ移すことになる。`lib/` は Archon を知らない Python の置き場（`lib/AGENTS.md`）なので、Archon の名を持つ `runread.py` は移せない。採らない。
- L3: リポジトリの外（`claude-plugins` など）。`viewer-in-repo` の時と同じく、読む物は工場の作りと記録の形に頼る。採らない。

### 2.2 木（L1）

```text
viewer/
├── runtrace.py        足す。入口: run を選び（flowview.py と同じ --target・--run）、span の木を組んで送る
└── src/
    ├── runread.py     そのまま使う（ノードの出来事・時刻・費用・トークン・会話の id の頭）
    ├── session.py     読みを 3 つ足す（3.4 の 3〜5）
    ├── stages.py      そのまま使う（出来事の段）
    ├── trace.py       足す。run と会話の読みから span の木（字と数だけの dict の列）を組む。網に出ない
    └── otlp.py        足す。span の木を OTLP で送る。網に出るのはこの 1 つだけ
```

- 試験は `tests/viewer/test_trace.py`・`tests/viewer/test_otlp.py`。記録は今の `test_read.py` と同じく、試験の中で一時のフォルダに行を書いて作る（実物の行の形を写し、利用者のパスと会話の字は作り物に替える）。新しい置き場（fixtures のフォルダ）は足さない。
- 外のパッケージ: OpenTelemetry の SDK と OTLP/HTTP の exporter（`opentelemetry-sdk`・`opentelemetry-exporter-otlp-proto-http`）を `pyproject.toml` の extra `trace` に版を止めて足す（持ち主の決め `outside-packages-ok`。今の extra `viewer` と同じ形）。protobuf を自分で組まないため。過去の時刻の span は SDK の `start_span(start_time=…)`・`end(end_time=…)` で作る（手元の Phoenix 21.0.0 で確かめた。3.6）。

### 2.3 決まり E25 の書き換え

E25 の 2「見る道具は読むだけ。書くのは出力と利用者のキャッシュと訳の控えだけ」と `docs/design/viewer.md` の 3 章「網には出ない」に、送る口を 1 つ足す。

- 送るのは `runtrace.py` だけで、送り先は利用者が名指す（引数 `--endpoint`、無ければ OpenTelemetry の標準の env `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT`・`OTEL_EXPORTER_OTLP_ENDPOINT`）。既定の送り先を持たない（E14。持ち主の環境の値を書かない。送り先の無い起動は 1 行の訳で止まる）。
- 送り先が手元（loopback）でなければ、`--remote` を付けない限り拒む（span は会話と道具の中身、つまり対象のリポジトリの字を持つ。公開のサービスへ黙って出さない。7 章の問い 2）。
- 手元へ送る時は、利用者の `HTTP_PROXY` を通さない（手元の確かめで、会社の proxy の env が在ると 127.0.0.1 への送りが proxy に切られた。exporter に `NO_PROXY` を足すか、手元の送り先では proxy を外す）。
- E25 の 1（工場の中から頼らない）・3（ページは 1 枚）・4（見た目の決まりは置かない）は変えない。機械の照らし `tests/layers/test_viewer_apart.py` もそのまま効く。
- Phoenix 本体はリポジトリに入れず、工場は起こさない（利用者が手元で起こす）。工場の run の流れにも入らない（送るのは run の後に人が打つ時だけ）。常駐の仕組みは足さない（E10）。

## 3 変換の形

### 3.1 木

1 本の run を 1 本のトレースにする。

```text
run（AGENT。名は graph の名。run の id・状態・結末・Archon の総額）
└ 段（CHAIN。stages.json の段。line の run だけ。時刻は中の出来事の最初と最後）
  └ 繰り返しの器（CHAIN。loop_group の出来事）
    └ 周（CHAIN。器の中の出来事を周の番号で分けた物。時刻は中の最初と最後）
      └ ノード（AI のノードは AGENT、script・bash は CHAIN、人の答え待ちは CHAIN）
        ├ 往復（LLM）
        ├ 道具（TOOL）
        │  └ 下請け（AGENT。Agent の道具の呼び出しの下）
        │     ├ 往復（LLM）…
        │     └ 道具（TOOL）…
        └ …
```

- include で開いた子（ノードの道の `__`）は span にせず、ノードの道を属性に持つ。子の run（`workflow:` のノード）の出来事は、`runread` が親のノードの道を頭に足して返すので、そのノードの span の下に入る。
- 並べて起こす器（`compose_fan_out`）と子の run を起こすノードも器の span にする。器の span には費用を載せない（中と二重になる。`runread.GROUP_KINDS` と同じ訳）。

### 3.2 属性の取り決め: OpenInference に寄せる（推し）

- 推しの訳: Phoenix の画面（span の種類の札・トークン・入出力の面・費用の和）は OpenInference の名を読む。OpenInference は cache の読みと書きのトークン（`llm.token_count.prompt_details.cache_read`・`cache_write`）を名で持つ。Phoenix は 15.10.0 から `gen_ai.*` も読むが、OpenInference の名へ変換して足りない所を埋めるだけ（https://arize.com/docs/phoenix/release-notes/05-2026/05-15-2026-otel-semconv-conversion）。GenAI の取り決めは Development で名が動きうる。
- 代案 GenAI: 道具を替えやすい（`swap-is-the-value`）が、Phoenix の側で変換を 1 段挟み、cache の名の扱いが割れる。Langfuse も OpenInference の span を受ける（https://langfuse.com/integrations/frameworks/claude-agent-sdk）ので、OpenInference に寄せても替えは閉じない。採らない。
- 足し算の訳: Claude Code の会話の記録の `input_tokens` は cache を含まない。OpenInference の `llm.token_count.prompt` は cache を含む全体なので、`input_tokens + cache_read_input_tokens + cache_creation_input_tokens` を入れ、cache の 2 つを内訳に入れる（GenAI の取り決めも同じ足し方を求める。https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/anthropic.md）。
- 工場の物は `works_factory.*` の名で持つ: ノードの道（`works_factory.path`）・周の番号（`works_factory.loop`）・ノードの種類・状態・段・Archon の費用（`works_factory.cost_usd`）・Archon が数えた往復（`works_factory.turns`）・4 分けのトークン・道具の結果の切る前の字の数（`works_factory.result_chars`）。

### 3.3 載せる物

| span | 載せる物 |
| --- | --- |
| run | run の id・状態・結末・総額・段ごとと AI のノードの上位の費用の表 |
| ノード | 道・周・種類・状態・費用・トークン・会話の id |
| 往復 | 模型・トークン・新しく入った字・返事 |
| 道具 | 道具の名・入力・結果 |
| 下請け | 説明・種類・深さ・最初の指示 |

- 費用は Archon の値（`node_completed` の `spend`。`runread` が読む `cost`）を正にする。手元の確かめで、Phoenix は span に明示した `llm.cost.total` を使わず、LLM の span の模型の名とトークンから自分の値段の表で計算し直した（値段の表に無い模型の名では費用が空になった。3.6）。なので Archon の値は属性 `works_factory.cost_usd` に置き、run の span の出力に「段ごと・ノードの上位の費用の表」を Archon の値で書く（トレースを開いた最初の面で正の内訳が読める）。Phoenix の費用の欄はその表との比べの値として読む。合わなければ利用者が Phoenix の設定で模型の値段を足す（E14。工場は値段の表を持たない。今の `waste.py` と同じ決め）。
- 下請けごとの費用は記録に無い。会話の `cost-state` の行は会話ごと・模型ごとの和だけを持ち、下請けは親と同じ模型で走る（見本の run で、`review-tree` の会話の `totalCostUSD` 9.3222 は Archon のノードの費用と同じで、下請けの分を含む）。下請けの span には トークンだけを置き、費用は Phoenix の計算に任せる。
- 中身の大きさ: 往復の span には、その往復で新しく入った物（道具の結果・後から入った指示）と返事だけを置き、文脈の全部は置かない（見本の run では 1 往復 19.9 万トークンを 61 回積むことになる）。system と道具の一覧と最初の指示は、ノードの span（下請けは下請けの span）に 1 度だけ置く。字は 1 欄 20,000 字で切り（`runread.CLIP` と同じ）、切る前の字の数を属性に持つ。
- 会話の中身を載せるか: 推しは載せる（7 章の問い 2）。

### 3.4 時刻と親子の復元（見本の run の実物で確かめた）

調べで二次が足りなかった点。見本の run の DB（出来事 2,778 行）と Archon のログ（`logs/<run>.jsonl`）と会話の記録（会話 28・下請け 7）を読むだけで確かめた。

1. run とノード: Archon のログの行はミリ秒の時刻を持ち、`runread.run` がノードの起動ごとの出来事（始め・終わり・状態・費用・トークン・往復の数・会話の id の頭・周の番号）にする。起き直し・落ち・閉じた出来事の扱い（`cut`・`fell`）も `runread` が済ませている。DB の時刻は秒までなので使わない（`runread` の今の訳のまま）。
2. ノードと会話: ノードの出来事の `binding.sessionPreview`（会話の id の頭 8 字）で、`claude-config/projects/*/<頭>*.jsonl` を引く（`session.find`）。見本の run で 28 の会話の全部が当たった。続けた会話（`sessionOrigin` が `resumed`）は前の会話の往復を写して持つので、出来事の始めより前の往復を外す（`session.read` の `since` の今の訳）。
3. 往復の時刻（足す読み）: 会話の記録の `api-request` の行が、頼みを出した時刻をミリ秒で持つ。返事は内容の片ごとに `assistant` の行になり、同じ `message.id` の最後の行の時刻が返事の終わり。往復の span は「`api-request` の時刻 → その次の `message.id` の最後の行の時刻」。見本の run で親の会話に 220 行、下請けに 198 行在り、下請けの往復の数（61・35 ほか）と同じ数だった。今の `session.read` は `api-request` を読まない型に入れている（`READ_FROM`）ので、時刻だけを読む形に足す。`api-request` の行が普通の利用者の Claude Code でも出るかは確かめていない（`docs/design/viewer.md` の 6 章の `api-request-shape` と同じ）。無ければ前の行（道具の結果か指示）の時刻を始めにする。
4. 道具の時刻（足す読み）: `tool_use` の片を持つ `assistant` の行の時刻が始め、同じ `tool_use_id` の `tool_result` を持つ `user` の行の時刻が終わり。今の `session.read` は呼び出しと結果を結ぶが、結果の行の時刻を捨てている。
5. 下請け（足す読み）: `<会話の id>/subagents/agent-<id>.jsonl` と同じ名の `.meta.json`。meta の `toolUseId` が親の会話の Agent の `tool_use` の id で、親の道具の span の下に置く。meta は `description`・`agentType`・`spawnDepth` も持つ。行は `isSidechain: true` とミリ秒の時刻を持つ。見本の run で 4 つの会話の 7 つの下請けの全部が親の呼び出しに当たった。
6. 裏で走る下請け: 見本の run の下請けは全部 `requestShape: background` で、Agent の道具は約 60 ミリ秒で「起こした」と返し、終わりは後から `<task-notification>` の行で届く（`review-tree` の周 1 では 10 分後）。なので下請けの span は親の道具の span より長く続く。OpenTelemetry は子が親より後に終わるのを許す。Phoenix の時間の帯での見え方は 6 章の T3 で人が見る。
7. 時計: Archon のログと会話の記録はどちらも同じ機械の UTC（`Z`）のミリ秒。合わせる手間は無い。
8. 手間の見積もり: 結ぶ鍵が全部記録に在るので、復元は読みと並べ替えだけ。難しい所は続けた会話の写しの往復と裏で走る下請けの 2 つで、前者は `session.py` が既に解いている。

### 3.5 受け入れの目安（見本の run）

Phoenix のトレースの画面で、次が開いてすぐ読めること。

1. run の span の出力の表で、計画の段が一番高く、その中で `review-tree` の周 1 が 9.32 USD（Archon の値）。
2. `review-tree` の周 1 の span を開くと、Agent の道具 2 つの下に下請けの span が 2 つ在り、往復の子がそれぞれ 35 と 61。
3. 下請けの往復の span の入力のトークンが積み上がり、最大が 198,786（項目 1）と 189,292（項目 2）。
4. Phoenix の費用の和と Archon の 29.87 USD の差を書き留める（合わなければ 3.3 の値段の足し）。

### 3.6 手元の Phoenix での確かめ（外へ何も送らない形）

- 入れた物: `uvx --isolated arize-phoenix serve`（arize-phoenix 21.0.0）を、`PHOENIX_TELEMETRY_ENABLED=false`・`PHOENIX_HOST=127.0.0.1`・置き場と SQLite を一時のフォルダ（`PHOENIX_WORKING_DIR`・`PHOENIX_SQL_DATABASE_URL`）にして起こし、終わったら止めた。送ったのは作り物の span 3 つ（run・ノード・往復。時刻だけ見本の run の値）で、run の記録の中身は送っていない。送りは `opentelemetry-sdk` と `opentelemetry-exporter-otlp-proto-http` を `uv run --isolated` の使い捨ての環境に入れた。
- 分かった事:
  1. 過去の時刻の span（2026-11-04 00:16〜01:25）を、親子とミリ秒のまま受けた（公開の文書には書いていない点）。
  2. LLM の span に明示した `llm.cost.total` は使われず、模型の名 `claude-opus-5-5` とトークンから Phoenix が自分の表で費用を出した。表に無い模型の名では費用が空。LLM でない span の `llm.cost.total` も費用に数えない（属性としては残る）。
  3. 親の span の「中の和」（トークンと費用）は子の LLM の span から積み上がる。
  4. 会社の proxy の env が在ると 127.0.0.1 への送りが切られ、`NO_PROXY` で通った（2.3）。

## 4 直に送る道の確かめ（頼みの 3）

### 4.1 源で読んだ事（止めた Archon `2886e883d`）

- Archon は起動の最初に、自分の `process.env` から認証の 3 つを除く `CLAUDE_CODE_*` を消す（`packages/paths/src/strip-cwd-env.ts` の `stripNestedSessionMarkers`）。
- AI のノードの子の env は「消した後の `process.env` の上に、設定の層の env（対象の `.archon/config.yaml` の `env:`・DB の codebase の env・run の設定の層 `--config` の `env:`）を重ねた物」（`packages/provider-contract/src/agent-provider.ts` の `buildProviderSubprocessEnv`）。Claude の provider の `buildRequestSubprocessEnv`（`packages/providers/src/claude/provider.ts`）は、資格を渡す時の資格の名の入れ替えと `CLAUDE_CODE_STARTUP_FAILURE_RESULTS` の足しだけをし、重ねた後に `CLAUDE_CODE_*` を消し直さない。調べが引いた「合成の後にも再度除く」（Archon の PR #1154）は、この版の源には無い。
- なので設定の層の env に書いた `CLAUDE_CODE_ENABLE_TELEMETRY` は役に届く（`docs/design/archon.md` の「役の claude の env の届き方」と同じ道）。
- 実物の裏づけ: 工場は同じ道（run の層の env）で `CLAUDE_CODE_PROMPT_CACHE_TTL=5m` を渡す（`factory-cache-ttl`）。見本の run の役の会話の cache の書きは 1,577,557 トークンが全部 5 分で、1 時間は 0。届いている。
- Claude Code 自身の設定ファイルの env の道: AI のノードは `settingSources: [user]` で、隔離した `CLAUDE_CONFIG_DIR` の `settings.json` を利用者の設定として読む。Claude Code はテレメトリの env を利用者の設定の `env` から受ける（https://code.claude.com/docs/en/monitoring-usage「Set them in managed settings, or have each developer set them in their shell or `~/.claude/settings.json`」）。ただし工場の柵（`bin/_lib/toolset.py` の guard）は隔離した `settings.json` の鍵を `enabledPlugins`・`extraKnownMarketplaces`・`hooks`・`permissions` に限るので、`env` を置くと起動が止まる。設定の層の env が既に届くので、この道を開ける訳は無い。
- 本物の claude を起こす確かめは要らない（上の実物の裏づけで足りる）。直の道を採ると決めた時だけ、6 章の T5 の手順で 1 回確かめる（AI のノード 1 つと下請け 1 つの小さな graph、見込みの費用 0.1〜0.5 USD）。

### 4.2 直に送る道で取れる物と取れない物

- 取れる: Claude Code の公式の span（`claude_code.interaction` → `claude_code.llm_request`・`claude_code.tool`、下請けは親の `claude_code.tool` の下。https://code.claude.com/docs/en/monitoring-usage）。run の間に見える。
- 取れない・弱い:
  1. run とノードと周の木が無い。ノードごとに別の claude の起動なので、run 1 本が会話の数だけの別々のトレースになる。Claude Code は Agent SDK の起動では入ってくる `TRACEPARENT` を親にする（https://code.claude.com/docs/en/agent-sdk/observability）が、Archon は span を持たず、設定の層の env は run ごと（ノードごとに替えられない）なので、ノードの span の下には入れられない。
  2. span に費用が無い（費用は指標と `api_request` の出来事だけ）。
  3. 中身は既定で伏せられ、`OTEL_LOG_USER_PROMPTS`・`OTEL_LOG_TOOL_DETAILS`・`OTEL_LOG_TOOL_CONTENT` で開く。
  4. トレースは beta（`CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1` が要る）。
  5. run の間ずっと受け口が起きている必要があり、受け口が無いと送りの失敗が役の stderr に出る。過去の run（見本の run）は見られない。

### 4.3 組み合わせの比べ

| 道 | 木 | 費用 | 過去の run | 工場の変更 |
| --- | --- | --- | --- | --- |
| 後から変換だけ（推し） | run から往復まで | Archon の値 | 見られる | viewer/ だけ |
| 直に送るだけ | 会話ごとに別 | 無い | 見られない | 無し（利用者の設定） |
| 両方を同じ project | 往復が二重 | 二重に積む | 一部 | viewer/ だけ |
| 直 + run ごとの TRACEPARENT | run の下に平ら | 無い | 見られない | bin/ も |

- 推しは「後から変換だけ」。直に送る道は工場のコードを変えずに利用者が自分で開けられる（`--config` の `env:` か対象の `.archon/config.yaml` の `env:` に上の名を書く）ので、工場の側で組み合わせを作る訳は今は無い。走っている run を見たい要望が出たら、別の project に送る形で足す（二重を避ける）。
