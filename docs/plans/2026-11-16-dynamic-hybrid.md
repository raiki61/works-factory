# 工場の次の形の案（下書き）: 依頼ごとに AI が書く段取りを芯にし、観点はスキル、関門はコードに置く

工場の次の形の下書き。今は固定の YAML のグラフ（`works-factory-line` ほか）で流れを持っているが、次の形では依頼ごとに AI が段取り（Claude Code の dynamic workflows の JS）を書き、観点はスキル（`perspectives/`）、関門（別の目・書き換えられない試験・人の承認）は段取りの外のコードに置く。
最初に作るのは外側の殻と関門だけで、中身は先にスキルだけの形（8.3 の代案 C）で通し、次に dynamic を同じ殻に載せて、工場の依頼を数件回して今のグラフと比べる（5.1・11 章）。実装・試験の準備はまだ始めていない。持ち主の言葉は「とりあえず、案として下書きだけしておいて。けっこう難しいが、さっき言ったようなハイブリッドになるんじゃないかな。dynamicworkflow の」（2026-11-16、受付 20261116-020745-289f7b の頼み）。2026-11-16 の 2 版で、持ち主の「設計の骨格も固めて」を受けて 5 章を骨格に書き直し、採る基準（7 章）・移植の代案（8.4）・問い 5 を足した。同じ日の外の調査（12 章）の見立ては、関門を外のコードに置くことと 3 通りの比べは裏付けが在り、依頼ごとに AI が段取りを書くことは直接の裏付けの無い賭け。
持ち主に聞く問いは 1 つ（9 章の問い 4: 新しいリポジトリにするか、このリポジトリで作り替えるか）。ほかの問いは見立てと確かめ方を書いた。

この文書の語:

- 段取り: 依頼ごとに AI が書く JS のスクリプト（`agent()`・`parallel()`・`pipeline()`・`workflow()`・`schema`）。Claude Code の runtime が決まった形で回す。
- 固めた部品: 手順の決まった流れを 1 つの呼び出しにした物。便利な部品（保存した workflow。呼ぶかは AI が選ぶ）と、必ず通る部品（外へ出る口 `deliver()` の 1 つ。中に関門）の 2 種。
- 関門: 合否を機械が決める確かめ。作った AI と別の目・書き換えられない試験（`.factory/holdout/` の型）・人の承認の 3 つ。
- 観点: 何を見るか・何を良しとするか・よくある失敗の型の文。`perspectives/` の 1 フォルダ 1 スキル（持ち主の決め `perspectives-apart`）。
- 外側の殻: 依頼を受けて作業ツリーを切り、`claude -p` で働き手を起こし、終わった後に関門を通して納品するコード。
- 働き手: 殻が起こす AI の会話 1 つ。中身は、段取りを書いて回す形（dynamic）か、スキルだけで直す形（代案 C）。殻はどちらかを知らない（5.1）。

## 1. 窓口で持ち主と合意した事（前提。やり直さない）

1. 重さの元は固定の YAML のグラフ（約 1 万 5 千行・47 block・line 2,200 行・試験千本超・埋め 21）。原因の読み: 毎回違う修正依頼を枝で覆おうとした・AI の失敗を構造で塞ぎ続けた・形を縛る試験・Archon との摩擦。
2. 固定にするのは、手順が毎回同じ・飛ばされると高い・合否を機械で決められる、の 3 つを全部満たす所だけ（受付・関門・納品）。調べる・計画する・直すの真ん中は AI に任せる。モデルの弱さを補う部品には期限を付け、モデルが上がるたびに外して測る。
3. 形: AI が依頼ごとに段取りを書き、コードが決まった形で回す。手順の決まった流れは固めた部品として 1 つの呼び出しで呼ぶ。
4. 関門でコードが握るのは「必ず起こすこと」と「合否の決め」。中身の判断は AI でよい。関門は AI の段取りの中に置かない。実現の強い順は (a) 道具の側で書けなくする（push・書き込みの権限を AI の側から外し、口は関門つきの `deliver()` 1 つ。憲法 6 と同じ考え）(b) 段取りの外の固定の殻が受ける (c) 実行環境の権限（hooks・sandbox）。
5. 観点は流れを持たず単独で完結し、スキルどうしは名で指さない。どの観点を読ませるかは段取りが名指して決める（AI の自己選択は弱い: 選んだスキルを強制で読ませた時の合格率 55.4%、全部を読み込んだのは 49% の run）。
6. 薄い既定の流れ: 保存した workflow 1〜2 本（例 調べる→計画→審査→直す→確かめる）。AI はこれを下敷きに段を足し引きする。line から「本当に毎回通っている段」だけを抜いて作る。
7. 層は 3 つ: 観点（スキル）・流れ（AI が書く段取りと保存した型）・関門（コード）。superpowers との違いは、流れを観点に混ぜないことと、関門を文でなくコードに置くこと。
8. 土台: Archon の YAML を AI に直に書かせる案は外す（重すぎる。Archon 自身も AI に YAML を書かせる `archon-workflow-builder` を代わり無しに消した）。土台の候補は Claude Code 公式の dynamic workflows と pi-dynamic-workflows。
9. 進め方: まず外側の殻だけ作り、工場の依頼を数件回す。効いた流れを部品に固める。公式で足りない所が分かったら pi に載せ替えるか、そこだけ自作する。実行の仕組み（隔離・再開・権限・打ち切り・費用・画面）は最初は自作しない。
10. 測る: 今のグラフ・スキルだけ・dynamic の 3 通りで同じ依頼を比べる（7 章）。

根拠と出典は持ち主のノート（my_notes の `notes/knowledge/` の `ai-workflow-fixed-graph-vs-dynamic-with-gates.md` と `perspectives-skill-collection-idea-and-prior-art.md`）に在る。この文書は数え直していない数を、ノートと頼みの字のまま引く。

## 2. 公式の dynamic workflows で分かっていること（2026-11-16 時点）

出典は公式文書「Orchestrate subagents at scale with dynamic workflows」（my_notes の写し `reference/primary/ai/claude-code-dynamic-workflows.md`、2026-10-15 更新の版）と、Claude Code に同梱の書き方の手引き（スキル `workflow-authoring`。この会話で読んだ版）。

- 本体は素の JS。`agent(prompt, {schema, model, effort, isolation: 'worktree', agentType})` がサブエージェントを 1 つ立てる。`agentType` は Agent の道具と同じ名簿から役（例 読むだけの役）を選べる。`isolation: 'worktree'` は agent ごとに新しい git の worktree で回す。
- `workflow(name, args)` で保存した workflow を段取りの中から呼べる（手引きに書いてある）。入れ子は 1 段だけで、子の中の `workflow()` は例外を投げる。頼みの「保存した workflow を段取りから呼べるかは未確認」は、手引きの上では呼べる。頭なしの起動でも同じかは 9 章の問い 1 で確かめる。
- スクリプト自身はファイルとシェルに触れない。読み書きとコマンドはエージェントがする。`Date.now()`・`Math.random()` は例外を投げる（再開のため）。
- 走る途中で人の入力を受けない。段の間で人が確かめたければ、段ごとに別の workflow にする。
- `claude -p` と Agent SDK では走る前の確認が出ず、Workflow の道具の呼び出しをほかの道具と同じ権限の評価にかける。キーワード `ultracode` は利用者が打ったプロンプトでだけ効き、`-p` で渡したプロンプトからは始まらない（v2.1.210 から）。
- 立てたサブエージェントは利用者の権限の規則を使い、道具の呼び出しは会話と同じ権限の確かめと sandbox を受ける。
- 同時は既定 16、1 回の run のエージェントは合わせて 1,000 まで。`schema` に合わない返答は 5 回で失敗にする。トークンは通常の会話より大幅に多く使いうる（提供元の注意）。
- 使えるのは有料の全プラン・Anthropic API・Bedrock・Google Cloud・Microsoft Foundry。Claude 専用。
- 頭なし（`claude -p`）では、使用量の上限で待たずに失敗し、会話が終わると run も続かない。頭なしで workflow を起こすには、許可の決まりに `Workflow`（全部を通す。AI がその場で書いた段取りも入る）か `Workflow(<名前>)`（保存した 1 本だけ）を足すか、PreToolUse の hook で通す（公式文書。2026-11-16 に読み直した版）。
- `agent()` は、利用者が飛ばした時と、やり直しの後も API のエラーで落ちた時に `null` を返す。`parallel()` は中の例外を `null` にして自分は投げず、`pipeline()` は例外を投げた段の後ろを飛ばして `null` にする（手引き）。段が黙って抜けうる（5.3 で受ける）。
- 再開は、同じ script で起こし直すと、済んだ agent の結果を使い回す。途中の agent が失敗していると、その agent と、後ろで始まった agent は済んでいても回し直す。使用量の上限で落ちた agent は回し直し、済んだ物は使い回す（v2.1.318 から）。
- 会話を閉じて run が止まった時は、結果が会話のフォルダに残る。`claude --resume` で会話を継いでから workflow を起こし直せば続きから回り、新しい会話では初めからになる（公式文書）。頭なしの `-p` で同じかは書いていない（9 章の問い 5）。
- 使用量の上限で待って自動で続くのは、サブスクで入った対話の会話だけ。`claude -p` と Agent SDK では待たず、当たった agent が失敗する（公式文書）。
- 出力が止まった agent は同じ指図で初めから回し直す（5 回まで）。止まった回が変えたファイルは変わったまま残る。
- AI が段取りを書く時の大きさの目安は設定 `workflowSizeGuideline` で、既定は 10 体未満（`medium`）。観点ごとに広げる段取りを書かせるなら、隔離した設定で上げる。同時の数は環境変数 `CLAUDE_CODE_WORKFLOW_MAX_CONCURRENT_AGENTS` で替えられる。
- 同梱の workflow は `/deep-research` の 1 本だけ（公式文書の表）。公式文書は script の中の口に `agent()`・`pipeline()`・`parallel()`・`phase()`・`log()`・`args` を挙げ、`workflow()` と `budget` は手引きにだけ在る。
- script の `budget` は会話のトークンの目標で、越えると `agent()` が例外を投げる（手引き）。`workflow()` で呼んだ子は、親と同時の数・エージェントの数・`budget` を分け合う。
- サブエージェントは、会話と同じ CLAUDE.md を始めに読む（読まない組み込みの役が在る。手引き）。
- `claude -p` の旗（v2.1.325 の `claude --help` で見た分）: 返す形を縛る `--json-schema`・費用の上限 `--max-budget-usd`・会話の続き `--resume <会話の id>`・設定を渡す `--settings`・役を渡す `--agents`。hooks を飛ばす `--bare` も在る（殻は使わない。5.8）。
- 同梱の `/deep-research` は、Anthropic が前もって書いた保存した workflow（442 行の JS。問いを分ける → 検索 → 取得 → 3 票の検証 → まとめ）で、呼ぶ側は名前と `args` を渡すだけ。この案の「固めた部品」と同じ作り。

pi-dynamic-workflows（QuintinShaw 版）は `workflow(name)`・役ごとに道具を絞る `agentType`・`gate()`・`checkpoint()`・多 provider を持つ。作者中心・半年・月 2 版で、Claude のサブスクの枠は使えない（頼みの字）。`schema` を付けない `agent()` の項目を読むと失敗せず `undefined` になる件がある。どちらに載せても「返す形を必ず `schema` で指定する」を段取りの決まりにする。

## 3. E11 の 3 つの答え

1. Archon が持っているか: 持っていない。Archon は人が書いた固定のグラフ（承認ノード・`workflow:` のノード・loop・worktree）を回す道具で、依頼ごとに AI が流れを書く口は持たない。AI に YAML を書かせる `archon-workflow-builder` は代わり無しに消えた（Archon の変更記録の削除した workflow の表で、代わりの欄が None）。消えた版を v0.12.0 とするのは窓口の字で、写した原典では確かめていない。Archon が持つ物のうち、承認で止めて再開する・run の記録を残す、は次の形でも要る。それは代案 A（8 章）で借りる道を残す。
2. ASF が持っているか: 流れを AI が書く仕組みは持っていない。ASF の sdlc の束は固定のグラフ。採る型は 2 つ: 書き換えられない試験を作り手の外に置く holdout（`.factory/holdout/HOLDOUT.md`。機械が読む JSON はリポジトリの外に置き、確かめる側にだけ渡す）と、関門の決まりを文書 `factory/WORKFLOW_POLICY.md` に置いて共有のグラフに当てる型。採ったら `docs/asf-notes.md` に 1 行足す（E8）。
3. 本当に要るか: keep-essence の 12 の仕組み（`docs/design/README.md` の 10 章）は、次の形でも全部が要る。置き場が変わるだけで、捨てる物は無い。

   - 関門のコードへ移す（手順が毎回同じ・飛ばすと高い・機械で決まる）: 2 元から赤のテストの区別・6 回さなかった試験を名で残す・10 守りのファイルに触れたら人の承認を開く・3 テストの凍結のうち「凍った試験が変わっていない」の照らし・5 書き込みの出どころの突き合わせ。
   - 便利な部品（保存した workflow）へ移す: 1 赤緑の機械の判定（TDD の段取り）・4 3 回拒まれたら諦める・7 探し方の数え直し・8 食い違いの申し出と読むだけの裁定役。
   - 関門の「別の目」と観点へ移す: 9 独立設計と R1〜R4（別の目は関門で必ず起こし、何を見るかは `perspectives/` の観点）・12 世界の解に照らす（観点。どの依頼で読ませるかは段取りが決める）。
   - 11 直す単位ごとの記録が報告と承認に届く: 働き手の返す形 `deliver`（5.3）の欄にし、殻が報告に写す。

   なぜ今の形でなく作り替えるか: 1 章の 1 の重さ。グラフの枝で依頼の違いを覆う作りが、47 block・千本超の試験・埋め 21 を呼んだ。次の形は、真ん中の流れを依頼ごとの使い捨ての段取りにして、保守する物を観点（文）と関門（数百行のコード）に絞る。

## 4. 今の block の分け方（読んだ見立て）

block の YAML の `description` と line のノードの並びを読んで分けた。どの block も観点（何を見るか）は `perspectives/` に残る（#1050 で 67 個に広げ中）。ここで分けるのは、観点のほかに何が残るか。

### 4.1 関門のコードへ移す（外側の殻の中）

- test-gate の機械の部分: 対象のテストの走らせ方を決める（対象の宣言 `.review-checks.json` の段と `test_cmd`）・直す前の版で元から赤の試験を区別する・回さなかった試験を名で残す。AI が実行器を書く道（`suite-by-ai`）は便利な部品に回す。
- merge: 差分を hash で封じる（seal）・封じた hash と今の差分を照らして置く（apply・check）・守りのファイルの当たり。PR を作る道は今は `archon-pr` に任せている（`deliver-via-archon-pr`）ので、Archon を外すならこの決めを書き直す（6 章）。
- report の機械の部分: 結末の語・止めた段・回さなかった試験・費用・模型の事実を、AI の報告でなく殻が書く。平易な要約と初見の読み手は便利な部品に回す。
- spec-driven の形 check: 人と固めた仕様の表とリポジトリの食い違いを機械で照らす部分。
- answer-direction の役目は、人の承認を殻が受けるなら殻の受け口（答えの語と一言）に吸われる。一言の向きを AI に判じさせる部分は観点に残す。

### 4.2 便利な部品（保存した workflow。呼ぶかは AI が選ぶ）

- 調べの束: judge の中身の順（premises・purpose・world・素材の観点・diagnose・verify）を 1 本の保存した workflow にした物。依頼が小さければ AI が呼ばない。
- 計画と事前審査の往復: plan と plan-review（と independent-design）。往復を止める決め（`transition-not-count`）は部品の中のコードに置く。
- TDD の段取り: fix の組の子の loop（赤を取る・凍らせる・緑にする・3 回で諦める）。書き手の型（weapon-pin・weapon-remove・weapon-static・weapon-tdd-close・weapon-tidy・weapon-variant）は、この部品に渡す観点になる。
- 差分の審査と手直し: delta-review と lens。
- 独立の目の束: eyes（r1〜r4 と structure の after）。関門の「別の目」は 5.7 の別の会話で必ず起こすので、この束は、AI が納品の前に自分で掛ける下見になる。
- 設計の往復: theme と spec（対話モードの run で使う物）。
- 初見の読み手と案内の道: cold-read・guidance-path。

`workflow()` の入れ子は 1 段だけなので、保存した部品は葉にする（部品から部品を呼ばない）。今の憲法 3 の「block はほかの block を名指さない」と同じ形になる。

### 4.3 観点としてだけ残る（流れも部品も持たない）

- 素材の観点の 10 本: consistency-bypass・external-standards・gate-efficacy・hygiene・local-review・main-path-observation・prior-decisions・procedure-trace・provenance・test-double-fidelity。
- 判定の中の役: premises・purpose・purpose-review・world・diagnose・verify・head-depth・structure・independent-design。
- 目と書き手: r1・r2・r3・r4・weapon-* の 6 本・answer-direction・parallel-pr（ぶつかる hunk の見方。gh を読む部分は段取りの中のエージェントがする）。

### 4.4 AI の段取りに置き換わって消える

- line（2,200 行）・chain（周の鎖）・judge と eyes の graph（並べ方）・policy-check（入口の graph）・fix の親（組に分けて子を起こす並べ方）。
- head-depth の「run の深さを 3 段から選ぶ」は、段取りを書く AI が依頼ごとに段を足し引きする形に吸われる（`three-tiers`・`dynamic-depth` は書き直しが要る。6 章）。

## 5. 外側の殻の骨格

### 5.1 骨格の芯（4 つの決め）

1. 殻は中身を知らない。殻が起こす AI の会話（働き手）は、段取りを書いて回す形（dynamic）でも、スキルだけで直す形（8.3 の代案 C）でもよい。殻と働き手の間の約束は 5.3 の 1 つだけ。最初の版は代案 C の働き手で殻と関門を通し、dynamic は同じ殻に差し替えて載せる（11 章）。だから、問い 1（9 章）の答えを待たずに殻を作れて、dynamic が期待に届かなくても殻と関門は残る。
2. 殻は AI の申告を信じず、作業ツリーを読む。差分は殻が起点の commit から取り、試験は殻が回し直す。働き手の返す形（`deliver`）は報告の材料で、合否の材料にしない。
3. 殻は段ごとに止まれて、同じ run のフォルダから続きを回せる。段が済んだかは、その段の出すファイルが run のフォルダに在るかで決める（状態の表を別に持たない）。上限で落ちた働き手の回し直し・関門が落ちた後の戻し・人の承認の待ちは、この 1 つの仕組みで受ける。
4. 関門は 1 つ 1 つが単独の実行ファイルで、同じ口を持つ（入力は run のフォルダ、出力は結果の JSON 1 つと終了コード。5.7）。関門は働き手の会話を読まない。

### 5.2 入出力

- 入る物: 対象のリポジトリのパス・依頼の本文のファイル・出口の語（`place`〔差分を置くだけ〕か `pr`）・holdout の置き場（リポジトリの外。省ける）・計画で一度止まるか（省くと止まらない）・上限（時間・費用・回し直しの数。省ける）。
- 出る物: run のフォルダ（`${XDG_STATE_HOME:-$HOME/.local/state}/works-factory/runs/<run>/`）。止まった時も報告を出す（`stop-at-gates` と同じ）。

run のフォルダの中（名は仮）:

```text
runs/<run>/
├── request.md        依頼の本文の写し
├── start.json        対象・起点の commit・出口の語・上限（受付が書き、以後は変えない）
├── tree/             作業ツリー（対象の外）
├── home/             隔離した HOME と設定（働き手だけが使う）
├── work/<n>/         働き手の n 回目の起動（返した deliver.json・会話の id・終わり方・AI が書いた段取りの script の写し）
├── plan.md           計画で止まる run だけ
├── seal/             封じた差分と hash
├── gates/<名>.json   関門ごとの結果
├── answers/<n>.json  人の答え
└── report.md         報告
```

命令は 4 つ（名は仮）: 始める `start`・続きを回す `resume <run>`・人が答える `answer <run> <語> [一言]`・今を見る `status <run>`。

### 5.3 殻と働き手の約束

- 殻が渡す物: 作業ツリー（働き手の cwd）・依頼の本文・隔離した設定（観点のスキル・保存した部品・役の定義・権限の規則・hooks）・指示の md 1 本（英語。憲法 2 と同じ）・前の回の関門の指摘（在る時だけ。5.7）。
- 働き手がすること: 作業ツリーの中で直し、直す単位ごとに commit する。外へは出さない（出す資格を持たない。5.8）。
- 働き手が返す物: `deliver` の形の JSON 1 つ。欄は、目的・単位ごとの記録・回した試験・回さなかった段と訳・残った問い・終わり方（直した・できない）。
- 働き手は、見える試験を中で回して直すのを繰り返してよい（早い確かめ）。殻の関門は最後の決めで、中の確かめの代わりではない。最後の浅い検査だけに頼る作りは足りないという測定が在る（12 章）。
- `deliver` は道具でも関数でもなく、会話の最後の返す形の名（段取りの script は道具を足せない）。形は殻が会話の出口で縛る（`claude -p` の `--json-schema`。2 章）。段取りの中の `schema` は agent ごとの返す形で、それとは別。
- 段取りの中で agent が落ちても、`parallel()`・`pipeline()` は例外を投げず `null` を返す（2 章）。段が黙って抜けうるので、「回さなかった段と訳」を必須の欄にし、そのうえで殻は欄を信じずに作業ツリーと試験で確かめる（芯の 2）。

### 5.4 段の順

1. 受付（コード）: 依頼のファイルと対象を確かめ、run のフォルダと `start.json` を作る。起点の commit を決め、対象の外に作業ツリーを切る。
2. 支度（コード）: 隔離した設定を組む。`CLAUDE_CONFIG_DIR`・HOME・XDG を run のフォルダの下へ向け、認証を子に渡し、選んだ物だけを置く。
3. 計画（AI。入力で頼んだ run だけ）: 働き手を読むだけの道具で起こし、`plan.md` を返させて止まる。人が `answer` で答えたら次へ進む。拒んだら一言を添えて計画をやり直す。大きい依頼で向きの違いを、直す前に安く見つけるための段。
4. 直す（AI）: 働き手を起こす。中身は代案 C か dynamic（芯の 1）。
5. 関門（コード。5.7）。
6. 納品（コード）: `place` は封じた差分を置く。`pr` は殻が持つ push の資格で枝を積み、PR を作る。

### 5.5 働き手が落ちた時と回し直し

- 働き手の終わり方は 3 つ: 返した（`deliver.json` が在る）・落ちた（使用量の上限・エラー・時間切れ）・できないと返した。
- 頭なしの dynamic は、使用量の上限で待たずに失敗し、会話が終わると run も続かない（2 章）。落ちても作業ツリーの commit は残るので、`resume` は新しい会話を起こし、「作業ツリーの今の姿と前の回の記録から続ける」指示を渡す。
- 同じ会話の続きから回す道（`claude --resume <会話の id>` で継いで workflow を起こし直す）は、済んだ agent の結果を使い回せて安い。対話の会話では公式文書に在る道で、頭なしで効くかは未確認（9 章の問い 5）。骨格はこれに頼らず、効くと分かったら `resume` の中の近道として足す。
- 上限に当たった時、最初の版の殻は待たない。落ちた訳を報告に書いて止まり、いつ `resume` を打つかは呼ぶ側（人か、会社の受付の dispatch）が決める。
- 回し直しの数には上限を置く（`start.json`）。越えたら人に止める。

### 5.6 上限（時間・費用）

- 時間: 殻が働き手の process を時間で止める。どの形の働き手にも必ず効く。
- 費用: `claude -p` の `--max-budget-usd`（API の費用の上限）。サブスクの枠で回す時に効くかは未確認（問い 5）。
- 段取りの中のトークン: script の `budget`（会話のトークンの目標。越えると `agent()` が例外を投げる）。頭なしで目標を渡せるかは未確認（問い 5）。
- 1 回の run のエージェントは 1,000 まで立つ（2 章）。止めにはならない高さなので、時間と費用の 2 つで止める。

### 5.7 関門

口（どの関門も同じ）: 入力は run のフォルダ。出力は `gates/<名>.json` と終了コード。JSON の欄は、合否 `pass`・訳 `why`・証拠のファイル `evidence`・働き手へ戻してよい字 `feedback`（無ければ空）。

欠けは不合格と読む: 結果の JSON が無い・読めない・`pass` の欄が無い時は落ちた扱いにする（落ちた働き手や抜けた段を合格と読まない）。

順（安い順。どれかが落ちたら後ろを回さない）:

1. 形: 差分が作業ツリーの中だけか・holdout と守りのファイルに触れていないか。守りのファイルに触れたら 5 の人の承認を必ず開く。
2. 封じ: 差分を hash で封じる（merge の seal）。以後の関門は、起点の commit を新しく取り出した所に封じた差分を当てた写しで回す。働き手が触った作業ツリーでは回さない（働き手と同じ作業ツリーで試験を回す作りは、試験の書き換えを止められない。12 章の先行例の弱い所）。
3. 試験: 殻が対象の試験を走らせる（test-gate の機械の部分。元から赤の試験は区別する）。続いて holdout の試験を、ここで初めて別の写しに入れて走らせる。働き手は holdout を見ていない。
4. 別の目: 新しい `claude -p` の会話を、読むだけの道具で起こす。渡すのは目的・封じた差分・試験の結果だけで、働き手の会話は渡さない。返す形を `--json-schema` で縛り、通すかは返答の欄で殻が決める。何を見るかは観点（R1〜R4 の `perspectives/`）。
5. 人の承認: 報告を書いて止まる。人は `answer` で答える（通す・拒む・一言）。殻は答えの時に封じた hash と今の差分を照らす。

落ちた時の戻し:

- 形・試験・別の目が落ちたら、その関門の `feedback` を添えて 4 の「直す」へ戻す（回の上限は `start.json`。越えたら人に止める）。
- holdout の関門は `feedback` を書かない。落ちた試験の名や中身を働き手へ戻すと、次の回から隠した試験でなくなる。holdout が落ちたら人に止める。
- 人が拒んだら、一言を `feedback` として「直す」へ戻す。
- 戻して作業ツリーが変わったら、封じ直して関門を 1 から全部やり直す（前の回の合格を持ち越さない）。

関門そのものの確かめ: 関門ごとに、落ちるはずの差分（作業ツリーの外に書く・守りのファイルに触れる・試験を消して緑にする・holdout で落ちる誤り）を fixture に持ち、必ず落ちることを殻の試験で見る。コードの関門も黙って壊れる（12 章の dark-factory の、いつも PASS と出る疑いの関門）。

### 5.8 権限の縛り方（関門 (a)〜(c)）

- (a) 道具の側で書けなくする: 働き手の環境に push の資格を置かない。gh は読むだけの代わり（`bin/_lib/no-post-bin/` の `gh`・`works-gh`。持ち主の決め `roles-read-only-gh`）を `PATH` の頭に置く。SSH の鍵と git の資格の助け手は隔離した HOME に置かない。holdout は作業ツリーにも隔離した HOME にも置かず、関門の 3 で殻が初めて取り出す。働き手から見て外へ出る口は、会話の最後の返す形 `deliver` の 1 つだけになる。
- (b) 働き手の外の殻が受ける: 関門の順と合否の決めは殻のコードが持つ。働き手の process が終わってから回すので、働き手は関門を飛ばせない。
- (c) 実行環境の権限: 隔離した設定の `permissions.deny`（`git push`・作業ツリーの外への書き込み）と sandbox（書ける所を作業ツリーだけに・外への通信を許した宛先だけに）を置く。書き込みの記録の hooks を置き、編集の道具を通らない変更を受け付けで拒む（keep-essence の 5）。deny の規則は字の前方一致で、`sh -c` などで回り道ができるので、(c) は (a) の後ろの守りとして置く。hooks を飛ばす起動の旗（`--bare`）は使わない。hooks が段取りのサブエージェントに効くかは未確認（問い 1）で、効かなくても (a) と (b) は崩れない。

### 5.9 薄い既定の流れ（dynamic の働き手だけ）

保存した workflow を 1 本（名は仮に `works-default`）置く。段は「目的を 1 文にする → 調べる → 計画 → 計画の審査 → 直す（TDD の部品）→ 確かめる → `deliver` を返す」。AI はこれを下敷きに、依頼ごとに段を足し引きした段取りを書く。足し引きが要らない依頼では、既定の流れをそのまま名で呼んでよい。AI が書いた script は、起こす前に Workflow の道具の PreToolUse の hook で受けて run のフォルダに写し、形（返す形に `schema` が在るか・`deliver` の欄を返すか）を機械で見る見立て（hook は親の会話の道具の呼び出しに掛かるので、サブエージェントに hooks が効くかの問い 1 とは別。試しで確かめる）。外の先行例の「AI が流れを作る → 機械で見る → 決まった形で回す」（12 章の Kilroy）と同じ型。

line から「本当に毎回通っている段」を抜く手順:

1. 今の工場の run の記録（Archon の run の記録と、`viewer/` が組むトレース）から、ノードごとに通った run の割合を数える。
2. 9 割以上の run で通った段だけを既定の流れに入れる。それより少ない段は便利な部品に回す。
3. 記録の数が足りない時は、line のノードの並びで `when` の無い include（judge・eyes・report・merge）と、ほぼ必ず開く承認ノードを候補にし、上の段の案を当てる。

既定の流れはモデルの弱さを補う部品なので、期限を付ける（5.10）。

### 5.10 期限を付ける部品

モデルが上がるたびに外して測る物（1 章の 2）。最初の版で印を付けるのは次の 3 つ。

- 既定の流れ `works-default`（AI が段取りを一から書いても同じ合格率なら外す）。
- 観点を段取りが名指して読ませる決まり（スキルの自己選択が強くなれば外す）。
- TDD の部品の「3 回で諦める」の数（モデルが自分で止まれれば外す）。

関門（別の目・holdout・人の承認）には期限を付けない。モデルの強さでなく、作った物と確かめる物を分ける仕組みだから。

### 5.11 今の起動の部品のどれを使うか（2026-11-16 に源を読んだ分）

- そのまま写す: 認証の読み口 `bin/_lib/claude_auth.py`・書いた記録と読んだ記録の hooks（`bin/_lib/record-write.py`・`bin/_lib/record-read.py`）・読むだけの gh（`bin/_lib/no-post-bin/`）・隔離 `bin/_lib/isolate.py`（58 行。Archon の家を向け直す 1 行を外す）。
- 関数だけ写す: `bin/_lib/startpoint.py` は、汚れた対象を包んだ commit にする `wrap` を使う。作業ツリーを切るのは今は Archon なので、そこは殻が新しく書く。`bin/_lib/apply.py`（421 行）は、差分を置く `put`・`git_apply` を使う。本体は Archon の run の記録を読み、`launcher`・`place` を import しているので書き直す。
- 読んでから決める: `bin/_lib/toolset.py`（1,227 行）・`bin/_lib/auth_launch.py`（772 行）・`bin/_lib/hostgh.py`。Archon を名指す所が少ない（4・2・3 か所）ことまでしか見ていない。merge と test-gate の script の機械の部分も、block の `src/` と pack の共通の部品への頼りを見ていない。
- 外す: `bin/_lib/place.py`（Archon の源の取り寄せ）・`bin/_lib/launcher.py` の Archon を起こす部分・`bin/_lib/runstop.py`・`bin/_lib/recordroot.py`・埋め（`docs/polyfills.md`）・`workflows/` の YAML の全部。
- `viewer/` のトレースとページの部品は、読む記録を Archon の run から殻の run のフォルダと Claude Code の会話の記録に替えれば使える見立て（源は読んでいない）。

## 6. 書き直しが要る持ち主の決め（E10）

次の形は、今の決めのいくつかと向きが違う。作り始める前に、持ち主の言葉つきで決めを書く。

- `on-archon-only`・`asf-on-archon`・`essence-is-graph`・`one-launcher`: Archon の上に載ること・エッセンスはグラフの形、の前提が変わる。
- `deliver-via-archon-pr`: PR を作る道を殻に戻す。
- `three-tiers`・`dynamic-depth`・`depth-by-reason`: run の深さを 3 段から選ぶ形が、AI が段を足し引きする形に変わる。
- `full-suite-in-ci`・`related-tests-only`: そのまま生きる（殻が回すのは変更に関わる試験だけ）。
- `coexist-before-switch`: そのまま生きる。次の形は今の工場の横に並べて作り、持ち主の動作確認の後に切り替える。

## 7. 測る

同じ依頼を 3 通りで回して比べる: 今のグラフ（`works-factory-line`）・スキルだけ（`claude -p` に依頼と `perspectives/` を渡すだけ。殻と関門は同じ物。5.1 の芯の 1）・dynamic（この案）。

- 比べる値: 関門の合格率・トークン・時間・人の手戻り（承認で拒んだ数と、置いた後に人が直した行の数）。
- 段取りが名指した観点を、エージェントが本当に読んだ割合（読んだ記録の hooks `bin/_lib/record-read.py` で数える）。
- 今のグラフで手が届かなかった依頼の割合（止めの語が `round_limit` や受け付けの拒みで終わった run と、人が工場の外で直した依頼）。
- グラフの変更の頻度と手間（今のグラフは git の履歴の `workflows/` の commit の数と行の数。次の形は保存した部品と観点の変更）。
- 関門を外した時の見逃し: 別の目と holdout を 1 つずつ外して回し、通ってしまった誤りの数。

採る基準（測る前に決めておく。数は持ち主と決める）:

- 既定の働き手はスキルだけ（代案 C）から始める。dynamic を既定にするのは、関門の合格率か人の手戻りで、決めた幅より良かった時だけ。
- 合格率が並んだら、トークンと時間の少ない方を既定にする。dynamic は、スキルだけが落とした型の依頼（大きい・並べて調べる所が多い・別の目を多く要る）にだけ使う道として残す。
- dynamic がどの型でも勝たなければ、段取りと保存した部品は作らず、殻・関門・観点の 3 つで工場にする。
- 10 章の 3〜5 件では、差が偶然かを言えない。この数で言えるのは「明らかに駄目か」までで、既定を替える決めは件数を足してからにする（外の測定は 20 件でも 1 マス ±20 ポイントの幅だった。12 章）。
- 腕ごとのトークンと費用を必ず並べる。外の観測では、トークンの量だけで出来の差の大半を説明できた例が在る。できれば費用をそろえた比べ（スキルだけの腕に同じ費用を使わせる）も足す。
- 落ち方を種類で数える: 試験の書き換え・範囲の外の変更・関門が誤って通した件・関門が誤って落とした件。

## 8. 代案

### 8.1 代案 A: Archon を薄い外回りとして残し、中の 1 ノードで dynamic を回す

line の代わりに短い YAML（受付 → `claude -p` で段取りを回す 1 ノード → 関門の script のノード → 承認ノード → merge）を Archon で回す。

- 良い所: 承認で止めて再開する・run の記録・`viewer/` のトレースが今のまま使える。殻の `bin/` も今のまま。
- 選ばない訳: 外回りは 6 つほどの段を順に回すだけで、DAG の道具が要らない。Archon を残すと、源の取り寄せと bun（`bin/_lib/place.py`）・埋め 21・版の止めの保守が残り、重さの元の 1 つ（Archon との摩擦）が消えない。Archon は固定のグラフを製品にする向きへ進んでいて、この使い方は Archon の芯から外れる。
- 戻す時: 殻の自作で承認と再開が重いと分かったら、この代案に寄せる。殻の関門は script のノードとしてそのまま移せる形（入力は run のフォルダ、出力は JSON）で書いておく。

### 8.2 代案 B: pi-dynamic-workflows に載せる

- 良い所: `gate()`・`checkpoint()` を持ち、多 provider で回せる。編集したスクリプトから再開できる。
- 選ばない訳（最初は）: Claude のサブスクの枠が使えず、普通の利用者（`claude /login` しただけの人。`others-may-use`）の既定の道にならない。作者中心で版が速い。公式で足りない所（9 章の問い 1・2）が分かった時の載せ替え先として残す。

- 載せ替える時に書き直す物（pi に限らず、より良い土台が出た時も同じ）: 働き手の起こし方（`claude -p` の旗と隔離した設定）・保存した workflow の script・実行環境の権限（5.8 の (c)。権限の規則・hooks・sandbox は Claude Code の物）。変わらない物: 殻の段と run のフォルダ・関門・観点・資格を置かない守り（5.8 の (a)）・働き手との約束（5.3）。載せ替えを安く保つために、保存した workflow は少なく小さく持ち、関門を土台の機能（`gate()` など）に置かない。pi の script の書き方が公式とどこまで同じかは確かめていない。

### 8.3 代案 C: スキルだけ（段取りを書かせない）

`claude -p` に依頼と観点のスキルを渡し、後ろに同じ関門を付けるだけ。代案であり、殻を作る時の最初の働き手でもある（5.1 の芯の 1・11 章）。合格率が dynamic と変わらなければ、段取りは要らないことになる（7 章の採る基準）。

### 8.4 代案 D: 今の Archon のグラフを、保存した workflow にそのまま移す

`/deep-research` と同じ作りで、今の固定の流れを JS の script に書き直して保存する案（持ち主の問い「Archon で書いている処理を dynamic workflow に移植することもまずはできるのか」）。

- できる所: AI のノード（`prompt:` 126 個）は `agent()` に、`depends_on`・`when`（224 個）・回数の上限つきの繰り返し（37 個）は JS の順・`if`・`while` に、そのまま移る。Archon との摩擦（埋め 21・源の取り寄せ・版の止め）は消える。
- きれいに移らない所:
  - script のノードが 305 個で、AI のノード（126 個）の 2 倍を超える。段取りの script はファイルにも shell にも触れないので、今の Python を回すには、ノードごとに「この命令を打て」と頼むエージェントを 1 つ立てることになる。コードが決めていた所に AI が挟まり、費用と時間が増え、打ち間違いの余地ができる（憲法 1 の「値はコードが計算する」が崩れる）。
  - 入れ子は 1 段だけ。今は 周の鎖 → line → judge → block と 3 段の入れ子なので、平らに潰すか、会話を分ける。
  - run の途中で人に聞けない。承認のたびに会話を切り、殻が続きを起こす。
  - AI のノードの指示の md を script は読めない。指示を script の中に写すか、エージェントに md を読ませる。
- 選ばない訳: 重さの元の 4 つ（1 章の 1）のうち、消えるのは Archon との摩擦の 1 つだけ。枝で依頼の違いを覆う作りは、YAML 1 万 5 千行が同じ大きさの JS に変わるだけで残る。
- 使い道: 葉の小さな block を 1 つだけ（AI のノードが主で script の少ない物。例 独立の目の束 eyes）保存した workflow に移すのは、問い 1 の試しを兼ねた最初の「便利な部品」として筋が通る。全体の移植はしない。

## 9. 残る問いと見立て

### 問い 1: 公式の dynamic workflows のサブエージェントに、worktree の許可の決まりと hooks が効くか。頭なしの起動で workflow の承認がどう扱われるか

- 見立て: 権限の規則と sandbox は効く（公式文書は、立てたエージェントが利用者の権限の規則を使い、会話と同じ権限の確かめと sandbox を受けると書く）。hooks は文書に書いていないので分からない。`isolation: 'worktree'` の agent の worktree が、殻の切った作業ツリーの中にできるか外にできるかも書いていない。頭なしの起動では走る前の確認は出ず、Workflow の道具の呼び出しがほかの道具と同じ権限の評価を受ける。だから殻は隔離した設定で Workflow の道具を許す必要がある。`ultracode` は `-p` からは効かないので、指示の字で段取りを書かせるか、保存した既定の流れ `/works-default` を名指して起こす。
- 確かめ方（実装の前に一度だけの小さな試し。一時のフォルダと隔離した設定で）: (1) `permissions.deny` で 1 つのファイルへの書き込みを禁じ、PreToolUse と PostToolUse の hooks が 1 行ずつ記録を書く設定を作る。(2) `claude -p` で、2 つの agent（1 つは `isolation: 'worktree'`）がそのファイルを書こうとする段取りを回させる。(3) 拒まれたか・hooks の記録に agent の呼び出しが出たか・worktree がどこにできたかを見る。(4) 同じ設定で、指示の字だけで Workflow が起きるか、`/works-default` を名指すと起きるかを見る。

### 問い 2: 関門 (a) を Claude Code の上で実現できるか（AI 側から push・holdout への読み書きを確実に外せるか）

- 見立て: できる。ただし権限の規則でなく「資格と物を置かない」で実現する。push は、AI の環境に資格が無ければ字をどう回しても通らない。holdout は、殻が関門の時まで AI の見える所に置かなければ読めない。sandbox で読める所を作業ツリーと隔離した HOME に絞れば、利用者の HOME の下の holdout にも届かない。残る穴は、AI が作業ツリーの中の試験を書き換えて緑にすること。これは holdout（AI が見ていない試験）と、凍った試験の hash の照らし（keep-essence の 3）で塞ぐ。
- 確かめ方: 問い 1 の試しに足す。(1) 隔離した環境で `git push`・`gh pr create`・`sh -c 'git push'` を打たせ、どれも通らないことを見る。(2) holdout を置いた場所を `cat`・`find` で探させ、見つからないことを見る。

### 問い 3: 今の工場（`bin/`・dispatch・`viewer/`）のどこを外側の殻と記録に流用できるか

- 見立て: 1 版の「大半はそのまま使える」は楽観だった。源を読んだ結果は 5.11（そのまま写す・関数だけ写す・読んでから決める・外す）。そのまま写せると確かめたのは小さな部品で、大きな 2 つ（`bin/_lib/toolset.py`・`bin/_lib/auth_launch.py`）は読んでいない。
- dispatch（works-dispatch。このリポジトリの外のプラグイン）は、持ち主の会社の受付と納品の口として、殻の前に置ける。殻は dispatch を知らない（依頼のファイルと対象のパスを受けるだけ）。上限で落ちた run をいつ `resume` するかも、呼ぶ側の dispatch か人が決める（5.5）。
- 確かめ方: 殻を書く時に、5.11 の「読んでから決める」の部品を import だけで呼べるか（Archon の物を引きずらないか）を 1 つずつ見る。

### 問い 4（持ち主に聞く）: 新しいリポジトリにするか、このリポジトリの中で作り替えるか

- 見立て（推し）: 新しいリポジトリ。訳: 今の決まり（E1〜E7・E12・E16・E17・E19・E20 の `workflows/` の決まり、千本超の試験、層の地図）はグラフの形を縛る物で、次の形にはほとんど当たらない。同じリポジトリで作り替えると、並べて比べる間（`coexist-before-switch`）ずっと 2 つの形の決まりが混ざる。持ってくる部品（問い 3 の「使える」）は元の名前のまま写し、どこから写したかを commit に書く（E18 と同じ）。
- 代わり: このリポジトリの根に新しい置き場を足す（E10 の決めが要る）。良い所は `perspectives/` と `bin/_lib/` を写さずに使えること。悪い所は上の決まりの混ざり。
- 持ち主が決めること: リポジトリを分けるか（分けるなら名前と公開か）。

### 問い 5: 頭なしで、落ちた run を同じ会話の続きから回せるか。費用とトークンの上限が効くか

- 見立て: 再開は効く見込みで、上限の 2 つは分からない。公式文書は、閉じた会話を `claude --resume` で継いで workflow を起こし直せば済んだ結果を使うと書くが、頭なしの `-p` で同じとは書いていない。`--max-budget-usd` は API の費用の上限と説明に在り、サブスクの枠で回す時の振る舞いは書いていない。`budget` の目標は利用者が打つ「+500k」の形の指図から来るので、`-p` のプロンプトから渡せるかは書いていない。
- 骨格はどれにも頼らない（回し直しは作業ツリーから、止めは時間で。5.5・5.6）。効くと分かった物だけ近道として足す。
- 確かめ方（問い 1 の試しに足す）: (1) 3 つの agent を順に回す段取りを `claude -p` で起こし、2 つ目の途中で process を止める。`--resume` で継いで `resumeFromRunId` を渡させ、1 つ目が回し直されないかを見る。(2) `--max-budget-usd` を小さくして、サブスクの認証と API キーの認証のそれぞれで止まるかを見る。(3) `-p` のプロンプトにトークンの目標を書き、script の `budget.total` が `null` でないかを返させる。

## 10. 最初に回す依頼の選び方

- 数は 3〜5 件。工場のリポジトリ自身の、もう merge した PR から選ぶ（答えが在るので、合否を人が比べやすい）。merge の前の commit を起点にし、PR の元の依頼の字を依頼にする。
- 選ぶ型: (1) 今のグラフが通した小さな直し 1〜2 件（比べの基準）。(2) 今のグラフで手が届かず、人が工場の外で直した依頼 1 件（次の形が効くかの本題）。(3) 文書だけの直し 1 件（TDD の部品を呼ばない段取りになるか）。(4) 守りのファイルに触れる直し 1 件（関門の人の承認が必ず開くか。keep-essence の 10 は本物の run でまだ一度も通っていない）。
- holdout: 選んだ PR が足した試験を holdout にし、AI に見せずに関門で走らせる。
- 回す順: スキルだけ（代案 C）→ dynamic → 今のグラフ。同じ起点・同じ依頼の字で回し、7 章の値を並べる。

## 12. 外の先行例と証拠（2026-11-16 の調査）

同梱の `/deep-research` で調べた（出典 24 本・主張 25 個を 3 票で検証・23 個が残った）。ここに書くのは残った主張だけ。当てはめは全部が類推で、「AI が書く段取り + 外のコードの関門」の形を直に測った物は 1 つも無かった。

裏付けが在る所:

- 関門を外のコードに置く・push の資格を持たせない: 確かめた先行例（Archon・StrongDM の Attractor・dark-factory-experiment）は、どれも関門を流れの中に置く。Archon は働き手と同じ作業ツリーで試験を回し、Attractor の関門はノードの自己申告を見うる。この案の隔離はそれより強い。ただし、外に置いた方が効くと直に測った証拠は無い。
- 隠した試験を置く動機: StrongDM が「狭い試験は `return true` で通される」「試験は書き換えられる」と報告し、筋書きをコードの外に置いて holdout と呼ぶ（1 社の体験談。StrongDM の物は LLM が判じる筋書きで、コードが回す隠した試験とは別物）。
- 最後に人の承認を残す: dark-factory は検証を通れば自動で merge する作りで、一度も動かしていない PR が自動で入って同じ日に取り消された記録が在る。
- 関門を層にする: 多エージェントの失敗を調べた論文（MAST。arXiv 2503.13657）は、最後の浅い検査だけに頼るのは足りず、途中にも確かめを持てと書く（5.3 の早い確かめ）。
- スキルだけの腕を本命の比べ相手にする: Anthropic は 2025-06 に、コーディングは調査より並べられる仕事が少なく多エージェントに向きにくいと書き、多エージェントはチャットの約 15 倍のトークンを使うと報告した（調査の製品での観測）。SWE-bench Verified で計算量をそろえた多エージェントの 4 構成が単一を下回った測定も在る（arXiv 2512.08296。20 件の部分集合で統計は弱い）。どれも 1 世代以上前のモデルの値。

賭けの所:

- 依頼ごとに AI が段取りを書く: 直接の裏付けが無い。一番近い先行例は逆を選んでいる。Archon は「workflow が段と確かめと関門を固め、エージェントは段の中の判断を出す」と書き、実行の時に組む構造を退ける（AI が書いた workflow を別の run として回す道は残す）。dark-factory の作者は、何を回すかを AI に決めさせたら在りもしない作業を回した、と 1 文で書く（頻度もモデルの名も無い）。同じリポジトリは、固定の振り分けの決まりのせいで工場が約 3 か月何もしなかったことも記録していて、固定の側の弱さも在る。
- 中間の道: Kilroy（Attractor のコミュニティの実装）は、AI が宣言の形のグラフを作り、機械で見てから決まったエンジンで回す（5.9 に採った）。

今回は何も言えない所（検証を通った主張が残らなかっただけで、否定されたのではない）:

- スキルの自己選択と名指しで読ませる形の比べ・観点と流れを分けるのが勧められた型か。1 章の 5 の数（55.4%・49%）は、この調査では確かめ直せていない。
- 隠した試験の効き目の測定（ImpossibleBench・METR など）・新しい会話の別の目と自己審査の比べ・コードの関門と文の指図の比べ・資格の隔離の実務。
- 名を挙げた OSS の大半（LangGraph・OpenHands・SWE-agent・Aider・spec-kit・BMAD・superpowers・pi-dynamic-workflows など）と、Cognition の「Don't build multi-agents」・薄い足場の結果。
- サブエージェントへの権限と hooks の振る舞い（問い 1 のまま）。

骨格へ入れた直し: 欠けを不合格と読む・封じた差分を新しく取り出した所に当てて試験を回す・関門そのものを落ちるはずの差分で確かめる（5.7）、中の早い確かめを残す（5.3）、AI が書いた script を起こす前に写して形を見る（5.9）、比べの件数と費用と落ち方の種類（7 章）。
