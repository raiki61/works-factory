## 語

- 工場: このリポジトリの Archon のグラフ（works-factory）。run は工場の 1 回の実行。
- 対話モード: 入力 `design_talk` が `true` で無人でない run（`docs/design/line.md` の 3.1）。今は計画の往復の末尾で人に設計を相談する。
- 計画の往復: 修正案の役（block `plan`）と事前審査の役（block `plan-review`）の往復（line の loop `plan-rounds`）。
- 今の設計の相談: 計画の往復の末尾の承認ノード `gate-design` で、修正案を人に見せて相談する今の仕組み（持ち主の決め `dialogue-gate-in-loop`）。名に「設計」が入るが、中身は修正案（ファイルと試験の計画）。この下書きが足す「設計の段」とは別の物。
- 受け箱: 対話モードの run の置き場の `talk/notes.txt`。人が往復の間に 1 行ずつ指摘を足す（持ち主の決め `human-notes-in-rounds`）。
- テーマ: 修正の依頼でない設計の問い（例「直し方の型を何段に分けるか」）。
- 設計の段: この下書きが足す段。テーマから設計の案を書き、審査し、持ち主の承認で固める。機械の名は `theme-*`（今の `design-*`・`gate-design` と重ならない名にした。13 章の 9）。
- 設計の案: 設計の段の書き手が 1 往復ごとに返す JSON（3 章。形の名 `theme-design`）。
- 設計の往復: 設計の段の書き手と審査役の往復（line の loop `theme-rounds`）。
- 降りる: 承認された設計から依頼の行を作り、同じ run のまま判定と計画の往復へ進むこと（8 章）。
- 取り次ぐ会話: 工場の外で持ち主と話す AI の会話（本社の窓口や、利用者が works-factory を呼ぶ Claude Code の会話）。持ち主の言葉を読み取り、run への答えに整える。工場の機能ではない（issue #862 の「役の分け方」）。
- 周: loop の 1 回り（設計の往復・計画の往復の 1 往復分）。「周の頭」は 1 回りの最初の node（`theme-turn`・`design-turn`）、「開く周」は承認ノードを開く回り、「上限の周」は安全の上限（20）に着いた回り。下の「周の鎖」の周とは別の意味。

```text
  │    → theme-rounds（loop）: theme-turn → theme（書き手の block）→ theme-review（plan-review の形 theme）
  │                            → theme-out → theme-talk → gate-theme（開く周だけ）
  │    → theme-descend（承認なら依頼の行を書く。止める答えなら報告へ）
  └─ どの run も: request-in（依頼の出どころを 1 つに選ぶ relay）
       → test-gate-base → judge → … → plan-rounds（今の計画の往復と gate-design）→ 修正 → 最後の承認 → 報告
```

### 2.1 入口

1. 依頼のファイル（`lib/carry.py` の `parts` が読む `{findings, pr, issue, answers, prior_failures, constraints}`）に欄 `theme` を足す。値はテーマの文（字）か、対象の根からの md のパス。`start` がテーマの写しを run の置き場の `theme.md` に固め、配る値 `ports` に `theme`（写しのパス。テーマの無い run は空の字）を足す。テーマの md には、テーマの文のほかに、名指す設計書の節（0.3 と同じ「`<path>` N 節」の書き方）と、取り次ぐ会話が始めに頼んだ調べものの結果を書いてよい（第 2 版で独立設計の D1 から採った。17.2）。欄を分けずに md 1 本で受ける。
   - 新しい起動の入力にしない訳: 持ち主の決め `one-input`（入口ごとに流れを分けず 1 つの入力の形にそろえる。当て方は始めの 1 か所）。依頼のファイルの欄なら、取り次ぐ会話が 1 つのファイルにテーマと答え（`answers`）を書いて渡せる。
2. 組めない物（`start` が AI の前で止め、訳を出す）: `findings` が空でない・`pr`・`base`・`spec_table`・`fix_fixture`・周の鎖の子。第 1 版は「テーマだけの run」に絞る（テーマと依頼の行を一緒に受ける形は 14 章の 1）。今の `start` は依頼の行も差分も無い run を拒む（`workflows/line/scripts/start.py:268` の `refuse_empty`）。テーマの欄が在る run はこの拒みの「依頼が在る」に数える（テーマも空なら今どおり拒む）。
3. テーマの run は `design_talk` が真の run に限る。偽か空なら `start` が AI の前で止め、`design_talk=true` を足す案内を出す（入力の意味を黙って上書きしない。13 章の 2）。この止めは `unattended` に関わらず先に効く。`design_talk` が真で無人の run（`unattended` も真）にテーマを渡した時は、今の無人の run の決まりをそのまま当てる（2.4。12 章の問い 3 の答え）。

### 2.2 設計の段の並び（line に足す node）

1. `theme-world`: `include: works-factory-world`。依頼の行 `[{where: "テーマ", text: <テーマの文>}]` で 1 度。返りの行を書き手と審査役に配る（keep-essence の 12・`step-up`）。
2. `theme-blind`: `include: works-factory-independent-design`。目的の port にテーマの文（14 章の 2 で、目的の役を挟むかを詰める）、人が決めた前提に方針の文書と依頼の `answers`。書き手の案は渡さない（独立の守り。keep-essence の 9）。返りは審査役だけが読む。
3. `theme-rounds`: `loop_group`。本体は `theme-turn` → `theme` → `theme-review` → `theme-out` → `theme-talk` → `gate-theme`。`until_bash` は `theme-talk` の `done` だけを読む（E16）。`max_iterations` は `rounds.LIMIT`（20）と `talk.EMPTY_LIMIT`（2）の和の 22（今の `plan-rounds` と同じ数え。試験が和を突き合わせる）。
4. `theme`（`include: works-factory-theme`）: 書き手の block（4 章）。前の周の設計の案・往復の記録・人の答えを受け、1 周分の設計の案を返す。
5. `theme-review`（`include: works-factory-plan-review`）: 形 `theme`（5 章）。設計の案を描いた md・往復の記録・世界の解の行・独立設計の返り・方針を受け、穴を返す。
6. `theme-out`・`theme-talk`・`gate-theme`: 今の `plan-out`・`design-talk`・`gate-design` と同じ役（往復の記録に足す・止め時を決める・周ごとの控えを書く・止まる周に開く）。関所の文は 7.1。
7. `theme-descend`（script）: 設計の往復が合意で終わった時だけ、承認された設計から依頼の行と答えを書く（8 章）。止める答え・設計の段の失敗は `stop_reason` を返し、後ろは飛び、報告は出る（`report-on-stop`）。
8. `request-in`（script。今の `relay` の形）: テーマの run は `theme-descend` の依頼、ほかの run は `start` の配る値を返す。今 `$start.output.ports.request`・`request_file`・`request_answers` を読む 18 か所（`workflows/line/works-factory-line.yaml`。7・7・4 か所）を、この返りを読む形に替える。`entry`・`request_origin`・`request_scope`・`prior_rows` は 13 章の 5。

### 2.3 往復の決まり（今の計画の往復の決まりを使い回す）

1. 止め時は `rounds.decide`（`lib/converge.py:233` の `decide` の写し。CLEAN・SETTLED・AGAIN・PERSISTED・UNSETTLED）。設計の案を往復の記録の項目 1 つとして入れてそのまま回るかは未確認（14 章の 3。回らなければ項目を持たない行を足す）。中央の穴が端の穴へ移ったら収まる（`transition-not-count`）。往復の回数で止めない。安全の上限 20（往復の回数。2.2 の 3 の 22 はこれに空の `revise` の聞き直しを足した loop の回りの数）は工場の不具合の止め。
2. 承認ノードを開くのは往復が止まる周だけ。途中の周は待たずに次の周を回し、周ごとの控え `talk/theme-<k>.md` を書いて在りかを告げる（`human-notes-in-rounds` の「ターンごとに設計を人に見せつつ」）。
3. `revise` と一言・空の `revise`・止める答え・上限の周の `revise` の扱いは今の 3.1 のまま。合意は設計の段を終えて降りる。
4. 受け箱: 設計の往復の間に入った行は人の block として設計の往復に差し込む。承認の行（「承認:」「もういいよ」）は、その時の段にだけ効く。降りる時に、出来事の並び（`timeline`）と承認を空にし直す（設計への承認で修正案の承認を飛ばさない）。読んだ行の数は計画の往復へ運ぶ（同じ行を 2 度読まない）。
5. 受け箱の承認で関所を飛ぶ時でも、最後の設計の案に持ち主に聞く問い（3 章の `asks`）が残っていれば関所を開く（推しを黙って採らない。今の「合意の時に見せていない行は修正前の承認ノードで開く」と同じ向き）。
6. 1 往復の費用の見込み: 書き手（計画の役と同じ程度、約 $2〜4）＋審査（形 text の実測 約 $4.00・約 10 分）。3 往復で約 $20 前後。頭の世界の解と独立設計は 1 度ずつ（実測 約 $0.19・$0.19）。降りた後は今の判定を全部回すので（12 章の問い 2 の答え A）、今の本線の判定と計画の往復の約 $16（12 章の問い 2 の案 A の出どころ）がこれに足される。

### 2.4 無人の run にテーマを渡した時（12 章の問い 3 の答え。部署の決め 13 章の 14）

テーマ専用の扱いを作らず、今の無人の run の決まり（持ち主の決め `unattended`。`docs/design/line.md` の 6 節）を設計の段にもそのまま当てる。

1. 頭の世界の解と独立設計・設計の往復は、人の居る run と同じに回す。往復は回数でなく指摘の遷移で終わる（2.3 の 1）。無人の run は受け箱を読まない（今の `talk.dialogue` が `unattended` の run を対話でないと読むのと同じ）。
2. 往復が止まる周の `gate-theme`: 人の居る run では、止まる周にいつも開く（設計の承認なので）。無人の run では開かない。代わりに、関所の項目を今の修正前の承認ノードと同じく line が組み、今の `passage`（`workflows/line/src/gates.py:103`。項目の全部が通す推しを持つ時だけ推しで進み、ほかは開かずに `works:needs-human` で止める）に掛ける。項目は次の 3 種で、4 つ目の箇条は項目が 1 つも無い時の扱い。
   - 最後の設計の案に残った持ち主への問い（3 章の `asks`）1 つにつき 1 行。この行は通す推しを持たないので、問いが 1 つでも残れば止まる。訳: `asks[].pick` は案の中の選び（A か B か）で、関所の項目の「通す・止める」の推し（`gatemarks.recommend_of` の `recommend`。尾は `gatemarks._push`）ではない。機械は推しを作らない（`docs/design/line.md` の 6 節。L-G24）ので、`pick` を通す推しに読み替えない。
   - 往復の止まり（PERSISTED・UNSETTLED）と上限の周（`capped`）の行。今の `rounds.stuck_pushable`（`workflows/line/src/rounds.py:486`）は設計だけの run（`design_talk` が真）では推しの尾（関所の項目の文の末尾に付く「／推し: 通す（continue）——…」の字。`gatemarks._push` が付け、`passage` はこの尾が通す推しの行だけを推しで進める）を付けない。テーマの run はいつも `design_talk` が真なので、止まった往復はいつも止まる。
   - 書き手か審査役が諦めた・落ちた周の行（今の修正前の承認ノードの `GIVEN_UP_KIND` の行と同じ）。推しを持たないので止まる。
   - どの項目も無い時（問いが残らず、往復が CLEAN か SETTLED で収まった時）は、関所を開かずに降りる（今の始めの承認ノードと修正前の承認ノードが、無人の run で項目が無ければ開かずに進むのと同じ）。`passage` は項目が空だと止める（`workflows/line/src/gates.py:108`）ので、今の修正前の承認ノードが `passage` の前に項目の空を分けている（`gates.py:375-379`）のと同じく、`gate-theme` の決めも `passage` の前に空を分ける。
3. 止まった時: 設計の案・残った問い・審査の結果を報告に出す（`report-on-stop`）。持ち主は、問いへの答えを依頼のファイルの `answers` に書くか、テーマの md に前の設計の在りかを書いて、人の居る run を起こし直す。
4. 降りた時の印: `gates/gate-theme.json` に、無人の run が問い無しで進んだことを人の答えと読み分けられる形で残す（今の `answer.PUSHED` の欄と同じ向き。欄の名は実装の前に詰める。14 章の 13）。`theme-descend` が書く依頼の `answers` の行（8.1 の 2）は、設計を「持ち主の承認」と書かず、`answer.PUSHED_NOTE`（「無人の run が採った推し。人の答えではない」）と同じ印を付ける（`answer.origin`・`answer.said`）。報告の冒頭にも、設計を持ち主が承認していないことを出す。
5. 降りた後: 計画の往復は今の無人の run のまま回る（対話でないので `gate-design` は開かない）。修正前の承認ノードは、`design_talk` が真の run を「設計だけの run」として必ず開き、無人の run は開けないので `works:needs-human` で止まる（`docs/design/line.md` の 6 節の「設計だけの run は無人でも止まる」・L-G27・持ち主の決め `design-only`）。だから無人のテーマの run は、どの道でも作り始めない。成果は設計と計画と審査の結果の報告。

## 3 設計の案の形（`workflows/.shared/schemas/theme-design.schema.json`。書き手の block と line の `theme-descend` の 2 つが読むので `.shared/` に置く。`docs/design/README.md` の 4.1）

欄の要は、「何を問うか → 何を前提にしたか → 今何が在るか → 何を足すか（在る物では足りない訳）→ 問い（案・推し・代償）と部署の決め → 変える所 → 作り変えの照らし → 前の穴と人の答えへの答え」。人に見せる欄は `{lang}`。

- `question`（字）: テーマの問いを 1〜3 文で言い直した物。`purpose`（字）: 何のための設計か。
- `premises[]`: 設計が置いた前提 `{id: P1…, what, by: owner|assumed, from}`。`owner` は人が決めた前提で、`from` に人の答えの番号（7.2）かテーマの md の行を書く。`assumed` は書き手が仮に置いた前提で、`from` に置いた訳を書く。仮の前提は審査役が攻める的になり、答えで動きが変わる物は `asks` に上げる（第 2 版で独立設計の D3 から採った。17.2）。
- `current[]`: 今在る物 `{id: N1…, what, where}`。`where` は `<パス>:<行>`。
- `parts[]`: 設計の中身 `{id: D1…, what, where, why}`。足す・変える部品ごとの 1 行。
- `reuse[]`: 足す物ごとに `{part: D<n>, existing: [N<n>…], enough: false, why_not}`。在る物を先に挙げ、足りない訳を書かせる（`reuse-first`・承認済みの条件「新しく作る物は、在る物では足りない訳を書く」）。対象の決まりが求める確かめ（このリポジトリなら E11 の 3 つ）は、方針の文書から読んで `checks[]` `{rule: <パス>:<行>, answer, where}` に答える（工場の指示の md は特定のリポジトリの決まりの名を書かない。E13・E14）。
- `asks[]`: 持ち主に聞く問い `{id: Q1…, ask, pick, pick_why, options: [{id: A…, what, cost, gain}]}`。初見の読み手に通じる詳しさで、推しを先に、捨てた案と代償を書く（`ask-shape`）。答えで次の動きが変わる物だけ（`obvious`）。
- `decided[]`: 部署の決め `{id: R1…, what, by: <パス>:<行>, why}`。決まりで決まるので聞かない物。
- `changes[]`: 変える所 `{id: C1…, where, what, op: add|edit|rework|remove, parts: [D<n>…]}`。降りる時に依頼の行になる（8 章）。`rework` は今在るファイルを作り変える行（6 章の照らしが要る）。
- `inventory[]`: 作り変えの照らしの行（6 章）。
- `narrows[]`: 設計が今の能力を狭める所 `{what, decided_by | undecided_because}`（計画の `narrows` と同じ欄。`no-narrow`）。
- `block_answers[]`: 前の往復の穴と人の block への答え（計画の `block_answers` と同じ形。`converge.answer_gaps` が読む）。
- `answers_used[]`: 人の答え（7 章）ごとに `{answer: <番号>, applied: [<欄の id>…] | declined_why}`。持ち主の言葉を黙って落とさない。

設計判断の記録の定番書式 MADR（Markdown Architectural Decision Records。https://adr.github.io/madr/ ）との対応（第 2 版。世の中の基準との照らしの所見への答え。17.3）:

| この形の欄 | MADR の節 |
| --- | --- |
| `asks[].ask` | Context and Problem Statement |
| `asks[].options[].what` | Considered Options |
| `options[].gain`・`cost` | Pros and Cons（Good・Bad） |
| `asks[].pick`・`pick_why` | Decision Outcome（status: proposed） |
| 持ち主の答え（7.2） | status: accepted |
| `decided[]` | Decision Outcome（status: accepted） |
| `decided[].by` | Decision Drivers |
| `narrows[]` | Consequences（Bad） |

欄の名を MADR に寄せずに自作のままにする訳:

- 単位が違う。MADR は決めた後の 1 つの決めを 1 本の文書に記録する。`asks` は 1 往復の中で、まだ決まっていない複数の問いに推しを付けて持ち主に出す物で、設計の案 1 つが問いを何本も持ち、`decided`・`changes`・`inventory` と組で読まれる。
- 機械の受け付け（4.4 の 3）が `pick`・`cost`・`gain` を名で照らし、計画の形と同じ短い欄の名にそろえてある（`narrows`・`block_answers`）。名を替えると、形・受け付け・指示の md が替わるのに、得る物は読み手の語の慣れだけ。
- 読み手の慣れは対応の表で取れる。人に見せる md（4.2 の `design_md`）では、問いを MADR と同じ並び（問い → 案 → 案ごとの得と代償 → 推しと訳）で描く。承認された設計は対象のリポジトリに自動では残さない（12 章の問い 1 の答え A）ので、MADR の形で書き出す道は足さない（14 章の 11）。

計画の形と分ける訳: 計画は判定の単位（欠陥）ごとの書き換えで、選び肢・推し・代償・部署の決めの欄を持たない（1.2 の `design-gap-refactor-route`）。逆に設計の案は試験とファイルの行（計画の形の `tests[]`・`files[]` の行。ファイルごとの書き換えのやり方・`symbols`・試験の中身）を持たない。設計の案の `changes[]` は `where` にパスを持つが、変える所と何を変えるかの 1 行だけで、書き換えの細目は持たない（試験とファイルの行は降りた後の計画の役が書く。仕様駆動の道の「ファイルの行は仕様に書かず、計画の AI が起こす」と同じ分け。`spec-driven-shape`）。

## 4 書き手の block `theme`（`workflows/theme/`。graph の名 `works-factory-theme`）

直し方の型の下書きの段 2（語の「段 1・段 2」）で型を葉の block に切り出した形（`docs/plans/2026-10-24-fix-weapons.md` の 11 章）に倣い、書き手を 1 つの block にする。この block はほかの workflow を名指さず、入口の node `intake` は script なので、憲法の 3 の外しの葉の block（`leaf-include`）に当たる。そのため AI の node を持っていても、line 以外の graph からも include できる。

### 4.1 node の並び

`intake`（script）→ `write-loop`（`loop_group`: `write-prep` → `theme-writer`（AI）・`theme-writer-fix`（AI。却下の後の同じ会話の続き）→ `write-accept`）→ `finish`（script。設計の案を md に描く・`report` を組む）。形は今の plan の block（`docs/design/plan.md` の 1.3）と同じ。却下 3 回で諦める（`lib/rolekit.py`。keep-essence の 4）。

### 4.2 port

入力: `theme`（file。必須）・`prior`（json(shared:plan-converge.schema.json)。往復の記録。1 周目は空）・`prior_design`（json(shared:theme-design)。前の周の設計の案）・`answers`（json。人の答えの行。7.2）・`world_rows`・`policy`（file）・`recorded`・`base`・`lang`。独立設計の返りは受けない（審査役だけが読む）。

出力: `ok`・`status`（`ok`・`gave_up`・`failed`）・`design`（pointer。json(shared:theme-design)）・`design_md`（pointer。人と審査役に見せる md）・`reason`・`report`。

### 4.3 指示（英語の md。`prompts/theme-writer.md`・`theme-writer-fix.md`）

決まった文の観点: 問いを言い直す・今在る物を先に挙げる・在る物に足す形を先に考える・新しく作る物は在る物で足りない訳を書く・決まりで決まる物は聞かずに出どころつきで書く・聞く物は答えで動きが変わる物だけで、推しを先に、捨てた案と代償・作り変えでは今の中身を 1 つずつ挙げて行き先を付け何も落とさない・世の中の定石と比べる（世界の解の行）・前の穴と人の答えに 1 つずつ答える。共通の断片は今の物を使う（`{shared:rejected}`・`{shared:policy}`・`{shared:recorded-policy}`・`{shared:query-rule}`・`{shared:lang-default}`）。特定の言語・試験の実行器・このリポジトリの決まりの名は書かない（E13）。

### 4.4 受け付け（yes/no の照らし。憲法の 6）

1. 形（schema）。
2. `<パス>:<行>` の名指しが作業ツリーに在る（`current`・`parts`・`decided`・`checks`）。

## 5 審査役（事前審査の block に形 `theme` を足す）

## 6 作り変えの照らし

### 6.1 形

`inventory[]` の行 `{path, lines: "<始め>-<終わり>", gist, to: keep|move|merge|drop, dest, why}`。手本は `docs/plans/2026-10-24-fix-weapons.md` の 1.4 と付録 A（direct の指示文を段落か箇条 1 つずつ行番号つきで挙げ、行き先と入った訳を付けた。持ち主の言葉「ここはうまくやってほしいね。」9.1 の 6）。

- `to`: `keep`（そのまま残す）・`move`（`dest` の所へ移す）・`merge`（`dest` の行とまとめる）・`drop`（消す。`why` が要り、`narrows` に同じ行を持つ）。
- 訳の分からない行は `drop` にせず `keep` か `move` にする（手本の決め「訳の分からない指示は消す側に回さない」）。

### 6.2 機械の照らし（4.4 の 6）

1. `changes` の `op: rework` の各パスについて、起点の木のそのファイルの空でない行の全部が、`inventory` のその `path` の行の `lines` の和に入る（覆いの抜けが無い）。
2. 範囲がファイルの行の数の中で、同じファイルの範囲が重ならない。
3. `drop` の行は `why` が空でなく、`narrows` に同じ `path` と `lines` を名指す行が在る。
4. `move`・`merge` の行の `dest` が `parts` か `changes` の id を指す。

行の分け方（段落か箇条か）は書き手が決め、機械は覆いだけを照らす（段落を機械が割る道具を足さない。13 章の 8）。行き先の正しさは審査役が見る（5.2 の 4）。

### 6.3 降りた後

承認された `inventory` は設計と一緒に人が決めた前提として計画と事前審査に届く（8.2）。計画が `drop` でない行の中身を消す修正案を書けば、事前審査が承認済みの設計からの外れとして中央の穴にする（`drift-in-loop`）。修正の後に機械で照らす形は 14 章の 4。

## 7 答えの口

### 7.1 関所の文（`gate-theme`）

見せる物: 設計の案の md（問い・前提〔人が決めた物と仮の物を分ける〕・今在る物・設計・変える所・作り変えの照らし）・持ち主に聞く問い（推しが先・捨てた案と代償）・部署の決め（出どころつき）・審査の結果（往復ごとの行と最後の往復の穴）・独立設計との差・答え方。答え方の文は今の `talk.outcomes` の決まり（その周に答えた時に実際に起きる事を 1 つの関数から組む）に、7.2 の書き方を足す。

答えの語は今の `gate-design` と同じ 5 つ（`approve`・`continue`・`stop`・`reject`・`revise`。意味の正本は `docs/design/line.md` の 3.1 の「答え」）。`approve`・`continue` はどちらも合意で動きは同じ（`approve` は関所の選び肢の語、`continue` は殻から答える命令の語。`lib/answer.py` の `GO_WORDS`）、`stop`・`reject` もどちらも同じ止める答え（`STOP_WORDS`）、`revise` は一言を添えて設計し直しを求める答え。`approve`・`continue` は「見せた設計と、答えの無い問いは推しを採って合意する」と関所の文に書く。

### 7.2 答えの書き方（`text` の節）

承認ノードの答えは Archon の正式な形 `{decision, text}` のまま（`form: select` の答えは `--choose` と `--text` だけ。止めた Archon の `reference/cli.md` の `workflow answer`）。`text` に、決まった見出しの節を書く:

```text
## 持ち主の言葉
「…」（日付。何への答えか）
## 調べもの
- <何を調べたか>: <分かった事>（出典: <URL か パス>）
## 問いへの答え
- Q1: B（足し: …）
## 取り次ぐ会話の読み
- …
```

- どの節も無くてよい。見出しの無い字は今と同じ一言として読む（今の答え方を壊さない）。
- 周の頭の `theme-turn` が節を分け（`talk` の口を 1 つ足す）、行ごとに番号を付けて書き手の port `answers` に渡す。持ち主の言葉と取り次ぐ会話の読みは別の行の種類にし、持ち主の言葉は字のまま運ぶ（持ち主の決めの書き方 `docs/owner-decisions.md` の頭、手本の 9.1 と同じ向き）。
- 見出しが在るのに節が読めない（`Q<n>` が見せた問いに無い・案の id が無い）時は、設計し直さずに訳を添えて同じ文で聞き直す（空の `revise` と同じ数え `talk.EMPTY_LIMIT`）。
- 受け箱の行にも同じ書き方の 1 行版を許す（`答え: Q1=B …`）。複数行の調べものは関所の `text` で渡す。
- 答えは今と同じく `gates/gate-theme.json` に残り、報告に出る。降りる時に依頼の `answers` の行（question `設計の段で持ち主が答えた Q<n>` など）にして計画へ運ぶ（8.2）。

ファイルの口（run の置き場に答えのファイルを置く形）にしない訳は 13 章の 3。

### 問い 4 の確かめ（第 3 版。止めた Archon `a972888a` の源と、読み込みだけの小さな試し）

読み込みの試し（止めた Archon の `loader.ts` の `parseWorkflow` に、bun で小さな YAML を 3 本読ませた。run は起こしていない）:

分かった事:

- 第 2 版の案 B（設計の往復と計画の往復を外の `loop_group` 1 つで包む）は読み込みで拒まれ、組めない。2 つの往復はどちらも本体の終わりに承認ノード（`wait:`）を持つから。

### 問い 5: 同じ run で設計へ戻る形が組めない時、どうするか（第 3 版で足した）

- 案 A（推し）: 戻る答えで run を閉じ、続きの run を同じ材料で起こす。テーマの run の `gate-design` で `redesign` と一言を答えると、計画の往復を終えて修正へ進まずに止まり、報告を出す。run の置き場に、続きの run のテーマの md（承認された設計の在りか・計画の段の最後の往復の穴・一言・受け箱の行・問いへの答え）と、そのまま打てる起動の行を書く。取り次ぐ会話がそれで次の run を起こす。第 2 版の案 A に、戻る答えの語と続きの材料の書き出しを足した物。代償: run が 2 本に分かれ、持ち主から見ると「同じ run のまま」が途切れる。続きの run は設計の段の頭（世界の解と独立設計。実測で合わせて約 $0.4）と判定を回し直す。得る物: Archon の決まりの中で組め、本線の前半の並びを変えない。戻った後の設計にも判定を全部回すので、問い 2 の答え A がそのまま効く。Archon が入れ子の待ちを許す版になれば、同じ材料のまま同じ run で戻る形へ移れる（14 章の 14）。
- 案 B: 本線の前半を 1 つの loop に組み直す。設計の周・降りる・判定・計画の周を同じ `loop_group` の本体に入れ、承認ノードを本体の唯一の終わり 1 つにして、段ごとに見せる文を替える（試し 2 の形）。代償: 判定の中の仕様の段の承認ノードが本体に入れないので、仕様の段を判定から出す（ほかの block の作り変え）か、テーマの run と仕様の段を組めなくする（13 章の 7 を変える）。node の id は graph の中で 1 つなので、テーマでない run も同じ loop を通り、本線の前半の作りが全部替わる（問い 2 の案 A の得る物「本線の作りを 1 字も変えない」を失う）。判定の全部の block を loop の本体で回すので、resume の決まりを確かめ直す（問い 4 の確かめの残る未確認）。得る物: 本当に同じ run のまま戻れ、戻るたびに判定も全部回る。
- 案 C: 計画の往復の loop の中で設計の周を回す。`redesign` の次の周は、計画の役の代わりに設計の書き手と形 `theme` の審査を回し、`gate-design` で設計の承認を取ったら、同じ loop の中で計画の周に戻る（承認ノードは `gate-design` 1 つのまま。本体に葉の block の include を足すだけで、読み込みの決まりの上では組める）。代償: 判定は loop の外に在るので回し直せない。戻って直した設計の変える所は、前の設計で割った直す単位のまま計画に渡る（問い 2 の答え「降りた後は判定を全部回す」が、戻った後には効かない）。設計の書き手と審査の include が、設計の段の loop と計画の loop の 2 か所に要る。得る物: run が 1 本のまま、本線の前半の並びは変えない。

### 17.3 世の中の基準との照らしの所見への答え

所見（`docs/plans/2026-10-27-design-stage.md:200`・重さ suggest）: `asks[]` の欄（`ask`・`pick`・`pick_why`・`options[].what`・`cost`・`gain`）は、設計判断の記録の定番書式 MADR の Considered Options・Decision Outcome・Pros and Cons of the Options とほぼ同じ中身の自作の形に見える。下書きは MADR に触れず、自作する訳も無い。役の順位は「MADR の節と語を採る ＞ MADR に対応づけた自作 ＞ 対応づけの無い自作（下書き）」。

答え: **対応づけた自作にする**（順位の 2 つ目）。3 章に対応の表と、欄の名を替えない訳（単位の違い・受け付けが名で照らす事・読み手の慣れは表で取れる事）を足した。人に見せる md は MADR と同じ並びで問いを描く。MADR の形で文書を書き出す道は足さない（12 章の問い 1 の答え A。14 章の 11 は閉じた）。部署の決めの 11 に書いた。持ち主に聞かない訳: 決まり（`reuse-first` と承認済みの条件「新しく作る物は、在る物では足りない訳を書く」・憲法の 6）で決まり、どちらを選んでも持ち主から見える動きは変わらない（`obvious`）。
