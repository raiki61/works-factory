## 2 段と型の口（どの型も同じ形）

型どうしは口の形だけをそろえ、中身を知らない。口の形はファイルの形（`workflows/fix/schemas/` の JSON Schema）で決め、Python の型や関数の呼び出しで決めない。こうしておくと、段 2 で型を block に上げる時（4.2）に、口がそのまま block の port になる。

### 2.0 2 つの段（持ち主の答え 2026-10-25 の 1）

型を 2 段に並べる。上の段は振る舞いを変えるかで分け、下の段が型。

- 変える段 `change`: 型は `tdd`・`remove`・`direct`。
- 変えない段 `keep`: 型は `tidy`（小さな書き直し。使われていないコードの削除を含む）・`rebuild`（大きな作り直し）。

決まり:

- どの型も 1 つの段にだけ属する。型の名から段を引く表は 1 か所（2.4 の表）に置き、注文に段の欄を別に持たない（型の名と段が食い違う注文を書けなくする。憲法の 6）。
- 型を足す時は、段を決めて型の義務を足すだけにする。ほかの型の段の決まりに例外を書き足さない（run 19268881 の 20 件の穴の形を作らない。7 章）。
- 段は注文で決まる。型が途中で諦めて別の型の注文に書き直される時も、段は変えない（変える段の型の逃げ先は変える段の型だけ。3.2）。

### 2.1 注文（受け取る物）

組の子の頭が、型ごとに 1 つ書く。型は注文のファイルだけを読み、計画の欄（`planmarks`）・判定・ほかの型の状態を読まない。

- `weapon`: 型の名（`tdd`・`remove`・`direct`・`tidy`・`rebuild`）。段はこの名から 2.4 の表で引く。
- `units`: 直す単位の並び。単位ごとに key・項目の id・何を直すか（判定と brief の該当の行）。
- `scope`: 書いてよいパスの glob（`allowed_paths`）と触らない物（`out_of_scope` の `{glob, why}`）。
- `permits`: 試験を変えてよい許しの行。`conflict.test_permits` の行を、この注文の項目と単位で絞った物だけ。行ごとに `kind`（`rewrite`・`remove`・`agreed`・`ruled`・`broken`・`replan`）と `duty`（2.4 の義務で、返しがその行を果たしたかを照らすか）を持つ。`rewrite` は義務の行（その試験を書き換えて新しい振る舞いを縛ったかを、2.4 の変える段の義務で照らす）、`remove` は義務でない許し。この 2 つを 1 つの語に混ぜない。
- `base`: 起点。run の修正前の版（`board.base_rev_of`。`board.py:1801`）と、組の頭で 1 度取った関わる試験の元の結末。どの型も同じ起点で比べる。下ごしらえ（3.6）を挟んだ時は、下ごしらえが足した試験を起点の木で走らせた結末もここに入る。
- `run`: 試験の走らせ方（test_cmd・実行器）と、当たる試験の選び方の結果。
- `asks_answered`: 前の周の申し出への答え（範囲の相談の答え・裁定）。

型ごとの欄は `orders.<weapon>` に入れる（例: TDD の受け入れの試験の名指しと整えの申告・remove の消す名の並び・rebuild の比べる境目）。共通の受け付けはこの欄を読まない。

### 2.2 返し（返す物）

- `status`: `done`（全部の単位を直した）・`parked`（申し出を積んで止めた）・`gave_up`（3 回の却下で諦めた。訳を添える）。
- `tree`: 返した時の作業ツリーの木の hash。差分は `base` からこの木までで、型は自分で差分を書かない。
- `changes`: 単位ごとの変更の行 `{unit, files, what}`。型が自分で書く。ほかの役に写させない（1.2 の 1・2 をやめる）。
- `evidence`: 確かめの証拠。どの型も同じ欄で、使わない欄は空。
  - `named`: 型が名指した試験（TDD の受け入れの試験・direct が後から足した試験など）。
  - `before`・`after`: 名指しと関わる試験の、起点と返した木での結末（JUnit の結末から機械が作る）。
  - `added`・`rewritten`・`removed`: 足した・書き換えた・関数ごと消した試験の id。型の申告で、共通の受け付けが木の比べで照らし直す。
  - `compared`: 新旧を同じ入力で比べた記録（rebuild が使う。3.5）。入力の id ごとに、古い経路と新しい経路の出力の hash と、比べから除いた揺れの印。形は言語を問わない JSON の行（E13）。
- `asks`: 食い違いの申し出の行（今の `lib/conflict.py` の形のまま）。
- `report`: 報告に載せる日本語の行。

### 2.3 共通の受け付け（型の中身を知らない機械）

返しが来たら、型の名を問わず同じ順で照らす。今の `accept_reply`・`gates.py`・`assert_changed.py` の照らしのうち、型を問わない物をここに集める。

1. 範囲: `base` から `tree` までに変わったパスが `scope` の中か（今の `scope.py`）。
2. 書き込みの出どころ: 書いたのが役の Edit・Write か（今の `lib/writes.py`。keep-essence の 5）。
3. 試験の変更: 起点の木と返した木の試験の関数を比べ、変わった・消えた関数がどれも `permits` の行の中か（今の `gates.py` の `test_edits`。許しは注文の `permits` だけを読む）。消えた関数の集まりは機械が出し、`evidence.removed` の申告と合うかも照らす。
4. 申告したファイルが本当に変わったか（今の `assert_changed.py`）。
5. 義務: 2.4 の表で、型の名から段と型の義務を引いて `evidence` に当てる。

この機械は `orders.<weapon>` も型の状態のファイルも読まない。型の名で枝分かれするのは 5 の表引きの 1 か所だけ。

### 2.4 確かめの表（段の共通の義務 + 型の義務の 2 層）

どれも yes/no で、機械が JUnit の結末と木の比べと `evidence.compared` の行だけで決める（憲法の 6）。

表の形の決まり:

- 型の義務は、段の義務で出た問題の並びに問題を足すことしかできない。受け付けは「段の義務の問題 + 型の義務の問題」が空の時だけ通す。型の義務の関数は段の義務の結果を受け取らない（例外を書く口が API に無い。憲法の 6）。
- 型の名から段を引く表と、段と型の義務の関数の表は、同じ 1 つのモジュールに置く（今の `board.py` と `tdd.py` に散る照らしを集める）。

全部の段に共通（どちらの段にも入る、今の受け付けの照らし）:

- 返した木で居なくなった試験は、どれも `permits` の中にあり `evidence.removed` に名がある（今の `lib/baseline_red.py:121-143` は居なくなった試験を見ないので、ここで足す）。

段の義務:

- 変える段 `change`: 変えた動きを試験か機械で示す。機械の照らしは「`evidence.named` に 1 つ以上の試験があり、どれも起点の木で failure（赤）・返した木で通る（緑）」。義務の `rewrite` の許しの試験も、書き換わって赤から緑になる。そのうえで、起点で通っていた関わる試験は、`permits` の中の物を除いて返した木でも通る。
- 変えない段 `keep`: 前に通っていた試験が直した後も同じ結果。機械の照らしは「関わる試験の結末の並びが、起点と返した木で同じ（通っていた物が全部通り、居なくなった物が `permits` の `remove` の中の物だけ）」。既存の試験は変えない（許しが名指した物だけ例外）。足してよい試験は、起点の木で通る試験だけ（Feathers の characterization test。赤を求めない）。

型の義務:

- `tdd`: 名指しの試験が、単位の頭（直す前の木）で赤になったことを輪の中で確かめた記録がある（先に赤。段の義務の「起点で赤」より強く、書く順を縛る）。`remove` の許しは使わない（消す依頼は remove に回す。3.3）。
- `remove`: 注文の消す名の定義が返した木で引けない（`planmarks.line_in` と `file_symbols` の機械の照らし）。消した試験は `remove` か `rewrite` の許しの中。変える段の「名指しの試験が赤から緑」は、消す名を使う呼び手の振る舞いが変わる試験（`rewrite`）で満たす。消えたことだけを縛る試験は名指しに数えない（3.3）。
- `direct`: 型の義務は足さない。段の義務の「名指しの試験が起点で赤・返した木で緑」を、直した後に足した試験で満たしてよい（後から足す試験。起点の木での赤は機械が走らせて確かめる）。
- `tidy`: 型の義務は足さない（段の義務だけ）。
- `rebuild`: `orders.rebuild` の境目について、`evidence.compared` の行が 1 つ以上あり、揺れの印の無いどの行でも古い経路と新しい経路の出力の hash が同じ。

TDD の refactor の段は、変えない段の義務と同じ照らしを使う（段の確かめを TDD の中に別に持たない）。`refactor-same` の「修正役が緑の後に同じ会話で整え（整える段に別の役を立てない）、緑のままかを機械が 1 回確かめる」はそのまま保つ。

direct の「起点の木で赤」を確かめる走らせは、持ち主の決め `base-runs-nothing`（run の始めには試験を何も走らせない）に当たらない。走らせるのは直した後に、名指しの試験だけを起点の木で 1 回で、`base-runs-nothing` が残す「元の結末に無い赤だけを、直す前の版で同じ走らせ方を 1 回して分ける」と同じ形。

## 3 場面の軸と型ごとの中身

### 3.0 場面の軸（持ち主の答え 2026-10-24 の 4）

直す場面を 5 つの軸で見る。軸の出どころは材料のノート（場面と直し方）の「軸と原典の表」。軸を一覧にした原典は無く、5 つに並べたのは材料のノートの読み。

1. 振る舞いを変えるか（変えない・変える）: 段の分け（2.0）そのもの。
2. 試験が在るか（直す所を縛る試験が在る・無い）: 無ければ下ごしらえ（3.6）を挟める。
3. 変更の大きさ（小さく積める・まとめて書き換える）: 変える段の tdd と、変えない段の tidy と rebuild を分ける。
4. 新旧を共存させて段階的に移せるか（両方の経路を呼べる・呼べない）: rebuild の前提（3.5）。
5. 利用者に見える境目（公開 API・データ）を越えるか（越えない・越える）: 機能を消す依頼の置き場（remove か tidy か。3.3）と、rebuild で古い経路を消すか（9.2 の 2）を分ける。

この設計は、型ごとに「どの軸の値を前提にするか」と「前提が崩れた時に型が何を返すか」だけを描く。軸の値から型を選ぶ決め方は描かない（範囲）。

### 3.1 tdd（変える段）

- 前提: 軸 1 が変える・軸 3 が小さく積める。直す所の試験の走らせ方が在る（試験そのものが無ければ輪が書く）。
- 受け取る: 共通の注文と、`orders.tdd` の受け入れの試験の名指し・整えの申告。
- やる: 今の輪の test・fix・refactor の段。
- 返す: 単位ごとの `changes` と `evidence`。今は修正役が `changes` に写していた行を、輪が自分で書く。
- 輪から出ていく物（持ち主の問い「TDD の loop がややこしかった。切り出すことですっきりするか」への答え）: 輪は赤 → 緑 → 整えの手順だけを持ち、次の 5 つを外へ出す。
  1. 振り分けの段（route）: 組の子の頭の前へ（10 章の 1）。
  2. direct への 4 つの道（1.2 の 5。`_to_direct`）: 輪は「tdd の義務を満たせない」を `status: gave_up` と訳で返すだけにし、direct の注文を書くのは組の子の頭（4.1 の 3）。
  3. 許しの読み（1.2 の 4）: `planmarks.unit_contract` を読まず、注文の `permits` だけを読む。段ごとの許しの違いは、共通の受け付けの 1 つの照らし（2.3 の 3）に寄る。
  4. 修正役への指示文（1.2 の 2。`FIXED_HEAD`・`DIRECT_HEAD`）: 輪が自分で `changes` を書くので要らない。
  5. 修正役の受け付けへの部品の貸し（1.2 の 6）: 共通のモジュールへ。
  - 残る物: 単位ごとの赤の照らし（`red_check`）・凍結・3 回の却下の数え・整えの段。整えの確かめは変えない段の義務の関数を呼ぶ。
- 消す名の許し: 読まない。消す依頼を tdd の輪で通すために段ごとの例外を足す形（run 19268881 の第 3 版の項目 1）は採らない。採ると 7 章の 1 群の穴がそのまま残る。

### 3.2 direct（変える段）

- 段の置き場の決め（持ち主の答え 2026-10-25 の 1 で設計の部署が詰める物）: 変える段に置く。変えない段には置かず、両方の段にも置かない。
  - 訳 1: 今 direct が「振る舞いを変えない直し」に使われるのは、変えない段の型が無いための逃げ道だった（run 19268881 の第 3 版の項目 3 の形。1.3 の run 20447be2）。tidy を立てれば、その直しは tidy の注文になり、direct が受ける訳が無くなる。
  - 訳 2: 変えない段に置くと、direct が今受けている振る舞いを変える直し（TDD の輪が先に赤を作れなかった単位・40 周に届いた単位）が「通っていた試験が通る」だけで照らされる。これは今の direct の弱さ（2.4 の第 1 版の「共通の義務だけ」）のままで、持ち主が変える段に求めた「変えた動きを示す」を満たさない。
  - 訳 3: 両方の段に置くと、型の名から段が 1 つに決まらず、2.0 の「型は 1 つの段にだけ属する」が崩れる。段を注文の欄で別に渡すことになり、段と型の食い違いを書ける形になる。
- 前提: 軸 1 が変える。tdd の「先に赤」を踏めない時（先に赤を書けない・輪が上限に届いた・範囲の裁定の後）に、変えた動きを後から足した試験で示す。
- 受け取る: 共通の注文だけ。
- やる: 今の修正役の直し。直した後に、変えた動きを縛る試験を名指す（足すか、`rewrite` の許しの試験を書き換える）。TDD で直した単位を見ない。
- 返す: 単位ごとの `changes` と `evidence`（`named` は直した後に足した・書き換えた試験）。
- 今と変わる所: TDD の後にいつも起きる形をやめ、direct の注文が在る時だけ起きる。修正役の指示から TDD の要約（`FIXED_HEAD`・`DIRECT_HEAD`）を外す。今は「共通の義務だけ」で通る direct が、変える段の義務（名指しの試験が起点で赤・返した木で緑）を負う。
- 逃げ道の向き: tdd → direct は同じ段の中の書き直しで、組の子の頭がする。変えない段の型（tidy・rebuild）が諦めた時に direct へ回すことはしない（段を越えない。2.0）。
- 試験を走らせる道が無い時（今の「実行器が走らない」で全部を direct にする道）: 変える段の義務を誰も満たせない。どうするかは 9.2 の 1。

### 3.3 remove（変える段）

- 前提: 軸 1 が変える・軸 5 が越える（利用者が使える機能を消す）。利用者から届かない、使われていないコードを消すのは tidy（3.4）。材料のノート（変更の種類）の読みで、機能の削除をどちらの箱に入れるかは「誰から見て届くか」で割れる（SemVer と Conventional Commits の破壊的変更・Tidy First? の整理）。
- 受け取る: 共通の注文と、`orders.remove` の消す物の並び（`change=remove` の名・`op=delete` のパス・`op=rename` の元）。`permits` には消す名を使う試験の `remove` の行が入る。
- やる: 消す物と、それを縛る試験を消す。消す物を使う残りのコードを直す。新しい振る舞いへの書き換えはしない。「X を消して振る舞いの違う Y に替える」依頼は、消す項目と足す項目（tdd）の 2 つにし、足す項目が `depends_on` で消す項目を待つ（計画の欄 `depends_on` は今在る）。
- 確かめ: 2.4 の変える段と `remove`。消えたことを縛る試験を書かせない（superpowers の `writing-good-tests.md:192` が悪い兆しとする「消した名が無いことを確かめる試験」）。消えたことは機械が木で照らす。
- 最後の承認: `evidence.removed` を受け付けが照らした集まりから、「消した試験」の節を id で並べる。「書き換えを許したテストを触った」の節には入れない。
- 今の形との違い: 今は消す依頼を tdd か direct のどちらかが別の型の都合で抱える。remove を立てると、消す依頼の確かめが 1 か所にまとまる。
- 段の義務との合わせ目（10 章の 3）: 消す名を使う呼び手が無く、`rewrite` の試験が 1 つも無い消し（機能だけを消して誰も呼んでいない）では、変える段の「名指しの試験が赤から緑」を満たす試験が無い。

### 3.4 tidy（変えない段。小さな書き直し）

- 前提: 軸 1 が変えない・軸 3 が小さく積める。使われていないコードの削除を含む（Beck の Tidy First? の整理に入る）。
- 受け取る: 共通の注文と、`orders.tidy` の保つ振る舞いの説明（何を変えずに何の形を変えるか）。
- やる: 書き直す。保つ振る舞いを縛る試験が足りなければ、先に下ごしらえ（3.6）を挟む（tidy の中に試験を足す段を持たない）。
- 確かめ: 2.4 の変えない段の義務だけ。
- 今の形とのつながり: TDD の refactor の段と照らしを分け合う（2.4）。`refactor-same` は「TDD の中の整え」の決めで、整えだけの単位の型はこの決めに当たらない。
- 使われていないコードを縛っていた試験: その試験を消すのは `remove` の許しで、2.4 の変えない段の義務は `permits` の `remove` の中の試験が居なくなるのを認める。許しを出すのは計画の `change=remove` の元（今の `_naming_removes`）で、tidy の中に別の許しの道を作らない。
- 届かない訳: 今の判定は欠陥の形の無い単位を作らない（`judge.py:268-272`・`exit.py:90`）。案の項目も単位を 1 つ以上要る（`planmarks.py:153-155`）。だから tidy を作っても、判定の単位の決めを見直すまでは、どの run も tidy に届かない。持ち主の答え（2026-10-25 の 2）に沿い、口の形だけを今決め、作るのは判定の単位の決めを見直す時と一緒にする。

### 3.5 rebuild（変えない段。大きな作り直し）

- 前提: 軸 1 が変えない・軸 3 がまとめて書き換える・軸 4 が両方の経路を呼べる。中は細かく試験せず、外側の境目で新旧を同じ入力で比べる。
- 受け取る: 共通の注文と、`orders.rebuild` の比べる境目（新旧を呼び分ける入口の名と、入力の集め方）。
- やる:
  1. 境目の内側に新しい経路を作り、古い経路を残したまま、境目から両方を呼べるようにする（Branch by Abstraction の抽象化の層）。
  2. 同じ入力を両方に投げ、出力を比べた記録を `evidence.compared` に書く（Scientist の比べ。揺れる出力は除いた印を付ける）。
  3. 比べが通ったら古い経路を消す（9.2 の 2）。
- 確かめ: 2.4 の変えない段と `rebuild`。境目の外の試験は段の義務で同じ結果、境目の中は比べの記録で照らす。
- 前提が崩れた時: 両方の経路を呼べない（副作用のある処理・外の状態・データの移し替え）なら、比べの記録を書けず `rebuild` の義務を満たせない。`status: gave_up` と訳を返し、組の子の頭は変える段の型へ回さない（段を越えない。2.0）。申し出として裁定に回る（keep-essence の 4）。
- 届かない訳: tidy と同じ（3.4）。口の形だけを今決める。

### 3.6 下ごしらえ（型ではない。どの型の前にも挟める段）

- やる: 直す所の今の振る舞いを試験で固める（characterization test・golden master・approval testing）。望む振る舞いでなく、今の振る舞いを記録する。
- 確かめ（yes/no）: 足した試験が、起点の木で 2 回走らせて 2 回とも通る（揺れる出力を除けていない試験を落とす。golden master の記事の「揺れる出力は Printer が除く」に当たる）。足した試験は `base` の関わる試験に入り、後の型の段の義務がそのまま照らす。
- 型にしない訳: 下ごしらえは振る舞いを変えないので段の義務は変えない段と同じだが、直す物を持たない。型にすると、変える段の型の前に挟む時に段が 2 つ混ざる。注文の外の段として組の子の頭が挟み、型はその結果を `base` で受け取るだけにする。
- いつ挟むか: 軸 2（試験が在るか）で決まるが、決め方は描かない（範囲）。

## 4 切り方（互いの中身を知らない形）

### 4.1 段 1: 修正の block の中で口をそろえる（段 2 への一歩）

1. 注文と返しの形を `workflows/fix/schemas/weapon-order.schema.json`・`weapon-return.schema.json` に置く。段 2 でこれがそのまま型の block の port の形になる。
2. 型の中身は型ごとのモジュールに分ける。`src/tdd.py` は tdd 型の中身だけを持ち、修正役の受け付けが借りている部品（1.2 の 6）は共通のモジュールへ移す（例: 作業ツリーの写しと戻し・試験の走らせ・版の読み口）。段 1 の時から型のモジュールどうしは import しない（持ち主の答え 2026-10-25 の 3）。段 1 の間は `tests/layers/` に yes/no の試験 1 本（型のモジュールが別の型のモジュールを import していない）を置き、段 2 で型が block になったら、その試験を消して block の形の検査（`tests/layers/test_block_shape.py`）に任せる。
3. 組の子の頭（今の `group-start`・`tdd-go`）が、計画の route から型ごとの注文を書く。型が `gave_up` で返した単位を同じ段の別の型の注文に書き直すのもここ（1.2 の 5 を型の外へ）。型の名から YAML の輪の id を引く表はここに 1 つだけ置く。
4. YAML の組の子は、型ごとの輪を `when:` で並べる。`when:` に渡すのは、組の子の頭が計算した「この型の注文が在るか」の真偽だけにする（憲法の 1）。
5. 共通の受け付け（2.3）と義務の表（2.4）を 1 つのモジュールにし、どの型の輪の後にも同じ受け付けを通す。
6. 合わせ役・裁定役・裁定の後の直しは、返しの `evidence.named` と `changes` だけを読む（1.2 の 7 をやめる）。裁定の後の直しは、裁定の範囲を `permits` に入れた direct の注文として出し、元の単位の型の義務で照らし直す（今の `gates.py` の red_green が受け入れの試験を照らし直すのと同じ）。
7. 修正の block の出力は、今の読み手（line・r2・report）が読む欄の形を保つ（`tdd`・`tdd_refused`・`freeze_off`・`units` など）。足すのは消した試験の並びの欄 1 つで、line の最後の承認がこれを「消した試験」の節に出す。
8. 段 1 で作る型は tdd・direct・remove。tidy・rebuild は schema の名と 2.4 の表の行だけを置き、注文を書く道を開けない（3.4・3.5 の届かない訳）。

### 4.2 段 2: 型を block に上げる（行き先。持ち主の答え 2026-10-25 の 3）

- 訳（持ち主の言葉の訳）: どの型を使うかは手前の振り分けで決まり、型は受けた注文をこなす部品にできる。振り分けの設計を型の作りと切り離して進められる。
- 形: 型ごとに `workflows/<型の block>/` を置き（名は `works-factory-<フォルダの名>`。E9）、修正の組の子が `include:` で型の block を並べる。`include:` は読み込みの時に同じ run の中へ展開されるので（`docs/design/archon.md:33`）、組の子の作業ツリーを分け合える。`loop_group` の中にも書ける（`archon.md:74`）。
- 得る物: 型どうしが互いの中身を知らないことを、今在る block の形の検査（`tests/layers/test_block_shape.py`。ほかの block のフォルダへのパスを組まない）と憲法の 3 がそのまま照らす。新しい検査を作らなくてよい（持ち主の決め `mechanism-over-tests`）。型を単独で回せる（憲法の 5。注文のファイルと対象のリポジトリだけで回る）。

## 5 世の中の定石との比べ

- Beck の Tidy First?: 構造の変更（tidying）と振る舞いの変更を別の変更に分ける。整理の 1 つに使われていないコードの削除を挙げる（Henrik Warne の書評）。→ 2 段の分け（2.0）と、使われていないコードの削除を tidy に入れる形（3.4）に合う。TDD の中の整えの段は、振る舞いの変更の直後の小さな整えで、Beck の「後で整える」に当たる。
- Beck の Canon TDD（https://tidyfirst.substack.com/p/canon-tdd）: 一度に書く試験を 1 つに限り、「Mistake: mixing refactoring into making the test pass.」とする。→ tdd の型が小さく積む前提（3.1）。整えを緑の後に分ける今の輪の形のまま。
- Fowler のリファクタリングの定義: 観測できる振る舞いを変えずに内部の構造を変え、変換のたびに動く状態に保つ。確かめは既存の試験を前後で回して同じ結果になること。→ 変えない段の義務（2.4）そのもの。
- Feathers の characterization test・golden master・approval testing（https://understandlegacycode.com/blog/characterization-tests-or-approval-tests/・https://codurance.com/2012/11/11/testing-legacy-code-with-golden-master/）: 「document your system's actual behavior; not to check for the behavior you wish your system had」。入力を投げて出力を記録し、直した後に比べる。揺れる出力は除く。→ 下ごしらえ（3.6）。TDD の「先に赤」の逆で、だから TDD の輪の段では書けない（1.3 の run 20447be2）。
- Fowler の Branch by Abstraction（https://martinfowler.com/bliki/BranchByAbstraction.html）: 呼び手と今の提供側の間に抽象化の層を置き、新しい提供側を試験の環境で動かして振る舞いを比べる。→ rebuild の手順 1（3.5）。
- GitHub の Scientist（https://github.com/github/scientist）と HEY の事例: 本番で両方を走らせ、現行の結果を返し、食い違いを記録する。比べは既定で `==`。「You need to make sure that invoking both paths is feasible, which is not always the case.」→ rebuild の手順 2 と前提（軸 4）。工場は本番を持たないので、比べは run の中で同じ入力を両方に投げる形にする。
- Fowler の Strangler Fig・Azure の文書・Spolsky: 段階の移し替えを勧め、単純な置き換えは「go down in flames most of the time」。旧システムへの要求を横取りできなければ合わないかもしれない。Spolsky は一からの書き直しを戒める。→ rebuild を「一から書く型」にせず、境目を残して新旧を比べる型にする（3.5）。工場の 1 つの run は数年にわたる移し替えを持てないので、Strangler Fig そのものは型にしない。
- Fowler の Parallel Change（https://martinfowler.com/bliki/ParallelChange.html）: 広げる・移す・縮めるの 3 段で、縮める段をやらないと始めより悪い状態に終わりうる。→ 利用者に見える境目を越える rebuild で古い経路を残すかの問い（9.2 の 2）。
- DHH の「TDD is dead」（https://dhh.dk/2014/tdd-is-dead-long-live-testing）: テスト先行が設計を損なう時があるとし、システムテストを重く見る。→ 持ち主の言葉「がっつりリアーキするときは TDD なんて細かくやるよりごっそりいったほうがいい」の側の原典。大きな作り直しに合わないとまでは書いていない（材料のノートの食い違いの節）。
- Google の大規模変更（https://abseil.io/resources/swe-book/html/ch22.html）: 大半は機能にほぼ影響しない書き換えで、機械で作り、境界で分けて別々に試験する。消した記号が再び入るのを防ぐ仕組みが要る。→ tidy の範囲。消した名が再び入るのを防ぐ物は、この設計の外（工場は 1 つの依頼の直しまでを持つ）。
- Cursor の報告（https://cursor.com/blog/reward-hacking-coding-benchmarks）: SWE-bench Pro で「63% of successful Opus 4.8 Max resolutions retrieved the fix rather than derived it」。git の履歴を封じて網を絞ると点が下がった。修正済みの実のバグから作った評価は特に弱い。→ 試験が通るだけでは証拠として弱い（10 章の 6）。
- superpowers 7.0.0 の test-driven-development（`lib/borrow/superpowers/7.0.0/skills/test-driven-development/`）: 「Always」に Refactoring を挙げる（`SKILL.md:17-21`）が、整えは「After green only」（`SKILL.md:195-201`）で、赤の無い整理の手順は無い。消した名が無いことを確かめる試験は悪い兆し（`writing-good-tests.md:192`）。→ TDD の型は今のまま superpowers に沿い、赤の無い直し方は別の型に出す。持ち主の問い「TDD でそれができるならいいけど」への答え: TDD の赤の義務を保ったままでは、消す依頼も書き直しの依頼も通らない。通すには TDD の段に例外を足すことになり、それが run 19268881 の 20 件の穴になった。
- ASF の implement（`.archon/workflows/sdlc/implement/commands/implement.md`）: 直し方で役を分けず、1 つの実装役が計画・審査の指摘・CI の落ち・説明のどれでも受ける。試験は壊れうる所だけに書く（`implement.md:49`）。消しは頼まれた範囲の中だけで、置き換わった仕組みは消す（`implement.md:54`）。確かめは変えた所の当たる試験を回すこと。→ ASF は「型を分けず、結果を当たる試験で確かめる」側。工場は持ち主の決め `tdd` で赤緑の機械の判定を持つので、ASF の 1 本の形には寄せない。採るのは「確かめを直し方の手順でなく結果の照らしに置く」型（2.3 の共通の受け付け）。
- ASF の simplify（`simplify/commands/simplify.md:3`）: 「求める結果を、要る以上の構造で届けている」を探す読むだけの審査。直す役ではない。→ 型の候補ではなく、型の後の差分の審査の側（delta-review・lens）の比べ相手。

### 9.2 新しく決めてほしいこと

1. 試験を走らせる道が無い対象（テストがそもそも無いリポジトリ・実行器が走らない）で、変える段の義務（変えた動きを試験か機械で示す）を満たせない時にどうするか。今は「実行器が走らない」で残りの単位を全部 direct にし、direct は共通の義務だけで通る（1.2 の 5）。direct を変える段に置くと（3.2）、この道は通らなくなる。
   - 推し: 下ごしらえ（3.6）の前に、試験の走らせ方（起動スクリプト）を工場の AI が作り、それで変えた動きを示す。作れない・作っても走らない時は止めて人に聞く。持ち主の決め `base-runs-nothing` の「工場の起動スクリプトを書き直させ、直らない時だけ止めて人に聞く」と同じ形で、段の義務に例外を作らない。
   - 代案 A: 作らずに止めて人に聞く。代償: テストの無いリポジトリへの依頼は全部人に回る（無人で回らない）。
   - 代案 B: 通して、最後の承認に「変えた動きを示せていない直し」の節を出す（今の `ALLOWED_UNCHECKED` の添えに近い形）。代償: 変える段の義務に「示せない時は通す」の例外が入り、2.0 の「段の決まりに例外を書き足さない」が崩れる。
2. 大きな作り直し（rebuild）で、1 つの run の差分に古い経路を残すか。
   - 推し: 比べが通ったら同じ run の中で古い経路を消し、差分には新しい経路だけを出す。比べの記録は消す前の木で取り、`evidence.compared` に残す。ただし、境目が利用者に見える物（公開 API・データ。軸 5）なら、古い経路を消さずに残して出し、消すのは別の依頼にする（Parallel Change の縮める段を後に回す）。
   - 代案 A: いつも消す。代償: 利用者に見える境目で、利用者が移る前に古い経路が消える（破壊的変更を告知なしに出す）。
   - 代案 B: いつも残す。代償: 境目の内側だけの作り直しでも、新旧の 2 つを抱えたまま出し、縮める段を誰もやらないと始めより悪い形に終わりうる（Parallel Change の警告）。
   - 響き: 推しは軸 5 の値を rebuild の中で読むことになる。軸の値を誰が決めるか（計画が `orders.rebuild` に書くか）は、型の選び方と一緒に別に詰める。

## 10 残る設計の問い（持ち主に聞かず、次の版で詰める物）

1. 振り分けの段（route）の居場所: `routes=auto` の時に TDD の役が単位を振る今の段を、組の子の頭の前の AI のノードとして型の外に出すか。選び方は変えない約束なので、振る役の指示は変えずに置き場だけを動かす形を次の版で描く。段 2 で型が block になると、振り分けは修正の block に残り、型の block は振り分けを知らない（4.2 の訳）。
2. 裁定の後の直し: direct の注文として出す形（4.1 の 6）で、tdd の単位の受け入れの試験の照らし直しが今と同じになるかを、`gates.py` の red_green の読み口で確かめる。
3. remove の段の義務との合わせ目（3.3）: 誰も呼んでいない機能を消す時、変える段の「名指しの試験が赤から緑」を満たす試験が無い。案は 2 つ: (a) 機能の入口（利用者が呼ぶ口）を縛る試験を `rewrite` で書き換え、「呼ぶと無い」と返す振る舞いを縛る（消えたことを縛る試験と近く、superpowers の悪い兆しに当たりうる）。(b) 変える段の義務の「機械で示す」を、消す名が木で引けないこと（`remove` の型の義務の照らし）で満たすと段の義務に書く。(b) は段の義務に型の名が入る形になるので、段の義務を「名指しの試験か、型が返す機械の照らしの印のどちらか」と型を問わない言い方にできるかを次の版で詰める。
4. 組の頭で取る元の結末: 今は TDD の輪の頭が取って控えに書く（`tdd.py:573`・持ち主の決め `base-runs-nothing`）。どの型も使うので組の子の頭に移す形が要る。`base-runs-nothing` の「直す前は走らせない」と食い違わない取り方（関わる試験を、最初の型の輪の頭で 1 度だけ取る）にする。下ごしらえ（3.6）を挟む時は、その後に取る。
5. rebuild の比べの入力: 入力をどこから集めるか（既存の試験の入力・下ごしらえが記録した入力・乱数）。言語を問わない形（E13）で、比べの記録の JSON の行の形を決める。
6. 試験が通るだけでは証拠として弱い（Cursor の報告。5 章）: 型の返す証拠に、試験の結果のほかに何を足すか。候補:
   - (a) 直しを外すと名指しの試験が赤に戻ること（今の「起点の木で赤」で既に照らしている。tdd・direct・remove の変える段は持つ。変えない段は持たない）。
   - (b) 型が足した・書き換えた試験を、型と別の役が読み、直しの中身に合わせて書かれた試験（入力を特別扱いする直し・試験の期待を直しに合わせた書き換え）でないかを照らす。今の delta-review・lens の側に置くか、型の返しの証拠にするか。
   - (c) 直しの出どころの印: 型の役が対象のリポジトリの git の履歴（後の版）や網から答えを取っていないか。工場の run は対象の今の版の上で直すので、Cursor の報告の「修正済みのバグの答えを履歴から取る」とは場面が違う。履歴を封じるかは、場面が当たるかを確かめてから決める。
   - (d) r2 の独立設計との比べ（今在る。修正の block の外）を、証拠の 1 つとして型の返しから指せるか。
7. 審査の鍵 `prompt-no-name-vs-red`・`prompt-sentence-english` の中身: round-1〜3 の記録に名しか無い。次の版で、審査の控えの全文を読んで照らす。
