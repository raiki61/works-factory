# 直し方の型（Weapon）を切り分ける設計の下書き（受付 20261024-104757-e4058d・第 1 版）

## 冒頭

- 型の数: 今の 2 本（TDD と direct）を、互いの中身を知らない 2 本に切り直す。そのうえで「機能を消す型」と「振る舞いを変えない書き直しの型」を足すかを案として描く。全部採ると 4 本になる。
- 今と変わる所:
  - どの型も同じ形の「注文」を受け、同じ形の「返し」（差分と確かめの証拠）を返す。
  - 確かめは、型ごとの義務の表を引く 1 つの機械が受け持つ。
  - TDD の後に修正役がいつも起きて TDD の記録を写し直す形をやめる。
  - 試験を変えてよい許しは、どの型にも注文の 1 欄でだけ届ける。
  - 最後の承認には「消した試験」の節を分けて出す。
  - どの依頼にどの型を当てるか（今の計画の route）は変えない。
- 持ち主に決めてほしいこと（9 章）: (1) 消す型を立てるか（推し: 立てる）。(2) 書き直しの型を立てるか（推し: 口の形だけ今決め、作るのは判定の単位の決めを見直す時と一緒にする）。(3) 型を将来 block に上げるか（推し: 段 1 は修正の block の中で口をそろえ、block に上げる段 2 は段 1 の後に決める）。

## 語

- 型（Weapon）: 1 つの直し方。受け取る物・やる事・返す物・確かめ方がひとそろいで決まっている物。今は TDD（赤 → 緑 → 申告した時だけ整える、の輪）と direct（修正役が試験を先に書かずに直す）の 2 本。
- 注文: 型が受け取る物のひとそろい（2.1）。
- 返し: 型が返す物のひとそろい（2.2）。
- 義務: 型ごとに、返しの証拠が満たさなければならない yes/no の決まり（2.4）。
- 共通の受け付け: 型の中身を知らずに、返しを注文と義務に照らす機械（2.3）。
- 許し: 既存の試験を変えてよいという印。出どころは `lib/conflict.py:792` の `test_permits` が並べる 6 つ（修正案の `rewrite_tests`・消す名の許し `plan-removes`・範囲の相談の合意・裁定の `fix_test_scope`・直す前から壊れていた試験・案の直しの単位）。
- 組の子: 修正の block が直しの組ごとに起こす子の run（`workflows/fix/works-factory-fix.yaml` の `group-start` 〜 `group-end`）。

## 2 型の口（どの型も同じ形）

型どうしは口の形だけをそろえ、中身を知らない。口の形はファイルの形（`workflows/fix/schemas/` の JSON Schema）で決め、Python の型や関数の呼び出しで決めない。こうしておくと、段 2 で型を block に上げる時（4.2）に、口がそのまま block の port になる。

### 2.1 注文（受け取る物）

組の子の頭が、型ごとに 1 つ書く。型は注文のファイルだけを読み、計画の欄（`planmarks`）・判定・ほかの型の状態を読まない。

- `weapon`: 型の名（`tdd`・`direct`。立てるなら `remove`・`keep`）。
- `units`: 直す単位の並び。単位ごとに key・項目の id・何を直すか（判定と brief の該当の行）。
- `scope`: 書いてよいパスの glob（`allowed_paths`）と触らない物（`out_of_scope` の `{glob, why}`）。
- `permits`: 試験を変えてよい許しの行。`conflict.test_permits` の行を、この注文の項目と単位で絞った物だけ。行ごとに `kind`（`rewrite`・`remove`・`agreed`・`ruled`・`broken`・`replan`）と `duty`（義務か）を持つ。`rewrite` は義務（その試験を書き換えて新しい振る舞いを縛る）、`remove` は義務でない許し。この 2 つを 1 つの語に混ぜない。
- `base`: 起点。run の修正前の版（`board.base_rev_of`。`board.py:1801`）と、組の頭で 1 度取った関わる試験の元の結末。どの型も同じ起点で比べる。
- `run`: 試験の走らせ方（test_cmd・実行器）と、当たる試験の選び方の結果。
- `asks_answered`: 前の周の申し出への答え（範囲の相談の答え・裁定）。

型ごとの欄は `orders.<weapon>` に入れる（例: TDD の受け入れの試験の名指しと整えの申告・消す型の消す名の並び）。共通の受け付けはこの欄を読まない。

### 2.2 返し（返す物）

- `status`: `done`（全部の単位を直した）・`parked`（申し出を積んで止めた）・`gave_up`（3 回の却下で諦めた）。
- `tree`: 返した時の作業ツリーの木の hash。差分は `base` からこの木までで、型は自分で差分を書かない。
- `changes`: 単位ごとの変更の行 `{unit, files, what}`。型が自分で書く。ほかの役に写させない（1.2 の 1・2 をやめる）。
- `evidence`: 確かめの証拠。どの型も同じ欄で、使わない欄は空。
  - `named`: 型が名指した試験（TDD の受け入れの試験など）。
  - `before`・`after`: 名指しと関わる試験の、起点と返した木での結末（JUnit の結末から機械が作る）。
  - `added`・`rewritten`・`removed`: 足した・書き換えた・関数ごと消した試験の id。型の申告で、共通の受け付けが木の比べで照らし直す。
- `asks`: 食い違いの申し出の行（今の `lib/conflict.py` の形のまま）。
- `report`: 報告に載せる日本語の行。

### 2.3 共通の受け付け（型の中身を知らない機械）

返しが来たら、型の名を問わず同じ順で照らす。今の `accept_reply`・`gates.py`・`assert_changed.py` の照らしのうち、型を問わない物をここに集める。

1. 範囲: `base` から `tree` までに変わったパスが `scope` の中か（今の `scope.py`）。
2. 書き込みの出どころ: 書いたのが役の Edit・Write か（今の `lib/writes.py`。keep-essence の 5）。
3. 試験の変更: 起点の木と返した木の試験の関数を比べ、変わった・消えた関数がどれも `permits` の行の中か（今の `gates.py` の `test_edits`。許しは注文の `permits` だけを読む）。消えた関数の集まりは機械が出し、`evidence.removed` の申告と合うかも照らす。
4. 申告したファイルが本当に変わったか（今の `assert_changed.py`）。
5. 義務: 2.4 の表で、型の名から義務を引いて `evidence` に当てる。

この機械は `orders.<weapon>` も型の状態のファイルも読まない。型の名で枝分かれするのは 5 の表引きの 1 か所だけ。

### 2.4 確かめの表（型ごとの義務）

どれも yes/no で、機械が JUnit の結末と木の比べだけで決める（憲法の 6）。

- 全部の型に共通: 起点で通っていた関わる試験が、返した木でも通る。返した木で居なくなった試験は、どれも `permits` の中にあり `evidence.removed` に名がある（今の `lib/baseline_red.py:121-143` は居なくなった試験を見ないので、ここで足す）。
- `tdd`: 名指しの試験が、単位の頭で failure（赤）、返した木で通る（緑）。義務の `rewrite` の試験は書き換わって赤から緑になる。`remove` の許しは使わない（消す依頼は消す型に回す。3.3）。
- `direct`: 共通の義務だけ。
- `remove`（立てるなら）: 注文の消す名の定義が返した木で引けない（`planmarks.line_in` と `file_symbols` の機械の照らし）。消した試験は `remove` か `rewrite` の許しの中。残った試験は共通の義務を満たす。
- `keep`（立てるなら）: 関わる試験の結末の並びが、起点と返した木で同じ（通っていた物が全部通り、居なくなった物が無い）。既存の試験は変えない（許しが名指した物だけ例外）。足してよい試験は、起点の木で通る試験だけ（Feathers の characterization test。赤を求めない）。

TDD の refactor の段は、`keep` の義務と同じ照らしを使う（段の確かめを TDD の中に別に持たない）。`refactor-same` の「修正役が緑の後に同じ会話で整え、緑のままかを機械が 1 回確かめる」はそのまま保つ。

## 3 型ごとの中身

### 3.1 tdd

- 受け取る: 共通の注文と、`orders.tdd` の受け入れの試験の名指し・整えの申告。
- やる: 今の輪の test・fix・refactor の段。振り分けの段（route）は型の外へ出す（今の `routes=plan` の道と同じく、組の子の頭が注文を型ごとに分けて書く）。
- 返す: 単位ごとの `changes` と `evidence`。今は修正役が `changes` に写していた行を、輪が自分で書く。
- 型の外に出す物: `_to_direct` の 4 つの道（1.2 の 5）。輪は「この単位は tdd の義務を満たせない」を `status` と訳で返すだけにし、direct の注文を書き直すのは組の子の頭（4.1 の 3）。
- 消す名の許し: 読まない。消す依頼を tdd の輪で通すために段ごとの例外を足す形（run 19268881 の第 3 版の項目 1）は採らない。採ると 7 章の 1 群の穴がそのまま残る。

### 3.2 direct

- 受け取る: 共通の注文だけ。
- やる: 今の修正役の直し。TDD で直した単位を見ない。
- 返す: 単位ごとの `changes` と `evidence`（`named` は空でよい）。
- 今と変わる所: TDD の後にいつも起きる形をやめ、direct の注文が在る時だけ起きる。修正役の指示から TDD の要約（`FIXED_HEAD`・`DIRECT_HEAD`）を外す。

### 3.3 （案）消す型 `remove`

- 受け取る: 共通の注文と、`orders.remove` の消す物の並び（`change=remove` の名・`op=delete` のパス・`op=rename` の元）。`permits` には消す名を使う試験の `remove` の行が入る。
- やる: 消す物と、それを縛る試験を消す。消す物を使う残りのコードを直す。新しい振る舞いへの書き換えはしない。「X を消して振る舞いの違う Y に替える」依頼は、消す項目と足す項目（tdd）の 2 つにし、足す項目が `depends_on` で消す項目を待つ（計画の欄 `depends_on` は今在る）。
- 確かめ: 2.4 の `remove`。消えたことを縛る試験を書かせない（superpowers の `writing-good-tests.md:192` が悪い兆しとする「消した名が無いことを確かめる試験」）。消えたことは機械が木で照らす。
- 最後の承認: `evidence.removed` を受け付けが照らした集まりから、「消した試験」の節を id で並べる。「書き換えを許したテストを触った」の節には入れない。
- 今の形との違い: 今は消す依頼を tdd か direct のどちらかが別の型の都合で抱える。消す型を立てると、消す依頼の確かめが 1 か所にまとまる。

### 3.4 （案）振る舞いを変えない書き直しの型 `keep`

- 受け取る: 共通の注文と、`orders.keep` の保つ振る舞いの説明（何を変えずに何の形を変えるか）。
- やる: 1 段目で、保つ振る舞いを縛る試験が関わる試験の中に在るかを見る。足りなければ、起点の木で通る試験を足す（Feathers の characterization test）。2 段目で書き直す。
- 確かめ: 2.4 の `keep`。1 段目で足した試験は、起点の木で走らせて通ることを機械が照らす（TDD の赤の照らしの裏返し）。
- 今の形とのつながり: TDD の refactor の段と照らしを分け合う（2.4）。`refactor-same` は「TDD の中の整え」の決めで、整えだけの単位の型はこの決めに当たらない。
- 届かない訳: 今の判定は欠陥の形の無い単位を作らない（`judge.py:268-272`・`exit.py:90`）。案の項目も単位を 1 つ以上要る（`planmarks.py:153-155`）。だからこの型を作っても、判定の単位の決めを見直すまでは、どの run もこの型に届かない。

## 4 切り方（互いの中身を知らない形）

### 4.1 段 1: 修正の block の中で口をそろえる（どの案でも要る）

1. 注文と返しの形を `workflows/fix/schemas/weapon-order.schema.json`・`weapon-return.schema.json` に置く。
2. 型の中身は型ごとのモジュールに分ける。`src/tdd.py` は tdd 型の中身だけを持ち、修正役の受け付けが借りている部品（1.2 の 6）は共通のモジュールへ移す（例: 作業ツリーの写しと戻し・試験の走らせ・版の読み口）。型のモジュールどうしは import しない。これを `tests/layers/` の yes/no の試験 1 本で照らすか、段 2 の block の形の検査に任せるかは 9 章の (3) で決まる。
3. 組の子の頭（今の `group-start`・`tdd-go`）が、計画の route から型ごとの注文を書く。型が「義務を満たせない」で返した単位を direct の注文に書き直すのもここ（1.2 の 5 を型の外へ）。型の名から YAML の輪の id と義務を引く表はここに 1 つだけ置く。
4. YAML の組の子は、型ごとの輪を `when:` で並べる。`when:` に渡すのは、組の子の頭が計算した「この型の注文が在るか」の真偽だけにする（憲法の 1）。
5. 共通の受け付け（2.3）を 1 つのモジュールにし、どの型の輪の後にも同じ受け付けを通す。
6. 合わせ役・裁定役・裁定の後の直しは、返しの `evidence.named` と `changes` だけを読む（1.2 の 7 をやめる）。裁定の後の直しは、裁定の範囲を `permits` に入れた direct の注文として出し、元の単位の型の義務で照らし直す（今の `gates.py` の red_green が受け入れの試験を照らし直すのと同じ）。
7. 修正の block の出力は、今の読み手（line・r2・report）が読む欄の形を保つ（`tdd`・`tdd_refused`・`freeze_off`・`units` など）。足すのは消した試験の並びの欄 1 つで、line の最後の承認がこれを「消した試験」の節に出す。

### 4.2 段 2（案）: 型を block に上げる

- 形: 型ごとに `workflows/<型の block>/` を置き、修正の組の子が `include:` で型の block を並べる。`include:` は読み込みの時に同じ run の中へ展開されるので（`docs/design/archon.md:33`）、組の子の作業ツリーを分け合える。`loop_group` の中にも書ける（`archon.md:74`）。
- 得る物: 型どうしが互いの中身を知らないことを、今在る block の形の検査（`tests/layers/test_block_shape.py`。ほかの block のフォルダへのパスを組まない）と憲法の 3 がそのまま照らす。新しい検査を作らなくてよい（持ち主の決め `mechanism-over-tests`）。型を単独で回せる（憲法の 5。注文のファイルと対象のリポジトリだけで回る）。
- 代償: 型の block ごとに YAML・筋書き・設計書が要る。修正の block の設計書（1077 行）を分け直す。`include:` の先の承認ノードと待ちの決まり（`archon.md:43`）と、include の入力が `if_skipped` を運べないこと（埋め P2）に合わせる。
- 未確認: `include:` のノードに `when:` を書いて型ごとに飛ばす形が、止めた Archon で読み込める・走るか。段 2 を採るなら、作る前に実物で確かめる（持ち主の決め `real-measure`）。

### 4.3 今の読み手への響き

- line の最後の承認（`final.py`）: 消した試験は修正の出力の新しい欄から読み、節を分ける。「書き換えを許したテストを触った」の数え（`final.py:89-90`）から消した試験を外す。「封じた差分が無い・読めない」の添え（`ALLOWED_UNCHECKED`）は、どの節の組み合わせでも 1 度だけ出す決まりを `final.py` の 1 か所に置く。
- 計画の役（`plan-writer.md`）: 型の中の決まり（段ごとに何を変えてよいか）を書かない。項目に「何を直す・消す・保つか」と route を書くだけ。欄の名は字で写さず `{machine_key}` のように差し込む。
- r2・report: 出力の `tdd` の形を保つので変わらない。

## 5 世の中の定石との比べ

- Beck の Tidy First?: 構造の変更（tidying）と振る舞いの変更を別の変更に分ける。機能を消すのは振る舞いの変更。→ `keep` と `remove` を別の型にし、混ぜる依頼は項目を分ける（3.3）形に合う。TDD の中の整えの段は、振る舞いの変更の直後の小さな整えで、Beck の「後で整える」に当たる。
- Fowler のリファクタリングの定義: 観測できる振る舞いを変えずに内部の構造を変える。確かめは既存の試験を前後で回して同じ結果になること。→ `keep` の義務（2.4）そのもの。
- Feathers の characterization test: 今の振る舞いを縛る試験を、直す前に足す。この試験は直す前から通るのが正しい。→ `keep` の 1 段目。TDD の「先に赤」の逆で、だから TDD の輪の段では書けない（1.3 の run 20447be2）。
- superpowers 7.0.0 の test-driven-development（`lib/borrow/superpowers/7.0.0/skills/test-driven-development/`）: 「Always」に Refactoring を挙げる（`SKILL.md:17-21`）が、整えは「After green only」（`SKILL.md:195-201`）で、赤の無い整理の手順は無い。消した名が無いことを確かめる試験は悪い兆し（`writing-good-tests.md:192`）。→ TDD の型は今のまま superpowers に沿い、赤の無い直し方は別の型に出す。持ち主の問い「TDD でそれができるならいいけど」への答え: TDD の赤の義務を保ったままでは、消す依頼も書き直しの依頼も通らない。通すには TDD の段に例外を足すことになり、それが run 19268881 の 20 件の穴になった。
- ASF の implement（`.archon/workflows/sdlc/implement/commands/implement.md`）: 直し方で役を分けず、1 つの実装役が計画・審査の指摘・CI の落ち・説明のどれでも受ける。試験は壊れうる所だけに書く（`implement.md:49`）。消しは頼まれた範囲の中だけで、置き換わった仕組みは消す（`implement.md:54`）。確かめは変えた所の当たる試験を回すこと。→ ASF は「型を分けず、結果を当たる試験で確かめる」側。工場は持ち主の決め `tdd` で赤緑の機械の判定を持つので、ASF の 1 本の形には寄せない。採るのは「確かめを直し方の手順でなく結果の照らしに置く」型（2.3 の共通の受け付け）。
- ASF の simplify（`simplify/commands/simplify.md:3`）: 「求める結果を、要る以上の構造で届けている」を探す読むだけの審査。直す役ではない。→ 型の候補ではなく、型の後の差分の審査の側（delta-review・lens）の比べ相手。

## 6 憲法の 3 と E11 の 3 つの確かめ

### 6.1 憲法の 3（block は宣言した port だけで受け渡す）

- 段 1: 型は block ではないので憲法の 3 は直に当たらない。同じ考えを block の中に当て、型は注文と返しのファイルだけで受け渡す（2 章）。型のモジュールどうしの import を禁じる。
- 段 2: 型が block になり、注文が port、返しが `returns:` の出力になる。憲法の 3 と E4・E5 がそのまま当たる。

### 6.2 E11 の 1: Archon が持っているか

- 直し方を選ぶ仕組みは無い。Archon が持つのは、つなぐ道具の `include:`（同じ run に展開。`archon.md:33`）・`when:`・`loop_group`・`workflow:` の `fan_out:` だけ。型を並べて選ぶのはこれで足り、新しい埋めは要らない見込み（4.2 の未確認を除く）。

### 6.3 E11 の 2: ASF が持っているか

- ASF は直し方で役を分けない（5 章の implement）。持つのは 1 本の実装役と、読むだけの審査（simplify ほか）。型の切り分けは ASF に無い。採る型は「確かめを結果の照らしに置く」こと。採ったら `docs/asf-notes.md` に 1 行足す（E8）。

### 6.4 E11 の 3: 本当に要るか

- 当たる失敗: run 82d22f4f（消す依頼で 259 件の許しが積まれて止まった）・run 20447be2 の組の子 5eba0fb0（書き直しで止め置き）・書き直しの依頼が修正まで届いた run は 0 件・run 19268881 の 3 往復で 20 件の穴。
- keep-essence: 3（試験の凍結と許す道は 1 本）は、今は輪の側が別の口を通るので守れていない（1.2 の 4）。段 1 で守れる形に戻る。ほかの項目は 8 章。
- 元の works の同じ場面: 元の works も修正の決まりを `direct.md` と `tdd.md` に分けていた（`docs/design/fix.md:374`）。分けた決まりを修正役が両方読む形で、型の口は無かった。

## 9 持ち主に決めてほしいこと

1. 消す型 `remove` を立てるか。
   - 推し: 立てる（3.3）。消す依頼の確かめが 1 か所にまとまり、最後の承認に消した試験を id で出せる。
   - 代案: 立てず、消す名の許しを tdd の輪に段ごとの例外で読ませる（run 19268881 の第 3 版の形）。
   - 代案の代償: 3 往復で 20 件の穴が出た形で、型の段の決まりに別の型の都合が入り続ける。
   - 決めの響き: 持ち主の決め `tdd`（「修正には TDD のループを踏ませる」）の例外が、今の direct に加えてもう 1 つ増える。
2. 書き直しの型 `keep` を立てるか。
   - 推し: 口の形（2 章・3.4）だけを今決め、作るのは判定の単位の決め（欠陥の形 1 つ）を見直す時と一緒にする。単位の決めが今のままでは、作ってもどの run も届かない（3.4）。
   - 代案: 今は立てず、振る舞いを保つ整理は route を direct にして共通の義務だけで確かめる（run 19268881 の第 3 版の項目 3 の形）。
   - 代案の代償: 書き直しで振る舞いが保たれたかの照らしが「通っていた試験が通る」だけになり、保つ振る舞いを縛る試験が無い所は誰も照らさない。
3. 型を block に上げる段 2 を採るか。
   - 推し: 段 1（4.1）を先に作り、段 2（4.2）は段 1 の後に、`include:` と `when:` の実物の確かめを見て決める。
   - 代案: 初めから型ごとの block で作る。
   - 代案の代償: 修正の block の設計書と試験を一度に分け直すことになり、段 1 の口の形が実物で固まる前に block の形を決めることになる。
