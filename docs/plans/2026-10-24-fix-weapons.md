## 語

- 赤・緑: 試験が落ちる結末と通る結末。「赤緑」は、直す前の木で赤、直した後で緑を見る確かめ。赤と緑は機械が JUnit XML の結末で判じる（`docs/design/fix.md` の TDD の loop）。
- 型（Weapon）: 1 つの直し方。受け取る物・やる事・返す物・確かめ方がひとそろいで決まっている物。今は TDD（赤 → 緑 → 申告した時だけ整える、の輪）と direct（修正役が試験を先に書かずに直す）の 2 本。第 5 版の案では tdd・variant・remove・static・tidy・rebuild の 6 本（第 4 版で足した pin は下ごしらえに寄せた）。
- 箱: 型の上の分け。「振る舞いを変える」段（`change`）・「振る舞いを変えない」段（`keep`）・試験で照らさない「段の外」（`outside`）の 3 つ。箱ごとに共通の義務を持ち、どの型も 1 つの箱にだけ属する（2.0）。第 2 版の「段」は、この中の 2 つ。
- 注文: 型が受け取る物のひとそろい（2.1）。
- 返し: 型が返す物のひとそろい（2.2）。
- 義務: 返しの証拠が満たさなければならない yes/no の決まり。箱の義務と型の義務の 2 層（2.4）。
- 共通の受け付け: 型の中身を知らずに、返しを注文と義務に照らす機械（2.3）。
- 閉じの証明: 今の修正役の返答のうち、単位ごとに「直したら閉じた」を示す欄のひとそろい（`closure`・`coverage`・`root_or_symptom`・`bypass_tried`・`breaks`・`precedent` と、周の全体の `interactions`・`fix_closure`）。元は graphloops の review-loop の修正の段（`docs/design/fix.md:397`）。棚卸しは 1.4。
- 許し: 既存の試験を変えてよいという印。出どころは `lib/conflict.py:792` の `test_permits` が並べる 6 つ（修正案の `rewrite_tests`・消す名の許し `plan-removes`・範囲の相談の合意・裁定の `fix_test_scope`・直す前から壊れていた試験・案の直しの単位）。
- 持ち主: この工場の持ち主で、設計の決めを出す人。「持ち主の答え」「持ち主の言葉」は、その人がこの下書きの問いに返した答えと発言（9.1）。「持ち主の決め `<名>`」は `docs/owner-decisions.md` の決めの名。
- 段 1・段 2: 型を切り分ける手順の 2 つの段階。段 1 は修正の block の中で型の口をそろえ、型ごとのモジュールに分ける今の一歩（4.1）。段 2 は型をそれぞれ block に上げる行き先（4.2）。箱（2.0）の「変える段」「変えない段」とは別の物。
- 口: 型が受け取る注文と返す返しの形（2 章）。ファイルの形（JSON Schema）で決め、段 2 でそのまま型の block の port になる。
- 場面の軸: 直す場面を分ける 6 つの見方（3.0）。「軸 1」〜「軸 6」は 3.0 の番号。
- 下ごしらえ: 今の振る舞いを試験で固める段（3.6）。機械の名は `pin`。どの型の前にも挟めて、試験の欠けだけを埋める依頼なら単独でも頼める（第 5 版）。コードを直さないので型ではない。
- 組の子: 修正の block が直しの組ごとに起こす子の run（`workflows/fix/works-factory-fix.yaml` の `group-start` 〜 `group-end`）。組の子の頭は、組の子の始めで型の輪より前に走る script のノード（今の `group-start`・`tdd-go`。4.1 の 3）。
- 周: Archon の loop のノードの 1 回分。修正の輪では、修正役が返答を 1 回書き、受け付けがそれを照らすまで（`docs/design/fix.md` の loop の中の会話）。「周の全体」は、その 1 回の返答に入る全部の単位。
- Archon: AI の処理をグラフにして YAML で書いて回す道具。工場はこの上で動く（根の `AGENTS.md`）。止めた Archon は、工場が使う版を 1 つの commit に固定した Archon（固定する commit は `factory/pack.json` の `integration_revision_required`。`docs/design/README.md` の語）。
- 凍結: TDD の輪が、テストのファイルの hash を取って控えること（凍ったテスト）。受け付けは、許しの無い凍ったテストが書き換わっていないかを、この hash で照らす（`docs/design/fix.md` の `frozen` の欄・`docs/design/README.md` の 10 章の 3）。
- run: Archon がワークフローを 1 回走らせた物（`archon workflow run` で起こす。`docs/design/archon.md`）。
- block・port: block は観点 1 つ分のノードのまとまりで、1 本の Archon の workflow。port は block の入力（`inputs:`）と出力（`returns:`）（`docs/design/README.md` の語）。
- line・r2・report: line はメイングラフ（`works-factory-line`）。r2 は独立設計との比べと前提の検算をする block、report は報告の block（`docs/design/README.md` の 8 章）。

## 2 箱と型の口（どの型も同じ形）

型どうしは口の形だけをそろえ、中身を知らない。口の形はファイルの形（`workflows/fix/schemas/` の JSON Schema）で決め、Python の型や関数の呼び出しで決めない。こうしておくと、段 2 で型を block に上げる時（4.2）に、口がそのまま block の port になる。

### 2.0 3 つの箱（持ち主の答え 2026-10-25 の 1・5）

型を 2 層に並べる。上の層が箱、下の層が型。

- 変える段 `change`: 型は `tdd`・`variant`・`remove`。
- 変えない段 `keep`: 型は `tidy`（小さな書き直し。使われていないコードの削除を含む）・`rebuild`（大きな作り直し）。型ではない段の下ごしらえ（機械の名 `pin`。今の振る舞いを試験で固める。3.6）も、この箱の義務で照らす（第 5 版。第 4 版の型 `pin` を寄せた）。
- 段の外 `outside`: 型は `static`（試験が要らない直し。3.7）。

決まり:

- どの型も 1 つの箱にだけ属する。下ごしらえも箱は `keep` の 1 つ。型の名（と下ごしらえの名 `pin`）から箱を引く表は 1 か所（2.4 の表）に置き、注文に箱の欄を別に持たない（型の名と箱が食い違う注文を書けなくする。憲法の 6）。
- 型を足す時は、箱を決めて型の義務を足すだけにする。ほかの型の箱の決まりに例外を書き足さない（run 19268881 の 20 件の穴の形を作らない。7 章）。
- 箱は注文で決まる。型が途中で諦めて別の型の注文に書き直される時も、箱は変えない（変える段の型の逃げ先は変える段の型だけ。3.2）。
- 段の外の箱は、試験で何も示さない直しだけを置く。持ち主が描いた 2 段（変える・変えない）は試験で何を示すかで分かれるので、試験で何も示さない直しはどちらの段にも入らない（3.7 の「箱の決め」）。

### 2.1 注文（受け取る物）

組の子の頭が、型ごとに 1 つ書く。下ごしらえ（3.6）を挟む・単独で頼む時は、下ごしらえの注文も同じ形で 1 つ書く。型は注文のファイルだけを読み、計画の欄（`planmarks`）・判定・ほかの型の状態を読まない。

- `weapon`: 型の名（`tdd`・`variant`・`remove`・`static`・`tidy`・`rebuild`）か、下ごしらえの名 `pin`。箱はこの名から 2.4 の表で引く。
- `units`: 直す単位の並び。単位ごとに key・項目の id・何を直すか（判定と brief の該当の行）・判定の `class_query`（在れば）。
- `scope`: 書いてよいパスの glob（`allowed_paths`）と触らない物（`out_of_scope` の `{glob, why}`）。
- `permits`: 試験を変えてよい許しの行。`conflict.test_permits` の行を、この注文の項目と単位で絞った物だけ。行ごとに `kind`（`rewrite`・`remove`・`agreed`・`ruled`・`broken`・`replan`）と `duty`（2.4 の義務で、返しがその行を果たしたかを照らすか）を持つ。`rewrite` は義務の行（その試験を書き換えて新しい振る舞いを縛ったかを、2.4 の変える段の義務で照らす）、`remove` は義務でない許し。この 2 つを 1 つの語に混ぜない。
  - 前の型の物を引く（第 5 版で足した。付録 A の F12・F13・F26 の前半の代わりの照らし）: 組の子の頭は、同じ組で前に返した型の `evidence.added`・`evidence.rewritten` の試験と、tdd が凍らせたファイルを、どの行の許しからも引いてから `permits` を書く。前の型が義務を果たした試験を、後の型が動かし直せない（今の `rules.py:250` が名指しから輪の確かめた書き換えを外すのと同じ向き）。引いた物は返しの `evidence` に前の型の物として残るので、最後の承認はどちらの型が書いたかを読める。
  - 裁定の行 `ruled` の例外: その裁定が出た時より前に返した型の物だけは、裁定の範囲の中で引かない（裁定がそれを見て許したので）。裁定より後に返した型の物は、古い裁定の範囲でも引いたままにする（今の `facts.py:146-159` の `_now_rulings`・`frozen_tests` の「事後の関門は裁定の範囲を許すのに、今の輪の凍結は解かない」の形を、許しの 1 本で言い直した物。古い裁定の範囲で、後の輪が凍らせたファイルを書き換えられる弱める向きを作らない）。機械がこれを yes/no で決められるように、裁定の控えと型の返しの両方に、組の中の順の番を持たせる。
- `base`: 起点。run の修正前の版（`board.base_rev_of`。`board.py:1801`）と、組の子の頭で 1 度取った関わる試験の元の結末。どの型も同じ起点で結末を比べる（2.4 の赤緑と同じ結果の照らし）。下ごしらえ（3.6）を挟んだ時は、下ごしらえが足した試験を起点の木で走らせた結末もここに入る。
- `since`: 差分の起点（第 5 版で足した）。同じ組で前に返した型の `tree`。組の最初の型なら `base` の版と同じ。共通の受け付けは「どの型の変更か」を、`since` から返しの `tree` までの差分で照らす（2.3 の 1・3・4）。結末を比べる起点（`base`）とは別の物で、`base` を段ごとに変えない（7 章の `stage-tree-not-run-base`）。今の修正役の受け付けが、凍結の印 `frozen_tree` から後の分だけで外れと余分を見る形（`facts.py:162` の `check_plan_scope` の docstring）を、型を問わない欄にした物。欠けの照らし（直すと言ったファイルが変わっていない）は今と同じく `base` からの差分の全部で見る。
- `run`: 試験の走らせ方（test_cmd・実行器）と、当たる試験の選び方の結果。
- `asks_answered`: 前の周の申し出への答え（範囲の相談の答え・裁定）。
- `why_untested`: static の注文だけが持つ、計画が試験を求めない訳（計画の項目の `route_why`）。

型ごとの欄は `orders.<weapon>` に入れる（例: TDD の受け入れの試験の名指しと整えの申告・remove の消す名の並び・static の変えてよい種類・rebuild の比べる境目）。共通の受け付けはこの欄を読まない。

### 2.2 返し（返す物）

- `status`: `done`（全部の単位を直した）・`parked`（申し出を積んで止めた）・`gave_up`（3 回の却下で諦めた。訳を添える）。
- `tree`: 返した時の作業ツリーの木の hash。型の差分は注文の `since` からこの木までで、型は自分で差分を書かない。
- `changes`: 単位ごとの変更の行 `{unit, files, what}` と、閉じの証明の欄（`closure`・`coverage`・`root_or_symptom`・`bypass_tried`・`breaks`・`precedent`。今の修正役の返答の形のまま）。型が自分で書く。ほかの役に写させない（1.2 の 1・2 をやめる）。
- 周の全体の欄: `not_done`・`interactions`・`plan_faces`・`wrote_refs`・`rejudge_requested`・差分の形の申告。今の修正役の返答の形のまま。
- `evidence`: 確かめの証拠。どの型も同じ欄で、使わない欄は空。
  - `named`: 型が名指した試験（TDD の受け入れの試験・variant が後から足した試験など）。
  - `before`・`after`: 名指しと関わる試験の、起点と返した木での結末（JUnit の結末から機械が作る）。
  - `added`・`rewritten`・`removed`: 足した・書き換えた・関数ごと消した試験の id。型の申告で、共通の受け付けが木の比べで照らし直す。
  - `sites`: 同じ決まりを共有する所ごとの、戻して赤・直して緑の記録（variant が使う。3.2）。下ごしらえ（`pin`）は、足した試験が縛るコードを壊して足した試験が赤になる記録に使う（3.6）。
  - `kinds`: 種類ごとの確かめの記録。行ごとに種類・したこと（走らせた命令と結果・引いた名）。どの型も、差分が試験の外の種類（文書・指示・設定・注記と型）に触れたら書く。どの型の書き手にも、共通の断片 `writer-rules.md` の種類ごとの確かめ（付録 A の W12・W16〜W19）が触るパスの種類で載るので（今と同じ。`workflows/fix/src/prompts.py:70-72`・`rules.py:126`）、tdd や variant の直しが文書も一緒に直す時もここに書く。書き先がこの 1 つにまとまるので、役ごとの書き先の段落（W13・W14）は要らなくなる。行の在る無しを型の義務で照らすのは static だけ（3.7 の確かめの 4）で、ほかの型では最後の承認で人が読む（今の `closure.verified_how` と同じ扱い）。
  - `compared`: 新旧を同じ入力で比べた記録（rebuild が使う。3.5）。入力の id ごとに、古い経路と新しい経路の出力の hash と、比べから除いた揺れの印。形は言語を問わない JSON の行（E13）。
- `asks`: 食い違いの申し出と範囲の相談の行（今の `lib/conflict.py` と相談の形のまま）。
- `report`: 報告に載せる日本語の行。

### 2.3 共通の受け付け（型の中身を知らない機械）

返しが来たら、型の名を問わず同じ順で照らす。今の `accept_reply`・`gates.py`・`assert_changed.py`・`recount.py` の照らしのうち、型を問わない物をここに集める（1.4.3 の 1。指示の項目は付録 A の行き先「共通」）。

1. 範囲: `since` から `tree` までに変わったパスが `scope` の中か（今の `scope.py`）。外なら範囲の相談に積む（今の overflow）。
2. 書き込みの出どころ: 書いたのが役の Edit・Write か（今の `lib/writes.py`。keep-essence の 5）。
3. 試験の変更: `since` の木と返した木の試験の関数を比べ、変わった・消えた関数がどれも `permits` の行の中か（今の `gates.py` の `test_edits`。許しは注文の `permits` だけを読む）。消えた関数の集まりは機械が出し、`evidence.removed` の申告と合うかも照らす。
4. 申告したファイルが本当に変わったか（今の `assert_changed.py`）と、単位の行がそろうか（今の duplicate・not_opened・excused）。
5. 当たる試験: 変更に直に関わる試験を走らせ、元で赤でなかった試験の赤を拒む（今の tests。keep-essence の 6）。
6. 閉じの証明の形: 今の copy の照らし（`recount.py` の `_reply_shape_problems`・`ref_problems`）と、`class_query` の在る単位の数え直し（keep-essence の 7）。今と同じく全部の行に当てる。ただし「赤を見ない clean を拒む」（付録 A の F135）は variant の型の義務に移す。
7. 申し出・審査の前読みの穴への答え・範囲の相談（今の conflict・plan_faces・consult）。
8. 義務: 2.4 の表で、型の名から箱と型の義務を引いて `evidence` に当てる。

この機械は `orders.<weapon>` も型の状態のファイルも読まない。型の名で枝分かれするのは 8 の表引きの 1 か所だけ。

### 2.4 確かめの表（箱の共通の義務 + 型の義務の 2 層）

どれも yes/no で、機械が JUnit の結末と木の比べと `evidence` の行だけで決める（憲法の 6）。

表の形の決まり:

- 型の義務は、箱の義務で出た問題の並びに問題を足すことしかできない。受け付けは「箱の義務の問題 + 型の義務の問題」が空の時だけ通す。型の義務の関数は箱の義務の結果を受け取らない（例外を書く口が API に無い。憲法の 6）。
- 型の名から箱を引く表と、箱と型の義務の関数の表は、同じ 1 つのモジュールに置く（今の `board.py` と `tdd.py` に散る照らしを集める）。
- 2 つの箱や型が同じ照らしを使う時は、同じ関数を呼ぶ（写さない）。

全部の箱に共通（どの箱にも入る、今の受け付けの照らし）:

- 返した木で居なくなった試験は、どれも `permits` の中にあり `evidence.removed` に名がある（今の `lib/baseline_red.py:121-143` は居なくなった試験を見ないので、ここで足す）。

箱の義務:

- 変える段 `change`: 変えた動きを試験か機械で示す。機械の照らしは「`evidence.named` に 1 つ以上の試験があり、どれも起点の木で failure（赤）・返した木で通る（緑）」。義務の `rewrite` の許しの試験も、書き換わって赤から緑になる。そのうえで、起点で通っていた関わる試験は、`permits` の中の物を除いて返した木でも通る。
- 変えない段 `keep`: 前に通っていた試験が直した後も同じ結果。機械の照らしは「関わる試験の結末の並びが、起点と返した木で同じ（通っていた物が全部通り、居なくなった物が `permits` の `remove` の中の物だけ）」（以下「同じ結果の照らし」）。既存の試験は変えない（許しが名指した物だけ例外）。足してよい試験は、起点の木で通る試験だけ（Feathers の characterization test。赤を求めない）。
- 段の外 `outside`: 箱の義務は持たない。箱に入る型が static の 1 本だけなので、照らしは全部 static の型の義務に書く。

型の義務:

- `tdd`: 名指しの試験が、単位の頭（直す前の木）で赤になったことを輪の中で確かめた記録がある（先に赤。箱の義務の「起点で赤」より強く、書く順を縛る）。`remove` の許しは使わない（消す依頼は remove に回す。3.3）。
- `variant`: 次の 2 つ（付録 A の F123・F135 を機械の照らしに上げた物）。
  1. `class_query` の在る単位は、`evidence.sites` に 1 行以上あり、どの行も `path` を持つ。
  2. 単位ごとに、`evidence.sites` のどれかに赤を見た記録がある（今の「赤を見ない clean を拒む」を、周の全体から単位ごとに直した物。今は同じ周の別の単位の赤で通ってしまう。1.5 の 3）。
  - 箱の義務の「名指しの試験が起点で赤・返した木で緑」は、直した後に足した試験で満たしてよい（後から足す試験。起点の木での赤は機械が走らせて確かめる）。
- `remove`: 注文の消す名の定義が返した木で引けない（`planmarks.line_in` と `file_symbols` の機械の照らし）。消した試験は `remove` か `rewrite` の許しの中。変える段の「名指しの試験が赤から緑」は、消す名を使う呼び手の振る舞いが変わる試験（`rewrite`）で満たす。消えたことだけを縛る試験は名指しに数えない（3.3）。
- `static`: 3.7 の 4 つ。
- `tidy`: 型の義務は足さない（箱の義務だけ）。
- `pin`（下ごしらえ。型ではない段。3.6）: 次の 3 つ。単独で頼んだ時も、ほかの型の前に挟んだ時も同じ（第 5 版で、第 4 版の型 `pin` の 2 つと、第 3 版の下ごしらえの 1 つを合わせた）。
  1. 差分は試験のファイルだけで、`evidence.added` が 1 つ以上ある（足した試験が起点の木で通ることは箱の義務が照らす）。
  2. 足した試験が、起点の木で 2 回走らせて 2 回とも通る（揺れる出力を除けていない試験を落とす）。
  3. 足した試験ごとに、`evidence.sites` に、その試験が縛るコードを壊すと赤・戻すと緑の記録がある。
- `rebuild`: `orders.rebuild` の境目について、`evidence.compared` の行が 1 つ以上あり、揺れの印の無いどの行でも古い経路と新しい経路の出力の hash が同じ。

TDD の refactor の段は、変えない段の義務と同じ照らしを使う（段の確かめを TDD の中に別に持たない）。`refactor-same` の「修正役が緑の後に同じ会話で整え（整える段に別の役を立てない）、緑のままかを機械が 1 回確かめる」はそのまま保つ。

variant の「起点の木で赤」と下ごしらえの「起点の木で 2 回通る」を確かめる走らせは、持ち主の決め `base-runs-nothing`（run の始めには試験を何も走らせない）に当たらない。走らせるのは直した後（下ごしらえは試験を足した後）に、名指しの試験か足した試験だけを起点の木で走らせる形で、`base-runs-nothing` が残す「元の結末に無い赤だけを、直す前の版で同じ走らせ方を 1 回して分ける」と同じ形。

## 3 場面の軸と型ごとの中身

### 3.0 場面の軸（持ち主の答え 2026-10-24 の 4・2026-10-25 の 5）

直す場面を 6 つの軸で見る。軸 1〜5 の出どころは材料のノート（場面と直し方）の「軸と原典の表」。軸を一覧にした原典は無く、並べたのは材料のノートの読み。軸 6 は第 3 版で、持ち主の言葉「テストが物理的に必要ない修正もある」から足した。

1. 振る舞いを変えるか（変えない・変える）: 変える段と変えない段の分け（2.0）。
2. 直す所を縛る試験が在り、走らせられるか（在って走る・無い・走らない）: 無ければ下ごしらえ（3.6）を挟める。走らせる道そのものが無い時は 9.2 の 1。直しの種類でなく対象のリポジトリの事情で決まる（1.4.1 の (b)）。
3. 変更の大きさ（小さく積める・まとめて書き換える）: 変える段の tdd と、変えない段の tidy と rebuild を分ける。
4. 新旧を共存させて段階的に移せるか（両方の経路を呼べる・呼べない）: rebuild の前提（3.5）。
5. 利用者に見える境目（公開 API・データ）を越えるか（越えない・越える）: 機能を消す依頼の置き場（remove か tidy か。3.3）と、rebuild で古い経路を消すか（9.2 の 2）を分ける。
6. 直しが試験で示せる種類か（示せる・示す物が無い）: 示す物が無い直し（文書・コメント・設定の値・指示の md の言い回し・CI の設定）は段の外の static（3.7）。直しの種類で決まる（1.4.1 の (a)）。軸 2 とは別の軸で、軸 2 は「示す物は在るのに道具が無い」。

この設計は、型ごとに「どの軸の値を前提にするか」と「前提が崩れた時に型が何を返すか」だけを描く。軸の値から型を選ぶ決め方は描かない（範囲）。

### 3.1 tdd（変える段）

- 前提: 軸 1 が変える・軸 3 が小さく積める・軸 6 が示せる。直す所の試験の走らせ方が在る（試験そのものが無ければ輪が書く）。
- 受け取る: 共通の注文と、`orders.tdd` の受け入れの試験の名指し・整えの申告。
- やる: 今の輪の test・fix・refactor の段。
- 返す: 単位ごとの `changes`（閉じの証明の欄を含む）と `evidence`。今は修正役が `changes` に写していた行を、輪が自分で書く。
- 閉じの証明の欄（第 3 版で足した。1.4.3 の響き）: 今の受け付けは TDD の単位の行にも根か症状か・破りに行った形跡・壊しうる面・先行例を求め、修正役が後から書いている。輪が自分で `changes` を書くので、fix の段の返答にこれらの欄を足し、同じ照らし（2.3 の 6）を通す。今 TDD の役が `what` に書いて修正役が写している物（`parts/tdd.md:45`）を、欄に書く形に替えるだけで、役の仕事は増えない。`closure.sites` と赤を見る証明（variant の型の義務）は求めない。tdd の赤は「先に赤」の義務が示す。
- 輪から出ていく物（持ち主の問い「TDD の loop がややこしかった。切り出すことですっきりするか」への答え）: 輪は赤 → 緑 → 整えの手順だけを持ち、次の 5 つを外へ出す。
  1. 振り分けの段（route）: 組の子の頭の前へ（10 章の 1）。
  2. 別の型への 4 つの道（1.2 の 5。`_to_direct`）: 輪は「tdd の義務を満たせない」を `status: gave_up` と訳で返すだけにし、次の型の注文を書くのは組の子の頭（4.1 の 3）。
  3. 許しの読み（1.2 の 4）: `planmarks.unit_contract` を読まず、注文の `permits` だけを読む。段ごとの許しの違いは、共通の受け付けの 1 つの照らし（2.3 の 3）に寄る。
  4. 修正役への指示文（1.2 の 2。`FIXED_HEAD`・`DIRECT_HEAD`）: 輪が自分で `changes` を書くので要らない。
  5. 修正役の受け付けへの部品の貸し（1.2 の 6）: 共通のモジュールへ。
  - 残る物: 単位ごとの赤の照らし（`red_check`）・凍結・3 回の却下の数え・整えの段。整えの確かめは変えない段の義務の関数を呼ぶ。
- 消す名の許し: 読まない。消す依頼を tdd の輪で通すために段ごとの例外を足す形（run 19268881 の第 3 版の項目 1）は採らない。採ると 7 章の 1 群の穴がそのまま残る。

### 3.2 variant（変える段。今の direct の核。第 3 版で名を付けた）

- 中身（1.4.3 の 3）: 1 つの欠陥を種にして、同じ決まりを共有する所を全部挙げ、全部を直し、1 か所ずつ退行を注入して赤を見て、戻して緑を見る。判定の `class_query` を機械が修正の前と後で数え直す（共通の受け付け）ので、型は「数が減った」の手前の「1 か所ずつ確かに効いている」を示す。
- 入った訳（第 4 版で足した。付録 A）: 1 か所ずつの証明（F123）は、元の graphloops の修正の段で「入口 2 つのうち 1 つしか塞がない直しが 3 回続いた」実測から入った。破りに行った形跡（F130。共通）は「直しを外すと赤」は不在の検知で完全さの証拠でない、という実測（全文一致を狭めた直しが改行 1 つで破れた）から入った。項目ごとに新しい会話の子を起こす回し方（F101）は、会話が積もって修正役が 86 分かかり文脈が尽きたことから入った（持ち主の決め `unit-sessions`）。
- 記録の手本（1.5 の 4）: run 6cc154f6 の 1 単位。同じ欠陥の形の 3 か所を 1 か所ずつ壊して対象の試験の実行器で赤を見て、戻して緑を見た。
- 名の決め: `variant`。比べた候補と訳:
  - 中心の手順は、セキュリティの variant analysis（既知の欠陥を種にして、同じ形の問題を問いで探す。CodeQL の文書・Google Project Zero）と同じ形をしている。判定の `class_query` は、欠陥の形を機械の問いにした物で、CodeQL の問いと同じ役をする。Project Zero は 2022 年の実際に悪用された 0-day の半分ほどが前に直した欠陥の変種で、根本からの包括的な直しと退行の試験で防げたと書く。直した 1 か所だけでなく変種まで閉じる、がこの型の訳と重なる。
  - 1 か所ずつ戻して赤を見る証明は、mutation testing（コードをわざと壊して、試験が気付くかを見る。気付けば mutant を kill した）の形。ただし mutation testing は試験の一式の質を測る道具で、直し方の名ではないので、型の名にしない（手順の中の証明の名として 5 章に置く）。
  - 窓口の見立ての候補 `sweep`（掃き出し）は、全部を探すことは言えるが、1 か所ずつの証明を言えず、定着した技術の語でもない。`root-close` は、返しの `root_or_symptom` で症状の直しも訳付きで許す今の形と食い違い（型の名が「いつも根を閉じる」と約束してしまう）、造語でもある。
  - Google の大規模変更（LSC）は、多くの所を機械で書き換える点が近いが、中身はほぼ振る舞いを変えない書き換えで、道具で作り、境界で分けて別々に試験する。変える段の型の名には合わない（5 章。むしろ tidy の側）。
- 箱の置き場（第 2 版の direct の決めを受け継ぐ）: 変える段に置く。
  - 訳 1: 今 direct が「振る舞いを変えない直し」に使われるのは、変えない段の型が無いための逃げ道だった（run 19268881 の第 3 版の項目 3 の形。1.3 の run 20447be2。計画が direct に回した 15 件のうち 7 件が振る舞いを変えない直しだった。1.5 の 2・3）。tidy を作り下ごしらえを単独で頼めるようにすれば、その直しは tidy か下ごしらえの注文になる（第 5 版）。
  - 訳 2: 試験で示す物が無い直し（1.4.1 の (a)）は static（3.7）に出したので、variant に残るのは振る舞いを変える直しだけになる。
  - 訳 3: 2 つの箱に置くと、型の名から箱が 1 つに決まらず、2.0 の決まりが崩れる。
- 前提: 軸 1 が変える・軸 6 が示せる。tdd の「先に赤」を踏まない時（先に赤を書けない・輪が上限に届いた・範囲の裁定の後・仕様の道で仕様の書き手が TDD に名指さなかった。1.4.1 の (c)・(d)）に、変えた動きを後から足した試験で示す。
- 受け取る: 共通の注文だけ。
- やる: 今の修正役の直し（付録 A の F101〜F106・F123 と共通の手順）。項目ごとに実装の子を起こし、差分を審査の子に読ませ、3 回まで直させる（superpowers の subagent-driven-development を借りた今の形のまま）。直した後に、変えた動きを縛る試験を名指す（足すか、`rewrite` の許しの試験を書き換える）。TDD で直した単位を見ない。
- 返す: 単位ごとの `changes`（閉じの証明の欄を含む）と `evidence`（`named` は直した後に足した・書き換えた試験、`sites` は 1 か所ずつの赤緑）。
- 今と変わる所: TDD の後にいつも起きる形をやめ、variant の注文が在る時だけ起きる。修正役の指示から TDD の要約（`FIXED_HEAD`・`DIRECT_HEAD`）を外す。今は閉じの証明の自己申告だけで通る direct の単位が、変える段の義務（名指しの試験が起点で赤・返した木で緑）を負う。種類ごとの確かめ（付録 A の W12・W16〜W19）は指示から外さない。共通の断片として、今と同じく触るパスの種類で載り、書き先は返しの `evidence.kinds`（2.2）にまとまる（第 4 版は「static に移す」と書いたが、指示の実物と食い違っていたので第 5 版で直した。1.4.3 の 4・4.3）。借りた型の段落（`seat_one`。付録 A の F108・F148b）は、下請けを起こさない周だけに載る物で、variant はいつも下請けを起こすので載らない。
- 逃げ道の向き: tdd → variant は同じ箱の中の書き直しで、組の子の頭がする。変えない段の型（tidy・rebuild）や下ごしらえや static が諦めた時に variant へ回すことはしない（箱を越えない。2.0）。
- 試験を走らせる道が無い時（今の「実行器が走らない」で全部を direct にする道。1.4.1 の (b)）: 変える段の義務を誰も満たせない。どうするかは 9.2 の 1。
- 機械の照らしに上げる余地（10 章の 9）: 1 か所ずつの赤は今は役の申告。直しの hunk を 1 つずつ戻して名指しの試験が赤になるかを機械が走らせれば、申告でなく yes/no の照らしになる。

### 3.3 remove（変える段）

- 前提: 軸 1 が変える・軸 5 が越える（利用者が使える機能を消す）。利用者から届かない、使われていないコードを消すのは tidy（3.4）。材料のノート（変更の種類）の読みで、機能の削除をどちらの箱に入れるかは「誰から見て届くか」で割れる（SemVer と Conventional Commits の破壊的変更・Tidy First? の整理）。
- 受け取る: 共通の注文と、`orders.remove` の消す物の並び（`change=remove` の名・`op=delete` のパス・`op=rename` の元）。`permits` には消す名を使う試験の `remove` の行が入る。
- やる: 消す物と、それを縛る試験を消す。消す物を使う残りのコードを直す。新しい振る舞いへの書き換えはしない。「X を消して振る舞いの違う Y に替える」依頼は、消す項目と足す項目（tdd）の 2 つにし、足す項目が `depends_on` で消す項目を待つ（計画の欄 `depends_on` は今在る）。
- 確かめ: 2.4 の変える段と `remove`。消えたことを縛る試験を書かせない（superpowers の `writing-good-tests.md:192` が悪い兆しとする「消した名が無いことを確かめる試験」）。消えたことは機械が木で照らす。
- 最後の承認: `evidence.removed` を受け付けが照らした集まりから、「消した試験」の節を id で並べる。「書き換えを許したテストを触った」の節には入れない。
- 今の形との違い: 今は消す依頼を tdd か direct のどちらかが別の型の都合で抱える。remove を立てると、消す依頼の確かめが 1 か所にまとまる。
- 箱の義務との合わせ目（10 章の 3）: 消す名を使う呼び手が無く、`rewrite` の試験が 1 つも無い消し（機能だけを消して誰も呼んでいない）では、変える段の「名指しの試験が赤から緑」を満たす試験が無い。

### 3.4 tidy（変えない段。小さな書き直し）

- 前提: 軸 1 が変えない・軸 3 が小さく積める。使われていないコードの削除を含む（Beck の Tidy First? の整理に入る）。
- 受け取る: 共通の注文と、`orders.tidy` の保つ振る舞いの説明（何を変えずに何の形を変えるか）。
- やる: 書き直す。保つ振る舞いを縛る試験が足りなければ、先に下ごしらえ（3.6）を挟む（tidy の中に試験を足す段を持たない）。
- 確かめ: 2.4 の変えない段の義務だけ。
- 今の形とのつながり: TDD の refactor の段と照らしを分け合う（2.4）。`refactor-same` は「TDD の中の整え」の決めで、整えだけの単位の型はこの決めに当たらない。
- 使われていないコードを縛っていた試験: その試験を消すのは `remove` の許しで、2.4 の変えない段の義務は `permits` の `remove` の中の試験が居なくなるのを認める。許しを出すのは計画の `change=remove` の元（今の `_naming_removes`）で、tidy の中に別の許しの道を作らない。
- 届くか（第 4 版で直した）: 第 3 版は「今の判定は欠陥の形の無い単位を作らない（`judge.py:268-272`・`exit.py:90`。案の項目も単位を 1 つ以上要る。`planmarks.py:153-155`）ので、どの run も tidy に届かない」とした。記録はこれと違った。判定は「守る対象の無い検査が残る」を欠陥の形（残った名を数える `class_query`）にして単位を作り、計画は route=direct と「消すだけの直しで新しい振る舞いが無く、先に落ちる受け入れのテストを書けない」の訳で修正に回していた（run 82d22f4f・806536fc。1.5 の 3）。欠陥の形を持つ単位として届く、使われていない物を消す直しは、今も tidy に届く。届かないのは、欠陥の形を持たない書き直し（構造だけを良くする依頼）で、こちらは第 3 版の訳のまま判定の単位の決めを見直す時まで届かない。
- 段 1 で作るか（第 5 版で決めた）: 作る。作る範囲は、欠陥の形を持つ単位として届く「使われていない物を消す」直しまで。持ち主の向き（9.1 の 7）に沿い、記録の 2 件（1.5 の 3）を新しい型で受けず、第 2 版から在る tidy に寄せた。持ち主の答え（9.1 の 2）の「口の形だけを今決める」は、どの run も届かないという第 3 版の見立ての上の答えで、届くのは欠陥の形を持つ消しだけなので、欠陥の形を持たない書き直しの tidy と rebuild には 9.1 の 2 のまま当てる。
- 寄せられるかの確かめ（第 5 版）: 寄せられない訳は無かった。
  - 中身: 記録の 2 件の直し（守る対象の無い検査の試験・CI の段・環境の変数を消す）は、3.4 の前提（振る舞いを変えない・小さく積める・使われていないコードの削除を含む）にそのまま入る。新しい手順は要らない。
  - 確かめ: 箱の義務（同じ結果の照らし。居なくなった試験は `remove` の許しの中だけ）で照らせる。消した試験の許しは計画の `change=remove` から出る（上の「使われていないコードを縛っていた試験」）。
  - 閉じの証明の欄（下の合わせ目）: この 2 件は欠陥の形（残った名を数える `class_query`。run 806536fc で修正の前 18・後 0）を持つので、根か症状か・破りに行った形跡が、欠陥を直す行として今と同じに書ける。合わせ目が残るのは欠陥の形を持たない書き直しだけ。
  - remove との見分け: 2 件の計画は消す名に `change=remove` を付けていたので、「消す名の在る項目は remove」（4.1 の 3 の第 4 版までの表）だけでは remove に回ってしまう。利用者から届くか（軸 5）を計画が route の語 `tidy` で言う（9.2 の 3）。
  - rebuild とは重ならない: rebuild は境目で新旧を比べる大きな作り直しで、消すだけの直しは持たない。
- 閉じの証明の欄との合わせ目（10 章の 10）: 共通の受け付けは今と同じく全部の行に根か症状か・破りに行った形跡を求める（2.3 の 6）。段 1 で作る欠陥の形を持つ消しの tidy には合う（上の確かめ）。欠陥を直さない書き直しの tidy の行にこれらが合うかは、その tidy を作る時に詰める。

### 3.5 rebuild（変えない段。大きな作り直し）

- 前提: 軸 1 が変えない・軸 3 がまとめて書き換える・軸 4 が両方の経路を呼べる。中は細かく試験せず、外側の境目で新旧を同じ入力で比べる。
- 受け取る: 共通の注文と、`orders.rebuild` の比べる境目（新旧を呼び分ける入口の名と、入力の集め方）。
- やる:
  1. 境目の内側に新しい経路を作り、古い経路を残したまま、境目から両方を呼べるようにする（Branch by Abstraction の抽象化の層）。
  2. 同じ入力を両方に投げ、出力を比べた記録を `evidence.compared` に書く（Scientist の比べ。揺れる出力は除いた印を付ける）。
  3. 比べが通ったら古い経路を消す（9.2 の 2）。
- 確かめ: 2.4 の変えない段と `rebuild`。境目の外の試験は箱の義務で同じ結果、境目の中は比べの記録で照らす。
- 前提が崩れた時: 両方の経路を呼べない（副作用のある処理・外の状態・データの移し替え）なら、比べの記録を書けず `rebuild` の義務を満たせない。`status: gave_up` と訳を返し、組の子の頭は変える段の型へ回さない（箱を越えない。2.0）。申し出として裁定に回る（keep-essence の 4）。
- 届かない訳: 欠陥の形を持たない大きな作り直しは、判定の単位の決めを見直すまで届かない（3.4 の後半）。記録にも届いた run は無い。口の形だけを今決める。

### 3.6 下ごしらえ（型ではない段。機械の名 `pin`。どの型の前にも挟め、単独でも頼める。第 5 版で第 4 版の型 pin を寄せた）

- やる: 直す所の今の振る舞いを試験で固める（characterization test・golden master・approval testing）。望む振る舞いでなく、今の振る舞いを記録する。足した試験ごとに、その試験が縛るコードを壊すと足した試験が赤になり、戻すと緑になることを見せ、`evidence.sites` に書く（記録の run fec72aa1 の修正役は、条件の式を壊すと足した試験だけが赤になることを見せた）。コードは変えない。コードを変える要る物が在るなら、それは別の型の直しで、下ごしらえの注文が誤っている。申し出にする。
- 2 つの頼まれ方:
  1. 挟む: 別の型の前に、組の子の頭が挟む。注文の `units` は後の型の単位で、下ごしらえ自身は直す欠陥を持たない。足した試験は後の型の注文の `base` の関わる試験に入り、後の型の箱の義務がそのまま照らす。いつ挟むかは軸 2 で決まるが、決め方は描かない（範囲）。
  2. 単独: 判定の単位の欠陥が「欠陥を捕まえる試験が無い」ことだけの時（コードは正しい。1.5 の 2）、計画が route の語 `pin` で名指す（9.2 の 3）。注文の `units` はその単位で、`orders.pin` に留める振る舞い（どの欠陥を捕まえる試験を足すか。判定の単位の `reason` から組の子の頭が写す）を書く。下ごしらえが返したら、その単位の直しは終わる。記録では、計画が route=direct と「今のコードは正しく保存を断るので、足すテストは今も緑で赤から始められない（欠陥はテストの欠けだけ）」の訳で修正に回した 5 件（run fec72aa1 など。同じ依頼の回し直し）がこれに当たる。
- 受け取る: 共通の注文（2.1。`weapon` は `pin`）。`permits` は空（既存の試験を変えない）。
- 確かめ: 2.4 の変えない段の箱の義務と、`pin` の 3 つ（差分は試験だけ・起点の木で 2 回通る・足した試験ごとに壊して赤）。2 回通るのは、揺れる出力を除けていない試験を落とすため（golden master の記事の「揺れる出力は Printer が除く」に当たる）。壊して赤の証明は、variant の 1 か所ずつの証明（F123）と同じ手順で、記録の書き方も同じ `evidence.sites`。機械の照らしに上げる道（10 章の 9）も variant と同じ関数を使う。挟む時も単独の時も同じ確かめで、頼まれ方で枝分かれしない。
- 型にしない訳: 型は直す物（コード・文書・設定）を持つ直し方で、下ごしらえは試験を足すだけで何も直さない。挟む時は後の型の前の段にすぎず、型の数に入れると、型を選ぶ表（4.1 の 3）に「ほかの型の前に挟まる型」という別の種類が混ざる。第 3 版の訳「型にすると、変える段の型の前に挟む時に箱が 2 つ混ざる」は、第 5 版で下ごしらえが自分の注文と返しを持ち、後の型と別に共通の受け付けを通すので、箱が混ざらなくなった（下ごしらえは `keep`、後の型はその型の箱で、別々に照らす）。
- 第 4 版の型 pin を寄せた訳（持ち主の向き。9.1 の 7）: 第 4 版の pin と下ごしらえは、手順（今の振る舞いを試験で固める）も箱（`keep`）も同じだった。違いは、試験を足すこと自体が依頼の目的になるか（pin）、別の型の前の段か（下ごしらえ）だけで、これは頼まれ方の違いにすぎない。寄せられない訳は無かった。寄せた時に 1 つ足した物: 第 3 版の下ごしらえは「壊して赤」を求めず、第 4 版の pin は「2 回通る」を求めなかった。合わせて、両方をどちらの頼まれ方にも求める。挟む時に壊して赤を求めるのは、後の型を守る試験が本当に何かを縛っているかを示すため（縛らない試験は後の型の箱の義務を素通りさせる）。
- 名の決め: 機械の名は `pin`（第 4 版の型 pin の名の訳を受け継ぐ）。Feathers は、今在る振る舞いを「pin down」するために characterization test を書く、と言う（Working Effectively with Legacy Code の 11 章。https://www.oreilly.com/library/view/working-effectively-with/0131177052/ch11.html）。下ごしらえは今の振る舞いを試験で留めるので、その動詞を名にした。「pinning test」を characterization test と別の種類として定めた一次情報は見つからないので、名は動詞から採ったと書くにとどめる。`characterize` は、第 4 版で「今の振る舞いが正しいかを問わない記録の意味が強く、欠陥を捕まえる証明を言わない」として採らなかった。第 5 版で壊して赤の証明を下ごしらえの確かめに入れたので、`pin` のままにする。backfill は定着した技術の語でないので採らない。日本語の名は下ごしらえのまま。
- 試験を走らせる道そのものが無い時は、下ごしらえの前に走らせ方を作る話になる（9.2 の 1）。

### 3.7 static（段の外。試験が要らない直し。第 3 版で足した）

- 受け持つ物: 1.4.1 の (a) だけ。文書・README・コメント・設定の値・AI のノードへの指示の md の言い回し・CI の設定など、直しの種類から試験で照らす振る舞いが無い直し。(b)（試験が書けない・走らない）は受け持たない（9.2 の 1）。
- 名の決め: `static`。確かめが試験を走らせることでなく、静的な確かめ（名とリンクが引ける・指示を組める・設定の検証が通る・静的な検査が通る。付録 A の W12・W16〜W19）だから。tdd が「どう確かめるか」で名付いているのと並ぶ。Conventional Commits の `docs`・`ci`・`chore` は変更の種類の名で、確かめ方を言わないので型の名にしない。
- 別の型に置くか、variant に含めるかの決め: 別の型に置く。
  - 訳 1: variant は変える段に属し、名指しの試験の赤緑を負う。含めると、variant の中で「示す物が無ければ赤緑を求めない」の例外が要り、2.0 の決まりが崩れる。第 2 版の 3.2 が 1.4.1 の (a)（試験が要らない直し）を通せなかったのは、この形だった。
  - 訳 2: 今の direct の受け付けは、(a) の直しにも「赤を見ない clean を拒む」（付録 A の F135）を当てていて、(a) の直しは意味の無い赤を作るか `found` を名乗るしかない。記録の run 9006464c は、1 度拒まれた後に文書を古い文に戻して grep が当たるのを赤と呼んで通った（1.5 の 1）。拒否の文そのもの（付録 A の P2。`lib/recount.py:161-162`）が「found にして……書くか、退行を注入して赤を見てから出せ」と方法まで指示しているので、偽の赤はこの文に従った形だった。static を分ける時は、この文も variant の型の義務の拒否の文として書き直す（単位ごとの照らしに合わせ、static・tidy・下ごしらえには届かない）。分ければ、variant は赤を求め、static は求めない、とそれぞれ素直に書ける。
  - 訳 3: 分けても手順の写しは増えない。同じ形を全部探すこと（W2）と数え直し（keep-essence の 7）は共通の受け付けに在るので、文書の古い言い回しを全部直す、のような static の直しにもそのまま効く。
- 箱の決め: 2 段の外の箱 `outside` に置く。
  - 変える段に入れない訳: 変える段の義務（変えた動きを試験で示す）を満たせない。入れると箱の義務に例外が要る。
  - 変えない段に入れない訳: 変えない段は「観測できる振る舞いを変えない」（Fowler のリファクタリングの定義）を約束する箱で、static の直しの中には振る舞いを変える物がある（設定の値・CI の設定・AI のノードへの指示の言い回しは、それぞれ動く物の振る舞いを変える）。入れると、変えない段の約束が static の分だけ嘘になり、後で tidy・rebuild を作る時にその約束に頼れなくなる。照らしの関数は変えない段と同じ物を呼ぶ（下の 3）ので、別の箱にしても写しは増えない。
- 受け取る: 共通の注文と、`why_untested`（計画が試験を求めない訳）、`orders.static` の変えてよい種類（計画の項目の files から機械が `rules.kind_of` で引いた種類の集まり）。`permits` は空（試験を変えない）。
- やる: 直す。触った種類ごとに付録 A の W12・W16〜W19 の確かめ（どの型の書き手にも載る共通の断片。static だけの手順ではない）をして、`evidence.kinds` に書く。振る舞いを変える static の直し（設定の値・CI の設定・指示の言い回し）は、それを述べる文を全部直す（付録 A の W11a。共通）。試験を足さない・変えない（足す要る物が在るなら、それは試験で示せる直しで、static の注文が誤っている。申し出にする）。
- 確かめ（型の義務。どれも yes/no）:
  1. 注文に `why_untested` が在る（計画の側で 10 字以上を照らす。今の direct の `route_why` の照らし `planmarks.py:103` と同じ）。
  2. 差分が許した範囲に収まる: 共通の受け付けの範囲（2.3 の 1）に加え、差分の各パスの種類が注文の変えてよい種類の中。
  3. 前から通っていた試験が通る: 変えない段の「同じ結果の照らし」の関数を呼ぶ（写さない）。試験の関数の変更は 1 つも無い（`evidence.added`・`rewritten`・`removed` が空で、共通の受け付けの 2.3 の 3 の木の比べも空）。
  4. `evidence.kinds` に、差分の種類ごとに 1 行以上ある。中身の正しさは機械が照らせない（指示を組めるか・設定の検証が通るかは対象のリポジトリの道具に依る。E13）ので、行の在る無しだけを照らし、中身は最後の承認で人が読む。文書の名とリンクは共通の受け付け（2.3 の 6 の `ref_problems`）がもう照らしている。
- 最後の承認: 「試験を求めなかった直し」の節に分けて出す。項目ごとに、計画が試験を求めなかった訳・変えたファイルと種類・種類ごとの確かめの行。コードの種類のファイル（コメントや型の直し）は、コメントだけの変更かを機械が言語を問わずに見分けられない（E13）ので、ファイルの名に「コードのファイルを試験なしで変えた」の印を付けて並べる。
- 選ばれ方: 計画が名指す。名指し方は 9.2 の 3。

## 5 世の中の定石との比べ

- Beck の Tidy First?: 構造の変更（tidying）と振る舞いの変更を別の変更に分ける。整理の 1 つに使われていないコードの削除を挙げる（Henrik Warne の書評）。→ 2 段の分け（2.0）と、使われていないコードの削除を tidy に入れる形（3.4）に合う。TDD の中の整えの段は、振る舞いの変更の直後の小さな整えで、Beck の「後で整える」に当たる。
- Beck の Canon TDD（https://tidyfirst.substack.com/p/canon-tdd）: 一度に書く試験を 1 つに限り、「Mistake: mixing refactoring into making the test pass.」とする。→ tdd の型が小さく積む前提（3.1）。整えを緑の後に分ける今の輪の形のまま。
- Fowler のリファクタリングの定義: 観測できる振る舞いを変えずに内部の構造を変え、変換のたびに動く状態に保つ。確かめは既存の試験を前後で回して同じ結果になること。→ 変えない段の義務（2.4）そのもの。この約束があるので、振る舞いを変えうる設定や指示の直し（static）を変えない段に入れない（3.7）。
- Feathers の characterization test・golden master・approval testing（https://understandlegacycode.com/blog/characterization-tests-or-approval-tests/・https://codurance.com/2012/11/11/testing-legacy-code-with-golden-master/）: 「document your system's actual behavior; not to check for the behavior you wish your system had」。入力を投げて出力を記録し、直した後に比べる。揺れる出力は除く。→ 下ごしらえ（3.6）。第 5 版で、試験の欠けだけを埋める依頼も単独の下ごしらえで受ける（第 4 版の型 pin を寄せた）。TDD の「先に赤」の逆で、だから TDD の輪の段では書けない（1.3 の run 20447be2）。
- Fowler の Branch by Abstraction（https://martinfowler.com/bliki/BranchByAbstraction.html）: 呼び手と今の提供側の間に抽象化の層を置き、新しい提供側を試験の環境で動かして振る舞いを比べる。→ rebuild の手順 1（3.5）。
- GitHub の Scientist（https://github.com/github/scientist）と HEY の事例: 本番で両方を走らせ、現行の結果を返し、食い違いを記録する。比べは既定で `==`。「You need to make sure that invoking both paths is feasible, which is not always the case.」→ rebuild の手順 2 と前提（軸 4）。工場は本番を持たないので、比べは run の中で同じ入力を両方に投げる形にする。
- Fowler の Strangler Fig・Azure の文書・Spolsky: 段階の移し替えを勧め、単純な置き換えは「go down in flames most of the time」。旧システムへの要求を横取りできなければ合わないかもしれない。Spolsky は一からの書き直しを戒める。→ rebuild を「一から書く型」にせず、境目を残して新旧を比べる型にする（3.5）。工場の 1 つの run は数年にわたる移し替えを持てないので、Strangler Fig そのものは型にしない。
- Fowler の Parallel Change（https://martinfowler.com/bliki/ParallelChange.html）: 広げる・移す・縮めるの 3 段で、縮める段をやらないと始めより悪い状態に終わりうる。→ 利用者に見える境目を越える rebuild で古い経路を残すかの問い（9.2 の 2）。
- DHH の「TDD is dead」（https://dhh.dk/2014/tdd-is-dead-long-live-testing）: テスト先行が設計を損なう時があるとし、システムテストを重く見る。→ 持ち主の言葉「がっつりリアーキするときは TDD なんて細かくやるよりごっそりいったほうがいい」の側の原典。大きな作り直しに合わないとまでは書いていない（材料のノートの食い違いの節）。
- Google の大規模変更（https://abseil.io/resources/swe-book/html/ch22.html）: 大半は機能にほぼ影響しない書き換えで、機械で作り、境界で分けて別々に試験する。消した記号が再び入るのを防ぐ仕組みが要る。→ tidy の範囲。variant の名にしない訳（3.2）。消した名が再び入るのを防ぐ物は、この設計の外（工場は 1 つの依頼の直しまでを持つ）。
- variant analysis（CodeQL の文書 https://codeql.github.com/docs/codeql-overview/about-codeql/ ・GitHub の multi-repository variant analysis の告知 https://github.blog/security/vulnerability-research/multi-repository-variant-analysis-a-powerful-new-way-to-perform-security-research-across-github/ ）: 既知の欠陥を種にして、同じ形の問題を問いで探す。問いは論理の変種も拾い、欠陥の類を一度に見つける。→ variant の中心の手順と名（3.2）。判定の `class_query` が問いの役をする。
- Google Project Zero「2022 0-day In-the-Wild Exploitation…so far」（https://projectzero.google/2022/06/2022-0-day-in-wild-exploitationso-far.html）: 2022 年前半に実際に悪用された 0-day 18 件のうち少なくとも 9 件が、前に直した欠陥の変種で、その半分以上はもっと包括的な直しと退行の試験で防げたとする。根本原因の分析と variant analysis を勧める。→ variant が直した 1 か所で止めず変種まで閉じる訳。退行の試験は 1 か所ずつ戻して赤を見る証明の側。
- mutation testing（https://en.wikipedia.org/wiki/Mutation_testing）: コードを小さく壊した版（mutant）を作り、試験の一式がそれを落とせば kill。試験の質を測る。→ variant の 1 か所ずつ退行を注入して赤を見る証明（付録 A の F123）と、下ごしらえ（`pin`）の「コードを壊すと足した試験が赤」の証明（3.6）の形。工場の証明は直した所だけに当てる点で狭い。型の名にはしない（3.2）。
- Conventional Commits（https://www.conventionalcommits.org/）の型 `docs`・`ci`・`chore`ほか: 変更の種類の語で、確かめ方を言わない。→ static の名にしない訳（3.7）。種類の見分けは今の `rules.kind_of` が持つ。
- Cursor の報告（https://cursor.com/blog/reward-hacking-coding-benchmarks）: SWE-bench Pro で「63% of successful Opus 4.8 Max resolutions retrieved the fix rather than derived it」。git の履歴を封じて網を絞ると点が下がった。修正済みの実のバグから作った評価は特に弱い。→ 試験が通るだけでは証拠として弱い（10 章の 6）。
- superpowers 7.0.0 の test-driven-development（`lib/borrow/superpowers/7.0.0/skills/test-driven-development/`）: 「Always」に Refactoring を挙げる（`SKILL.md:17-21`）が、整えは「After green only」（`SKILL.md:195-201`）で、赤の無い整理の手順は無い。消した名が無いことを確かめる試験は悪い兆し（`writing-good-tests.md:192`）。→ TDD の型は今のまま superpowers に沿い、赤の無い直し方は別の型に出す。持ち主の問い「TDD でそれができるならいいけど」への答え: TDD の赤の義務を保ったままでは、消す依頼も書き直しの依頼も通らない。通すには TDD の段に例外を足すことになり、それが run 19268881 の 20 件の穴になった。
- superpowers 7.0.0 の subagent-driven-development（`lib/borrow/superpowers/7.0.0/skills/subagent-driven-development/` の `implementer-prompt.md`・`task-reviewer-prompt.md`）: 項目ごとに新しい実装の子を起こし、審査の子に読ませる。→ variant の中の回し方（付録 A の F101〜F106）。今の形のまま variant に残す。
- ASF の implement（`.archon/workflows/sdlc/implement/commands/implement.md`）: 直し方で役を分けず、1 つの実装役が計画・審査の指摘・CI の落ち・説明のどれでも受ける。試験は壊れうる所だけに書く（`implement.md:49`）。消しは頼まれた範囲の中だけで、置き換わった仕組みは消す（`implement.md:54`）。確かめは変えた所の当たる試験を回すこと。→ ASF は「型を分けず、結果を当たる試験で確かめる」側。工場は持ち主の決め `tdd` で赤緑の機械の判定を持つので、ASF の 1 本の形には寄せない。採るのは「確かめを直し方の手順でなく結果の照らしに置く」型（2.3 の共通の受け付け）。「試験は壊れうる所だけに書く」は static の「試験を求めない直し」と向きが同じ。
- ASF の simplify（`simplify/commands/simplify.md:3`）: 「求める結果を、要る以上の構造で届けている」を探す読むだけの審査。直す役ではない。→ 型の候補ではなく、型の後の差分の審査の側（delta-review・lens）の比べ相手。

## 7 run 19268881 の審査の指摘との照らし

   - 型を切った後: 第 3 版の型では通らない。variant は起点の木で名指しの試験の赤を求めるが、足した試験は起点の木で緑。static は試験を足させない。第 4 版は型 pin で通すとした。第 5 版は単独の下ごしらえ（3.6）で通す（B.3 の 2）。今の修正役がした「壊すと足した試験だけが赤」の証明が、そのまま下ごしらえの確かめになる。

3. 役目を終えた検査を消す直し（2 件。run 82d22f4f・806536fc。同じ依頼の回し直し。通った run 1 本）
   - 計画の訳: 「消すだけの直しで新しい振る舞いが無く、先に落ちる受け入れのテストを書けない」。計画の files は 3 つ（試験のファイル・CI の設定・コード）で、消す名に `change=remove` を付けていた。
   - 今の通り方（run 806536fc）: 判定の `class_query`（残った名を数える問い）が修正の前 18・後 0 に減った。sites は 3 行で、3 行とも赤を見ていない。`verified_how` は「名を grep して 0 件・CI の設定の検査が通る・関わる試験が緑」。受け付けは範囲で 2 度拒み、3 回目に通した。F135 は、同じ周の別の単位（振る舞いを変える直し）が赤を見ていたので通った（照らしが周の全体に 1 つの赤を見るだけのため。`lib/recount.py:159-162`）。この run は `tdd-start.json` が go:false で、別の単位も TDD の輪でなく修正役が直した。
   - 1.3 で挙げた run 82d22f4f は、同じ依頼の別の回（どちらが先かは時刻で確かめていない）。最後の関門が、消した試験の許しが 259 件積まれたことと、最後のテストが認証できなかったことの 2 つで止めた。
   - 型を切った後: 利用者に見える機能ではないので remove でなく tidy（3.4）。消す試験は計画の `change=remove` から出る `remove` の許しの中で、変えない段の義務（既存の試験の結果が同じで、居なくなった試験は `remove` の許しの中だけ）で照らせる。段 1 で tidy を作らないと通らない。第 5 版で tidy を段 1 で作る型に繰り上げた（B.3 の 3）。

4. 振る舞いを変える直しを修正役が直した例（形 1〜3 とは別。run 6cc154f6 の 1 単位。同じ依頼の run 54a313d5 も TDD の輪が走らず、その単位の sites が 3 行とも赤なのは同じ。ただし 54a313d5 は裁定の後の受け付けで 1 度拒まれた〔試験の欠けの単位の `class_query` が修正の前 1・後 1 で閉じない〕ので、「1 回で通した」までは同じでない）
   - 計画は route=tdd だったが、run に試験の実行器の入力が無く、TDD の輪が走らずに修正役が直した（1.4.1 の (b)）。
   - 判定の `class_query` は修正の前 3・後 0。sites は 3 行で全部赤を見た。`verified_how` は「退行を 1 か所ずつ注入して赤、戻して緑を見た。1 つ目を戻すと 3 つの試験が赤、2 つ目を外すと 1 つの試験が赤。戻した後は関わる試験 209 件が緑」。修正役は対象のリポジトリの試験の実行器を自分で走らせていた。受け付けは 1 回で通し、受け入れの試験の事後の赤緑は「試験の実行器が無い run」として確かめなかった。
   - 別の run 1e5eafbd の 1 単位も同じ道（route=tdd・試験の実行器の入力が無い・修正役が直した）だった。差分は .py だけで、`sites` に 8 行を書き、5 行が赤を見ていない。sites が「欠陥の現れる所」でなく「直した所の一覧」になっている。型を切ってもこの単位は TDD の輪の外の変える段の直し（9.2 の 1）で、static を分けても消えない。variant の `sites` を欠陥の所だけにする決まりが別に要る（10 章の 9）。
   - 型を切った後: variant（3.2）の手本の形。ただし variant の箱の義務（名指しの試験が起点で赤・返した木で緑）を機械が照らすには試験の走らせ方が要る。修正役が対象の実行器を走らせられたので、9.2 の 1 の案 1（工場の AI が走らせ方を作る）は、この場面では届く見込みがある。

### B.3 寄せた後の段 1 の並びで照らし直す（第 5 版）

段 1 で作る物（9.1 の 7 の後）:

- 変える段 `change`: tdd・variant・remove。
- 変えない段 `keep`: tidy（欠陥の形を持つ単位として届く「使われていない物を消す」直しまで）と、型ではない段の下ごしらえ（`pin`。挟む・単独の 2 つの頼まれ方）。
- 段の外 `outside`: static。
- 口の形だけ: rebuild と、欠陥の形を持たない書き直しの tidy。

計画が direct に回した 15 件の通り方（件数は計画の項目の数。括弧は実際に通った run の数）:

1. 文書の言い回しの直し（8 件。4 本）: route の語 `static`（9.2 の 3）で static に回る。通り方は B.2 の 1 のまま（第 4 版から変わらない）。
2. 試験の欠けだけを埋める直し（5 件。2 本）: route の語 `pin`（9.2 の 3）で、下ごしらえを単独で頼む注文になる。
   - 箱の義務（`keep`）: 既存の試験の結果が同じで、足した試験は起点の木で通る。run fec72aa1 は試験のファイルだけを変え、足した試験を含む試験のファイルが全部緑だったので満たす。
   - `pin` の 1（差分は試験だけ・足した試験が 1 つ以上）: 満たす。
   - `pin` の 2（起点の木で 2 回通る）: 第 5 版で寄せた時に足した確かめで、記録の run では照らしていない。足した試験は条件の式を照らす試験で、揺れる出力を持つとは記録から読めない。
   - `pin` の 3（足した試験ごとに壊して赤）: 修正役が書いた「条件の式を壊すと足した試験だけが赤、戻して全部緑」がそのまま当たる。
   - 第 4 版の型 pin で通した時との違いは、上の `pin` の 2 が増えたことだけ。
3. 役目を終えた検査を消す直し（2 件。1 本）: route の語 `tidy`（9.2 の 3）で tidy に回る。消す名に `change=remove` が付いていても、`tidy` の語が在れば remove に回らない（4.1 の 3）。
   - 箱の義務（`keep`）: 居なくなった試験（守る対象の無くなった検査の試験）は、計画の `change=remove` から出る `remove` の許しの中。ほかの関わる試験の結果は同じ。run 806536fc の `verified_how`（関わる試験が緑）と合う。
   - 共通の受け付け: `class_query` の数え直し（修正の前 18・後 0）は今と同じく効く。閉じの証明の欄は、欠陥の形を持つ単位なので今と同じに書ける（3.4）。範囲の照らし（run 806536fc で 2 度拒んだ物）は共通の受け付けの 1 で、今と変わらない。
   - 今との違い: 「赤を一度も見ない clean を拒む」（F135）は variant の型の義務に移る（2.3 の 6）ので、tidy の単位は赤を求められない。今のように同じ周の別の単位の赤に頼って通ることも、この単位だけの周で拒まれることも無くなる。
4. 振る舞いを変える直しを修正役が直した例（run 6cc154f6・1e5eafbd。route=tdd で、15 件の外）: variant の手本の形のまま（B.2 の 4）。第 5 版で変わらない。
