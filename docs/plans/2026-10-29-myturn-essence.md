## 0 語

- 芯: /my-turn（`attention` 0.52.0 の `commands/my-turn.md`）の手順の核の 4 つ。芯 1 は構造を捉える（手順 6）。芯 2 は、差分を見ない別の目に同じ種類のシステムの一般の構造を描かせて比べる（手順 7〜9 と「守ること」の 2 つ目）。芯 3 は、作る仕組みが補っている前提を消せないかから掘る（手順 10〜11）。芯 4 は、世の中の解と突き合わせ、自作をゼロベースで疑う（手順 13〜15）。
- 一般の構造: その種類のシステムが一般にどんな部品に分かれ、部品の間を何が流れ、正本（値の元）をどこに置き、依存をどちら向きにし、境目をどこに引くか。解き方やツールではない。
- 正典: 例の対象の持ち主が書いた設定の決めの文書。まだ取り込まれていない枝にだけ在り、run の版には無かった。中身は承認ノードの revise の答えの要約で読んだ。
- 例の対象・例の run: この調べの元になった社内のリポジトリと、それを直した工場の run。工場のリポジトリは公開なので、名前・番号・ファイル・中身は書かず、型だけを書く。下の `judge/`・`structure/` などは run の記録の中の置き場の名。
- 外れの理由: 一般の構造から外れる形を選ぶ時の訳。/my-turn は、外の基準（書かれた意図・一般の構造・業界の定石）か、外の動かせない事実（外のツールの仕様・法や契約）だけを認め、リポジトリの今の状態（設定・コード・置き方・慣習・既に在る物）は認めない。

## 2 答え 4: structure と world は項目 2 に走ったか

結論: どちらも項目 2 に走った。深さで飛んだのではない。根本は「段が無い」の側。ただし無いのは structure や world という段ではなく、その中の「外から一般の構造を描いて比べる」働き。

### 2.1 深さ

- run の深さは標準（判定の `tier: 標準`、訳「設計だけの run」）。
- line.md の 5.1 と 16 章の表では、標準は省く物も足す物も無い。表が省く物は軽量の差分の審査と R1〜R4 だけで、structure と world はどの段でも省く物に無い。ノードを深さの `when` で飛ばす道も無い（16 章）。
- structure は `$owed.output.owed == true` で走り（line の YAML の `structure` の node）、world は判定の中で走る（`judge/world/`）。

### 2.2 structure（構造の目）が項目 2 にしたこと

- 単位に項目 2 を持ち、飛ばした単位は無い。
- 判じた行: 汚れる（形 2「1 つの責務を 2 か所に分ける」）。推しの避け方は、名前を配る側の既定に 1 か所だけ足し、ローカルの設定には写さないという物。比べた相手は対象の指示ファイルの 2 行（個別最適で全体を汚さない・同じ事実は 1 か所に置く）。
- 同じ指示ファイルの次の行は、まさに芯 1・2 を対象の決まりとして書いていた（作る前に、一般の全体像の中のどの部品を触るかを言い、一般の理想像と並べ、外れるなら今そうなっているから以外の理由を書く、という趣旨）。構造の目の問いは「書いた意図に反するか・考えを知る場所が増えるか」で、この行を当てる働きを課していない。目は 1 か所にまとめる先として配る側を選び、名前を用意する側から流す形は出なかった。

### 2.3 world（世界の解）が項目 2 にしたこと

- 言い直す役は項目 2 の類を「ローカル開発環境を本番に合わせる（dev/prod parity）」とし、検索語もローカルの初期化を本番に揃える方へ向けた。
- web の役は 12factor の dev/prod parity を引き、依頼の解き方と「同じ」と判じた。当たらない所の欄に「本番とローカルの一覧が自動で揃う仕組みはこの出典では裏付けられない」とだけ残った。
- world は設計どおり、依頼の行の症状を 1 段上の作業の類に上げて問う（`world.md` の 2.1）。触る部品を含むシステムの構造（名前がどこで生まれ、誰に流れるか）は問わない作り。

### 2.4 ほかの段

- independent-design（独立設計）: 目的の文が手段（どの基盤のどの初期化に役を寄せるか）まで含んで渡った。項目 1 には「全体の中の位置づけ」と一般の理想を描いた。一方、項目 2 の名前の正本は「1 か所から作る手段が今は無い」を訳に退けた。今の状態を外れの理由にした形。
- plan（計画役）: 周 1 の項目 2 は「配る側の既存の部品が別の名前を導いているのと同じ形」で、名前を配る側に置いた。計画役の指示は、決め手 `decided_by` に「対象の中の同じ場面（コードが同じ問題をどう解いているか）」を数え（`plan-writer.md:43`）、「今在る物を先に探す」「考えの住処を使う」も課す（`:35`・`:41`）。前例が正典の消すと決めた形でも、決まりの上では正しい決め手になる。
- plan-review（事前審査）: 周 1 は「名前を導く住処は配る側の既存の部品で、計画はそこに寄せており、写しの穴は無い」と判じた。前例を住処として認めた。
- 並行 PR の役: 正典を持つ PR は、行が重なるかの判定でだけ見た。重ならないので除かず、中身は読んでいない。

### 2.5 まとめ

- 段は全部走り、全部通った。どの段も自分の問いには正しく答えている。
- 足りないのは、触る部品の理想形を外の基準から描いて比べる問い。今の比べる相手は、頼みの行（world）・目的の文（independent-design）・書いた意図（structure）・対象の前例（plan・plan-review）で、どれも頼みか対象の今から出発する。
- 対象のほうは指示ファイルの 1 行でその働きを求めていた。工場はそれを 1 つの書いた意図として渡しただけで、どの役にも課していなかった。正典が無い対象や、そういう行を書いていない対象では、なおさら通らない。

## 3 取り込めるエッセンス

1. 構造を捉える（芯 1）: 頼みの行ではなく、触る部品を含むシステムを、対象の名を使わずに、部品・流れ・正本・依存の向き・境目で描く。解き方は書かない。最後に「どんな種類のシステムで、触る部品がそこで何を揃えたいか」を 1 文で言う。工場で近い物は world の言い直す役（対象の名を外す）だが、あちらは依頼の行を言い直し、システムを描かない。
2. 一般の構造を別の目に描かせて比べる（芯 2）: 1 の 1 文だけを、道具も対象の名も頼みも持たない目に渡し、一般の構造を理由つきで描かせる。並べて違い（部品の切り方・流れの向き・正本の位置・境目）を挙げ、違いごとに寄せるか外れるかを決める。工場で近い物は independent-design（道具なしの目）だが、あちらは目的の文と対象の実測を受けて解き方を設計し、一般の構造は描かない。
3. 外れの理由の決まり（芯 2 の後半）: 外れてよい理由は外の基準か外の動かせない事実だけで、対象の今の状態は理由にしない。「同じ問題があと 3 回来たら、この形の延長で何が積み上がるか」も言う。工場では逆向きの決まりが在る（2.4 の計画役の決め手・構造の目の決め手の「対象の中の同じ場面」）。この決まりが今回の分かれ目に一番効いた。
4. 前提を消す（芯 3）: 作る仕組みを 1 文で言い、それが補っている前提（「〜を作る。要るのは、〜が〜を持たないから」）を言って、その前提を消す形を必ず先に探す。工場で近い物は計画役の `shrink_first`（足さずに消す・まとめる形を先に考える）で、補う前提までは言わせていない。今回なら「配る側が名前を導く部品が要るのは、用意する側から名前が流れてこないから」で、消す形は「流す」になる。
5. 世の中の解を部品の全体に当てる（芯 4）: 世の中の解を、まず部品の全体（作る仕組みが解く問題）に、次に依頼の行と案に当てる。ツールは、一般の構造のどの部品を受け持つかを言ってから数える。自作をゼロベースで疑う。工場の world は依頼の行ごとに当てるだけで、部品の全体には当てない。

取り込まない物: 手順 1〜5 と 16〜20（PR の会話を読む・インラインコメントの下書き・作業ツリーの片付けなど、PR を審査する形に付いた物）。工場では判定・報告・承認ノードが同じ役を持つ。

## 5 答え 3: 取り込んでいたら今回の run は何を出していたか（見立て）

### 5.1 試したこと

/my-turn の手順 7 と同じ問いを、道具を持たない別の目（convergence-loops の blind-judge）に 1 回だけ投げた。渡した 1 文は、対象の名を使わずに「資源を用意する側・アプリを配る側・名前を使うアプリ・ローカルの開発環境の初期化の間で、ある資源の名前を揃えたいシステム」を言う物。問いの文は手順 7 の字のまま。

返った一般の構造の要点:

- 論理名（アプリにとっての役割名）・物理名（実際の資源の名前）・受け渡しの鍵（アプリが物理名を受け取る口）を分ける。
- 流れは「宣言 → 用意する側（本番とローカルは兄弟）→ 配る側 → アプリ」の一方向。用意する側は作った物理名を出力として流し、配る側はそれを鍵に入れてアプリへ渡す。逆向きの流れは作らない。
- アプリは鍵から読むだけで、名前を直に書かない。
- ローカルの初期化を正本にしない（本番に無い部品が名前を決めると、本番とローカルの差が見えなくなる）。
- 配る時か起動時に、資源が在るかを確かめてすぐ止まる。

### 5.2 並べ

- 周 1・2 の形: 名前の正本が配る側。ローカルの初期化と本番のジョブの設定はそこから導く。本番の用意する側は別に名前を持ち、検査で突き合わせて揃える。アプリは自分の既定の名前を持ったまま。一般の構造と比べると、正本の位置（配る側）・流れの向き（用意する側から流れていない）・アプリが名前を直に持つ、の 3 つが違う。
- 正典の形（承認ノードの答えの要約）: 配る側は名前を作らず、受け渡しの鍵を読むだけ。鍵に既定を持たせない。本番は用意する側が鍵に書き、ローカルはローカルの宣言から作る。一般の構造の流れ・正本・鍵の分け方と同じ向き。
- 周 3 の形（正典の要約で組み直した物）: ローカルの名前はローカルの宣言へ寄ったが、本番の受け渡しは別の作業に回り、手元で流す設定はアプリの既定を読むので、事前審査は「読む者の無いキー」と判じた。一般の構造の「アプリは鍵から読むだけ」が抜けた形。

### 5.3 見立て

- 4.1 と 4.2 が入っていれば、構造の目は周 1 の前に、上の 3 つの違いを挙げていた見込みが高い。配る側の既存の部品という前例は対象の今の状態なので外れの理由にならず、寄せる側に決まる。
- 周 1 の計画は、名前を用意する側から流す形（本番は用意する側が渡し、ローカルはローカルの宣言から作り、アプリは鍵だけを読む）を出していた見込み。例の依頼の範囲を超える分（本番の受け渡しを変える・アプリの既定の名前を消す）は、6 章の問い 2 の答え次第で、範囲の中に入れるか、別の作業の案として承認ノードに上がる。
- 人の revise（周 2 の答え）は要らなかった見込み。ただし正典の細かい所（鍵の受け渡しの具体の仕組み・鍵に既定を持たせない）までは保証しない。正典を読ませる直し（元の頼みの A-1・A-2）は別に要る。

### 5.4 見立ての弱さ

- 試しは 1 回だけ。
- 1 文は、正典の要約を読んだ後の自分が書いた。答えの語（明示的に受け渡す・契約・鍵）は入れないようにしたが、4 つの部品を並べた所が答えへ寄せた恐れはある。工場では構造を描く役が正典を知らずに書くので、1 文がもっと狭くなりうる。
- 工場の run では確かめていない。確かめるなら、4.1 を入れた structure の block を、例の run の単位と対象の版で単独で回し、項目 2 の行が上の 3 つの違いを挙げるかを見る（7 章の T1 の確かめ）。

## 6 持ち主に選んでほしい分かれ目

### 問い 1: 一般の構造と、対象の中の前例がぶつかる時に、どちらを既定で勝たせるか

- 案 A（推し）: 一般の構造が勝つ。前例は一般の構造と同じ向きの時だけ決め手に数え、外れの理由には数えない（/my-turn と同じ。例の対象の指示ファイルの 1 行とも同じ）。得: 今回の周 1 のように、消す予定の形を前例に固める道が塞がる。代償: 対象の流儀に揃える小さな直しでも「外れ」が出て、承認ノードの項目が増えうる。
- 案 B: 今のまま、前例も決め手に数える。一般の構造との違いは構造の目の行として見せるだけ。得: 計画役の振る舞いが変わらない。代償: 今回と同じ所へ戻りうる（4.2 の「要るか」）。
- 案 C: ぶつかったら毎回人に上げる。得: 持ち主が全部決める。代償: 無人の run が止まりやすくなる。
- 持ち主の答え: A（一般の構造を勝たせる）。条件: リポジトリが文書で決めた決まり（AGENTS.md が指す正本の文書）は一般の構造より優先する。前例（リポジトリの今の形）は外れてよい理由にしない。

### 問い 2: 一般の構造に寄せると頼みの範囲を超える時、どこまで直すか

- 案 A（推し）: 頼みの範囲の中だけを直し、超える分は別の作業の案（依頼の行の下書き）として承認ノードと報告に出す。/my-turn も、触る部品の外の話は作者に頼まず持ち主に上げる。得: run が膨らまない。代償: 理想形への道が 2 本の作業に分かれる。
- 案 B: 超える分が小さければ計画に入れてよい。得: 1 回で寄る。代償: 「小さい」の線引きが要り、範囲の膨張を見る事前審査とぶつかる。
- 持ち主の答え: 推しの A ではない。持ち主の言葉「ついでに直す。別PRにもしない。そもそもPRで出したときに見えてなかっただけ。そしてこの辺は工場に線引きあったはず。修正過程でも。」
  - 窓口の読み: 一般の構造に寄せるのに要る分は、同じ計画・同じ PR に入れる。線引きは新しく作らず、既に在る物に従う。計画の段では案の `allowed_paths` に入れる。修正の段では書き手の範囲の相談 `consult`（`workflows/.shared/prompts/writer.md` の「Scope consultation」）と、無人の run で範囲を広げるだけの案の直しは聞かずに通して報告に出す L-G45、無人の run で約束の欄が変わる項目は止まる L-D30（`docs/design/line.md` の 6 章。人の居る run では約束の欄を変える案の直しを承認ノードで人に見せる）。

### 問い 3: どの深さの run で回すか

- 案 A（推し）: どの深さでも回す。structure の段は今も軽量で回っており、計画の壁打ちをどの段でも省かない決めと同じ扱いになる。得: 軽量でも消す予定の形を固めない。代償: 軽量の run にも AI の役が 2 つ増える。
