# 報告の書き手が模型の安全の判定（reasoning_extraction）に止められる（#712）

## 結論（先に 3 行）

- 報告のサブグラフ `workflows/report/works-factory-report.yaml` の `write-loop` の中の `write`（模型の群 `@wf-report`＝sonnet・medium）が、2026-10-17 11:53 以降、模型の提供元の安全の判定 `reasoning_extraction` に止められて落ちる。
- 指示書 `workflows/report/commands/report.md` は変わっていない。同じ指示書で `write` はそれまで 148 回通っており、落ち始めたのは判定の側が厳しくなったため。
- **この枝では直せない**。直した版を実際に流して判定を通るか確かめる手段が、この隔離の作業ツリーには無い（模型の認証に届かない）。持ち主の判断が要る。下の「持ち主に選んでほしい道」を読んでほしい。

## 何が起きているか（確かめた事実）

- 落ちた run（記録は工場の家の Archon の DB と run の置き場）: `c67db709`・`d5a46972`・`b1a9f81b`・`d5101820`・`4bcd3c2e`（issue 本文は 4 本だが `d5a46972` を含め 5 本）。いずれも 2026-10-17〜18。
- 落ち方は 5 本とも同じ。`write` の最初の模型の呼びで（道具を 1 つも呼ぶ前に）落ちる。誤りの文は「API Error: Sonnet 5.5's safeguards flagged this message … Details: `[reasoning_extraction]`」。送った模型は `claude-sonnet-5-5`（記録の `model_usage.resolved` が `claude-haiku-5-5` と出るのは、拒みの応答の課金の見かけ。入力 ~31k tokens と系の大きさから本体は sonnet）。
- `write` の成否の履歴（同じ archon-home の Archon の DB）:
  - 成功 148 回（2026-10-14 22:50 〜 2026-10-17 09:40。すべて `claude-sonnet-5-5`）。
  - 落ち 25 回。うち 2026-10-17 以前の落ちは「使用量・上限」だけ。`reasoning_extraction` は 2026-10-17 11:53 が初出で、以後 10/18 まで。最後の成功は 2026-10-17 09:40。
- よって `report.md` の中身が当たっているのは確かだが（5 本の run は git の状態も材料も違うのに同じ所で落ちる）、**落ち始めたきっかけは指示書の変更ではなく、判定の側の厳格化**（2026-10-17 午前の間）。

## どこが当たっているかの見立て（未確認）

`write` の初回メッセージのうち、run をまたいで変わらないのは `report.md` 本体＋末尾の引き継ぎのメモの頼み（`lib/handoff.py` の `ASK`）＋ Claude Code の系のプロンプト。この中で `reasoning_extraction`（別の模型の考えの過程の引き出し）と読まれやすいのは:

- 構成 7「判定の生の返答（判定のファイル。要約で丸めず、根本の単位のキーの集合と判定と理由はそのまま転記する）」。
- 構成 5「R1・R2・R3・R4 それぞれの判定と理由」を本文に写す頼み。
- 末尾の引き継ぎのメモの頼み「decided＝そう決めた訳・rejected＝退けた案と退けた訳・doubts＝迷っている所」。

補強: 同じ引き継ぎのメモの頼みを持つ計画の書き手（`@wf-plan-writer`＝opus）は落ちていない。sonnet の `write` だけが落ちる。ただし**どの一文が決め手かは流して確かめていない**（下の制約のため）。

なお issue の求め 2 の例（ほかの役の理由の全文を貼らずにファイルのパスを渡して読ませる）は、落ちる 1 周目には既にその形になっている。`report.md` は材料をパスで渡して Read させており、生の理由を本文に貼り込んではいない（前の周のメモを貼るのは 2 周目以降で、落ちるのは 1 周目）。したがって当たっているのは**渡し方（貼る／読ませる）ではなく、指示書の言い回し**の見込みが高い。

## なぜこの枝では確かめられないか

issue の求め 1（材料を減らした版・言い換えた版を同じ模型で 1 回ずつ流す）と求め 4（直した版の報告のグラフを流し直す）は、どちらも `write` を本物の文脈で sonnet に流す必要がある。この隔離の作業ツリーからはそれができない:

- `write` は Claude Code の `command` エージェントの大きな系のプロンプト（入力 ~31k tokens）の下で、`report.md` を**初回メッセージ**として sonnet に渡して走る。判定はこの文脈でだけ立つ。
- この作業ツリーから模型の認証に届かない。環境変数にトークンが無く（子プロセスも subagent も同じ）、keychain の項目 `Claude Code-credentials` は `accessToken` が空の殻、login keychain はこの文脈から見えない。独立の `claude -p` は「Not logged in」で落ちる。
- 私の認証で動く唯一の経路は subagent だが、subagent は `command` エージェントの系のプロンプトを再現できない。`report.md` を初回メッセージでも道具の結果でも sonnet の subagent に渡したが、原寸（v0）も言い換え版も全部通ってしまい、本物の落ちを再現できない。

したがって、言い換えが判定を通るか／模型を替えれば通るかは、**認証の在る環境で 1 回流し直せば分かる**が、ここでは判定できない。推測で指示書（写しの台帳 `tests/workflows/copied_rewrites.json` に縛られる）を書き換えても、当たらない保証が無いまま触ることになるので、この枝では変更していない。

## 持ち主に選んでほしい道（どちらも認証の在る環境で 1 回の流し直しで確かめられる）

1. **指示書の言い換え**: 構成 7・5・引き継ぎのメモの頼みを、別の模型の考えの過程を引き出す頼みと読まれない言い回しに替える（例: 「生の返答をそのまま転記」→「判定ファイルの該当欄の判定と理由を本文に写す」）。本文に載る中身（R1〜R4 の判定と理由・問いの台帳・判定の転記）は落とさない。※落ちた run の記録を材料に流し直して、通ることを確かめてから入れる。
2. **`@wf-report` の模型を替える**（求め 3）: opus の書き手は同種の判定に強い（計画の書き手が落ちない）。費用の見込み（この archon-home の成功した `write` 148 回から）:
   - sonnet: `write` 1 回 平均 $0.44（$0.13〜$0.92）、1 run 合計（冷えた読み手の往復で `write` は 1〜3 回）平均 $1.31・最大 $2.24。
   - opus は入出力とも約 5 倍。`write` だけで 1 run 平均 ~$6.6・最大 ~$11。
   - 注意: `@wf-report` は `write`（書き手）と `cold`（冷えた読み手）の両方を指す（`lib/launchgroups.py`）。群を分けないと `cold` も opus になる。報告のサブグラフは毎 run の最後に 1 回走る。

替えるかは持ち主が決める（自分では替えない）。

## 補足

- #702（PR #707）で、`write` が落ちた run は failed で終え、機械が組む報告は残す形になっている。本文が載らない状態は、この判定を通さない限り続く。#707 の resume のやり直しは使用量の上限のための物で、安全の判定は同じ模型ならアカウントを替えても通らない。
