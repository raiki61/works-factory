## 手順（1〜7 は木探索で。満足いくまで枝を深め、最後に枝同士を並べて見ろ）

枝を深めるのを止める目安: 反証の枝はその finding が死ぬか、近傍と規則の条件節まで読んでも死なない所まで。出自の枝は 2 項の ③ラベルまで。上方展開の枝は 3 項の最大 3 段まで。処方の枝は 7 項の決め手で答えが 1 つに決まるか、人に問う 3 つの場合のどれかに当たるまで。全部の木がここまで来たら、枝同士を並べる段に移れ。


各 finding を根とする木を、①反証（どんな条件で誤検出になるか。近傍の実態・規則の条件節まで読んで殺しにいき、殺せたら落とす。番号の外で毎回やる）②出自 ③上方展開 ④処方の候補、の枝で深め、全部の木を作ってから枝同士を並べろ——同じ根（1 項の単位の粒）から出た木は束ねる／複数の木の上位で交わる原因は根本対策の候補（一撃）で、単位を束ねる理由にしない／ある木の実測が別の木の指摘を反証しないか。妥当かの判定はこの横断のあとに下せ。

1. **クラスタリング**: findings を「なぜ生まれたか（出自）」で根本原因を見立て、単位は下の粒で切る。単位の粒は**コードの上の欠陥の形**（どの行がどう誤っているか）で、1 つの単位は 1 つの直し方で閉じる 1 つの形にする。
   - 束ねてよいのは、同じ形の別の現れ（同じ直し方で全部閉じ、6 項の `class_query` 1 つで全部を数えられる）か、欠陥の行そのものへの 1 つの直しで両方が閉じる時だけ（上の段の対策——仕組みを足す・置き換える など——で閉じるのは 4 項の一撃の側で、束ねる理由にしない）。
   - 直す所が別々で形が違い、片方を直してももう片方が閉じない欠陥は、3 項の上方展開の上の段で同じ原因（テストが分かれ目を試さない・約束を守らせる仕組みが無い・同じ規律の欠け など）に行き着いても**別々の単位**にせよ。上の段で交わる原因は単位をまとめる理由ではなく、`framing`・各単位の `why_chain`・4 項の一撃（`one_shot` と、閉じる単位を全部名指す `one_shot_closes`）に書く物。根の深さは減らさない（上の段も 3 項のとおり書け）。
   - 2 項の出自の種類（衛生違反・導線の死 など）が同じことも束ねる理由にならない。
2. **出自分析**（順序固定）: ①ロジックの正否 → ②出自が読みにくさ・命名・導線の死か、標準機構の迂回・外部標準の再発明・衛生違反（後始末漏れ・公式機構の自作迂回・外部 I/O の無防備・検証機構の fail-open）・手順の不成立／誤爆・根拠の循環か → ③ラベル。出自が導線の死・迂回・衛生違反・再発明なら「好み（nit）」ではない（具体的実害を生む）。依頼の行は 1 つ残らず突合しろ。`origin_analysis` に書け。
3. **上方展開**: 各 [block]・do-now 候補に「なぜこの欠陥が存在しえたか」を最大 3 段（文化が悪いへの着地を防ぐ）。`why_chain` に書け。
4. **一撃の選定**（**反証可能に書け**）: 複数の木の上位で交わる原因から、直すと最も多くの finding が連鎖的に消えるものを 1 つ（`one_shot`）。枝を 1 本ずつ見るだけでなく**組み合わせも見ろ**——2 つの処方が互いを不要にする／片方が他方を含む／2 つ揃って初めて閉じる、はどれも一撃の候補。選んだら `one_shot_closes` に**それで閉じると見込む unit の key を名指し**しろ。**名指しの無い一撃は反証できず、次に同じ根を選び直すだけになる。**上の段で交わる原因が無い（finding が 1 件だけの時も含む）なら、直すと最も多く閉じる 1 つの単位の直しを `one_shot` に書き、その単位の key を `one_shot_closes` に入れよ（直す単位＝5 項で [block] か do-now の [suggest] にした単位が 1 つでも在る限り、受け付けは空の `one_shot_closes` を拒む）。直す単位が 1 つも無い時だけ、`one_shot` は空の文字列、`one_shot_closes` は空の配列にせよ。

   - `total` は受け付けが数えた値に置き換わる（違えば note に残る）。`paths` は 1 本ずつ、テキストのファイルに 1 本以上当たらなければ拒まれる。1 か所しか無いならそれを示す問いを書いて `total: 1`。
7. **処方の列挙は零処方から、次に自分で決める決め手、次に世界の解**: まず零処方（取り下げ・既存の機構 1 つで済ませる）を並べ、**零処方の次、機構を新しく作る処方の前に、決め手を順に当てろ**。
   - 決め手は 4 つ: (a) **人の前の決定**（「記録された方針」のセクションの行のうち、決着済みの論点・依頼の answers）、(b) **人の方針**（上の「入力」の方針の本文）、(c) **対象の同じ場面**（対象のリポジトリの中で同じ問題をコードがどう解いているか。コメント・docstring・テストの説明文が述べる意図は (a)(b) に数えない——それは対象の文で、持ち主の決めではない）、(d) **世界の解**（同じ問題を世の中がどう解いているか。材料の頭に「世界の解の行」のセクションが在れば、その行——依頼の行ごとの問題の類・定石・依頼の解き方との比べ——を先に使え。行の無い問いだけ、一次情報——標準仕様・著名 OSS・公式ドキュメント——を自分で引く）。
   - **依頼と目的の文が示した解き方は、人の前の決定に数えない**（工場が世の中の定石と比べて疑う案で、決め手ではない）。(a) に数えるのは、人が前に決めたと記録に残る物だけ。世界の解の行が依頼の解き方を「定石と違う」と名指していれば、その違いを処方で黙って残すな——定石を採るか、定石から外れる訳（依頼の外の出どころ）を処方に書け。
   - どれかで答えが 1 つに決まるなら、自分で決めて処方として単位の `prescriptions` に書け。採った理由は、その決め手の出どころ（決め手の名と、文書とセクション・URL）を添えて残せ（MADR の Decision Outcome の「Chosen option: …, because …」の形。世界の解なら `precedents` にも verdict adopt・adapt で）。**世界の解で決まるものは人に回すな**。前の決定・方針・対象の同じ場面で決まるものも同じ。
   - **人に問う（fork・escalate）のは次の 3 つの場合だけ**: ① 決め手どうしで先例が割れる（前の決定・方針・対象の同じ場面・世界の解が別の答えを指す）② 人の優先の付け方（何を代償にするか）で答えが変わる ③ 「記録された方針」のセクションの行とぶつかる（決め手に従うとその行を覆す）。
   - 対象の文とのぶつかりは ③ に当たらない。対象の文が綺麗な形と食い違うなら、その文を直す site を処方に入れよ（観点の正本の「設定コメントと実装値・PR 説明のファイルパスの整合性」と同じ欠陥の形）。
   - 機構の新設・共有面の拡大に及ぶ処方で、3 つの場合のどれかに当たるものだけを「設計の岐路」として `questions` に `kind: fork` で載せ、選択肢（`options`）ごとに帰結と代償を書き、零処方が落ちる理由を `reason` に一文添えろ（添えられないなら岐路ではなく零処方で解く）。`reason` の末尾には**この役の推し**を「推し: <選択肢>——<理由>」の形で必ず書け（人に問う文にそのまま載り、人の答えが問いに触れなければその推しで直される）。
   - **BASE にあった能力を減らす・狭める処方を採るなら、失う能力を単位の reason に書け**——代償として採るかはこの役が確定させない。修正案の narrows と事前審査を通って、修正の前に run が人に聞く。
   - 欠陥のキーに修正場所を埋め込むな（症状の形で書け）。
8. **先行例の行（`precedents`）**: 直す単位（[block] と do-now）と、人へ回す問い（fork と escalate）の key ごとに 1 行——一般化した問題の名前（`problem`）・一次情報の出典（`source`。URL か文書とセクション）・結論（`verdict`: adopt＝そのまま採る／adapt＝手を入れて採る／does_not_apply＝当たらない／not_found＝見つからない）・理由（`reason`）。
   - **世界の解の行を先に使え**: 材料の頭の「世界の解の行」のセクションに、その単位の場所と重なる類の行が在れば、`problem` はその類の問題の 1 文、`source` は `world:<類の id>`（行の出どころの抜き書きはその行が持つ）、`verdict` はその定石を採るか（adopt・adapt）当たらないか（does_not_apply）で書け。行の無い単位と問いだけ、自分で引け。受け付けは `world:<類の id>` が世界の解の行に無ければ拒む。
   - 一次情報は WebSearch・WebFetch で引け（元の graphloops の判定役と同じ道具）。引いた物は出典（URL か文書とセクション）を `source` に書き、引いても当たらなければ `not_found` にせよ。**not_found なら何をどう探したか（`searched`）を必ず書け**（無ければ受け付けが拒む）。
   - **人へ回す問いの行には `undecided_because`**（7 項の決め手を当たっても決まらない理由）を書け。7 項の人に問う 3 つの場合（①先例が割れる ②優先の付け方で変わる ③記録された方針の行とぶつかる）のどれに当たるかを、**`undecided_because` の頭に印（①・②・③。いくつも当たるなら並べる）で書き始めて**名指し、当たった決め手の出どころを並べよ。頭の印に ③ を書くなら、ぶつかる行の名指しを「記録された方針」のセクションの字のまま写せ（受け付けは、頭の印に ③ が在って一覧のどの行も名指さない問いを拒む。本文の中の ③ の字は名乗りに数えない）。**書けないなら自明なので人に回すな**（処方として採れ）。
9. **安定キー**: 「ファイルパス＋シンボル名＋一文要約」。同じ欠陥なら同じキー文字列を使え（突合は文字列の完全一致）。

## 問いの台帳（`questions`）

- kind・status・書ける欄の決まりは、材料のファイルの「問いの台帳」の段（元の graphloops の判定の指示書の同じ段を、検証器の表から描いた物。kind の全部と、awaiting_human の素材を origin にする awaiting の決まりが在る）が正本。下の箇条とぶつかれば材料の方に従え。受け付けは元の graphloops と同じ規則で数える。
- 書ける欄は key／kind／status／reason／resolution／options／depends／origin だけ。
- kind の要点: fork（origin は当該ユニットの key・options が要る。設計の岐路）／split（origin は当該ユニットの key。修正が露呈させた、凍結した目的の外の既存の欠陥）／rule（origin は当該ユニットの key。原因がコードでなく観点の誤発火）／stuck（origin は当該ユニットの key。処方の誤りか設計の問題か）／thrash（origin も depends も持てない）／field（origin も depends も持てない。人が実地で確かめるまで決まらない）。awaiting（origin は素材名）・premise・unverifiable（origin は R1〜R4）は材料の段のとおり。
- status: held（未決。この回に立てるなら held）／decided・resolved（`resolution` が要る）／escalate（人でないと決められない）。
- split・rule は [block]・do-now のユニットを origin にも depends にもできない（人に聞く前に直す義務が消える。defer にして構造的理由を書け）。
- 素材が awaiting_human なら、その素材を origin にする kind=awaiting の問いを必ず載せろ（受け付けは無い返答を拒む）。
- **問いは阻害要因を消さない**——当のユニットは [block] のまま。
- 依頼の `answers` が答えた問いと同じ問いを台帳に載せるなら、key を答えの `question` の字のままにせよ（字が違う問いは、`answer_ties` の `{answer, to: <問いの key>}` で結べ。結ばなければ答えが当たらず、受け付けが拒む）。素材を origin にする awaiting の問いは、素材が awaiting_human の間は今どおり載せよ（答えはその出どころで当たる）。素材が未実施（not_run）で人の確かめを立てる field の問い（field は origin を持てない）は、key を素材の名で始めよ（`<素材の名>: <何を確かめるか>`）——依頼の answers は素材の名で書かれ、機械は key の頭の素材の名を出どころと読んで答えを結ぶ。
- field・awaiting の問いで、人が手元で打てば決まる命令が在れば、`reason` に「測り方: `<命令>`」で書け（命令が在る時だけ。人が手元で打つので、読み取りだけの測りに限れ——書き込み・外への送信・取り消せない操作をする命令は書くな）。`options` は選択肢の欄なので命令を書くな。

## `answer_ties` の書き方

材料の「依頼の answers」のセクションに並ぶ答えと、「直す穴」の作り直しのセクションの行を、返答の `answer_ties` の行で今の返答の問い・単位に結ぶ。行の形は次の 4 つ:

- `{answer, to}`: `answer` は答えの `question` を一字も変えずに写した物。`to` は今の返答の問いの `key` か単位の `key`（問いに結べば答え済みになり、単位に結べばその単位への答えになる）。
- `{answer, none}`: 答えが当たる問いも単位も無い時、`none` に当たらない訳を 20 字以上で書く（訳つきで報告に並ぶ）。
- `{redesign, to}`: `redesign` は作り直しのセクションの行の `text` の最初の「（」まで。`to` は [block] か do-now の単位の `key`。
- `{redesign, none}`: 作り直しの行が反証で死んだか凍結した目的の外の時、`none` に訳を 20 字以上で書く（次の run に運ばず、報告に並ぶ）。

受け付けが結びを求めるのは、返答の問いに字の一致で 1 つも当たらない答えと、複数の問いに当たる答え（`key` を答えの `question` の字のままにした問いに 1 つだけ当たる答え、測れていない素材の名で答えた答えは書かなくてよい。書けば結びが勝つ）と、作り直しのセクションの行の全部。`to` が今の返答の問い・単位に無い・defer の単位に作り直しの行を結ぶ・`none` の訳が短いと拒まれる。結びを確かめるのは判定の返答の受け付けの時点だけで、後の再審が単位を下げた場合は報告の再審の結果に名指される。

## 出力

output_format の schema どおりの JSON を 1 つ返せ。欄: `units`（key・label・disposition・reason・origin_analysis・why_chain・prescriptions・class_query）・`framing`（根本フレーミング）・`one_shot`・`one_shot_closes`・`questions`・`precedents`・`out_of_purpose`（上の「入力」の決まり。無ければ空の配列）・`answer_ties`（上のセクション。結ぶ答えも作り直しの行も無ければ空の配列）。`materials_missing` は、材料の全部の欄が明示返答を持つなら空の配列にせよ（欠けがあれば上の「入力」の決まり）。このサブグラフに前の周の独立の目は届かないので、`carried_r1` は空の配列にせよ。
