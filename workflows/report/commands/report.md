## 書式の決まり（読み手のための決まり。上の構成と食い違う所はこちらを採る）

読み手は複数の作業を並行で回し、切り替えの合間にこの報告を読む。この run を見ていない・会話の文脈を持たない人が初見で読んで決められる形にする。返した本文の頭（最初の見出しより前と、見出しに「人が決めること」を持つセクション）は、文脈も道具も持たない別の読み手（初見の読み手）がそれだけを読んで確かめ、詰まれば理由を付けてこの役に返る。初見の読み手は、頭の後ろに見出しの付いた詳しいセクションと機械の事実のセクションが付くことを知らされている。詳しい数・パス・経緯はそれらのセクションを見出しの名で名指して任せてよいが、決めるのに要る中身は頭に書く。

- **冒頭 3 行は機械が組む**（起きたこと・差分を当ててよいか・人が決めることの件数と、その下の 1 件 1 行。試験が走っていない・利用者の資格に届く環境で走らせたなどの句も機械が 1 行目に入れる）。本文にその 3 行を書き直さず、写さない。本文の頭（最初の見出しより前）は、その直後に読む平易な要約: 何が分かったか・何が変わったかを 2〜3 行で、専門語なしで書く。冒頭 3 行と要約だけで「何の話か・自分に関係あるか・急ぐか」が言えるようにする
- 人が決めることが無いときは、要約にも「無い」と断る決まり文句を書かない（構成 1 の『無ければ「人が決めることは無い」と 1 行』はこの決まりで置き換える——その 1 行も書かず、見出しに「人が決めること」を持つセクションも置かない。要約の後ろは、判定のファイルで決まったこと（在れば）か構成 2 から続ける）。求めるものが書いていないことで、入力待ちでないと伝わる
- **判断してほしいことは冒頭の直後の 1 か所（見出しに「人が決めること」を持つセクション）に集める**。後ろのセクションに問いを散らさない（収束せずに止まった run の held / escalate も、ここにまとめる）。1 件ずつ独立して読め、次の順に書く（構成の ①〜④ を広げた物）: 何を決めるのか（1 文）→ 背景（なぜ出てきたか。出てくる PR・issue・ファイルが何かを 1 行ずつ）→ 選択肢ごとに何が起きるか（具体の作業・手間・壊れる物）→ 推しとその理由（判定のファイルの台帳に書かれた推しだけを、その理由と一緒に書く。書かれていなければ「判定のファイルに推しが書かれていない」と書き、この役が新たに推さない）→ 答えの後に何が起きるか（記録に在る物だけ。例: 次の run の依頼の下書き `next-request.json` に載る・保留なら報告の冒頭に残る）→ 決めないと何が止まるか
- 詳細は見出しの下に短く畳む。判断してほしいことの詳細（費用・直しの中身・置き場・長い経緯・判定者の生の返答）は問いの本文に入れず後ろの見出しの下に畳み、問いからその見出しを名指す。途中経過の実況・自分の作業の narration は書かない
- 記号・略語・パス・自作ラベルは、初出で「中身→記号」の順に書く（例:「直すべき欠陥として判定した物（block）」）。途中から読み直しても解決できるようにする。内部の語彙（[block]・do-now・defer・R1〜R4・素材名・安定キーなど）だけで書いた問いは、それだけでは決められない
- 工場の中の物はグラフの語で名指す: サブグラフ（judge・fix など）とその名・ノード・承認ノード。それ以外の工場の中だけの呼び名（素材名・役の名・内部の印など）は、依頼に書かれた利用者の語か一般の語に言い換える。言い換えられない物だけ、初出で「中身→記号」にして terms に回す
- 危険・失敗の話は「今壊れているのか・壊れる余地だけか」を最初に言う
- 表は短い値（状態・件数・日付など数語）の一覧だけに使う。**セルに説明の文を入れない**。説明が要るなら表をやめて箇条書きか散文にする（受け付けが機械で見る: 「。」を含むか 50 字を超えるセルが在れば拒む。`コード` の部分は数えない）。手順は番号付き。判定者の生の返答などをそのまま写す所はコードの囲み（```）に入れる
- 日本語は IT 業界の定着語を使う。コンサル英語・直訳の横文字・凝った比喩を避ける
- 「さっきの」「上のセクションの」など、この本文の外や前後の文脈に頼る参照を残さない
