## Brief rules (the source of the requirement and the background)

A brief is a file the machine cut out of one item of the fix plan that passed the pre-review and the person's approval, and froze (even if a role rewrites it, what is read next returns to the text as it was when it passed). They are listed with absolute paths in the section "The requirement (briefs)" at the head of these instructions.
Words used below: a "conflict declaration" is a declaration returned in the form of the later section "Conflict declarations (do not bend to get green)" of these instructions (the fields and the values of `which_is_right` and `kind` are in that section). A "ruling" is the result of the read-only ruler ruling on that declaration. "The judgment file" and "the request file" are the judgment file in "What to read" of these instructions and the request file named at the head.

1. **The briefs listed in the section "The requirement (briefs)" at the head are the only source of the requirement.** First Read all the briefs, and fix as they say. You need not read the whole fix plan.
2. **The judgment file is background.** Read it to look up the brief's units' `class_query` (the query that finds every instance of the same shape) and `origin_analysis` (where it came from). How the units are cut is as the judgment says. What to fix and how is what the brief says. If the brief and the judgment disagree, the brief wins: do not stop, fix as the brief says (do not reinterpret it to fit the judgment). Only when you see the brief itself as wrong, return the declaration of 3. Even if the reach of "Fix every instance of the same shape" in the rules below disagrees with the brief's scope, the brief decides what to fix and how far. But the acceptance's machine checks all apply even with a brief: the recount of the defect's shape with `class_query`, the check of frozen tests, selecting and running the tests the change reaches, and the listing in the list shown to the person at the end (the rewritten tests of 4 are listed too). If the brief's scope is narrower than what the `class_query` recount asks for and it does not close without fixing outside the scope too, do not narrow it silently. If you need something outside the scope, consult first as 8 says (the answer's `consult` field; if allowed, fix it), and when there is no consultation section, you cannot ask, or it is not allowed, return that unit as a conflict declaration saying it needs something outside the scope. `which_is_right` is request if it needs something outside the scope (`kind` is `scope_needed`). If the judgment's query also hits the correct form after the fix (the count does not drop even when fixed correctly, or a `population` query also hits things that need no fix; a `population` query is one whose `class_query` `counts` is population, counting the population of things to fix rather than the defects), return the conflict declaration with `which_is_right` query (with `correct_lines`; copy into the field `correct_lines` the correct lines after the fix that the query still hits), and `kind` is `query_hits_fixed`.
3. **If you think the brief is wrong, do not reinterpret it yourself; return a conflict declaration.** In `between`, put the brief file's line (the absolute path listed at the head) and the judgment file's or the request file's line. `which_is_right` is request if you see the judgment or the request as right, unknown if you cannot decide. `kind` is `brief_vs_judgment` (it needs the brief's line in `between`; it cannot be used for a unit without a brief). For a unit that received a ruling, the ruling wins over the brief within the ruling's scope (a unit that received a ruling is a unit whose ruling appears in the file named at the head of the instructions of the second start, "the file with the rulings on the conflict declarations". The scope is the place written in the ruling. Outside the ruling, the brief stands).
4. **Only the existing tests named in the brief's `rewrite_tests` may be rewritten.** Each row of `rewrite_tests` has `id` (the test to rewrite), `behavior` (the behavior it binds), `old` (the current expectation), and `new` (the expectation after rewriting); rewrite the test with that `id` to the `new` expectation. This is to rebind the behavior the request changes, not to fit an expectation to the implementation. Do not change tests outside those named, as now. The rewritten tests are listed at the last approval node.
5. **The brief's `tests` are the acceptance tests decided beforehand.** Under those names, bind the written behavior through the written real path, and make them red in the written way.
6. **In a run without the section "The requirement (briefs)" at the head (a run without a fix plan) and for a unit without a brief, the judgment file is the source.** Then Read the whole judgment file first, and do not apply 1–5 above.
7. **The conditions answered at the approval node before the fix (notes_file; by a person, or by the recommendation an unattended run took) win over the brief.** Apply them before 1–5. notes_file is "the file with the answers at the approval node" in "What to read"; if it is empty there are no conditions and 7 does not apply. If the brief goes beyond a condition, fix as the condition says, and return the part beyond it as a conflict declaration (in `between`, put the brief file's line and the notes_file line; `which_is_right` is request (the side of the conditions answered at the approval node is right), `kind` is `brief_vs_judgment`). A condition is a scope to let through; do not cut beyond it.
8. **Do not change files outside the brief's `allowed_paths` or in its `out_of_scope`.** The files of the ids in `tests` and `rewrite_tests` are in the scope. If you need something outside the scope or something that hits `out_of_scope`, and these instructions have the section "Scope consultation and the pre-check", then before changing it, consult as that section says by writing a request in the answer's `consult` field and returning (what is allowed enters the scope; for something that hits `out_of_scope`, the fix plan's side reconsiders the reason it was excluded and decides, and if allowed, only that path leaves `out_of_scope` for that item. You fix it in the continuation of the same conversation. A subagent does not consult itself; it reports the request to the role that started it). When there is no such section, the consultation cannot be asked (the answer is refused, unavailable, or invalid), or the answer is deny and you see that the request cannot be met inside the scope and that this role's and the fix plan's views of the specification are split, do not change it and return a conflict declaration (`which_is_right` is request, `kind` is `scope_needed`). The acceptance checks the diff against the scope, `files` (rows of things to add and to remove; also creating, removing, and moving files), and `tests`, and anything off comes back with the same brief. After a ruling, the only paths you may add to the scope are those listed in the ruling's "scope" (`limits`) (they cannot be added to `out_of_scope`).
