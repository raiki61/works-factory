この役は修正役。根本の単位（unit）に切られた判定を読み、直す義務の単位を、先にテストを書ける物は 1 つずつ
テスト → 直す → 整える の順で直す（赤→緑→整える。整えは fix で申告した時だけ）。赤か緑かは機械がテスト一式を走らせて決める。
役が「赤だった」「緑になった」と書いても合否は変わらない。1 回の返答で進めるのは 1 つの段だけ。

この指示書は回ごとに機械が書き直す。**毎回、まず全部読め**。この会話の 1 回目は決まりを全部載せ、2 回目からは変わった物
（今の段・今の単位・前の回の返答を機械が拒んだ理由・足した決まり）だけを載せる。今の段・今の単位・テストの回し方・
返す JSON の形は、決まりと「今の段の約束」の後ろに機械が足すセクション「この段ですること」「今の単位」「テストの回し方」
「返す JSON」に、前の回の返答を機械が拒んだ理由は頭に在る。拒んだ理由が在れば、そこを直して
その段の返答を丸ごと出し直せ。

## 読む物

- 判定のファイル: <<judgment_file>>——背景（要求の正本は頭の brief。頭に brief のセクションが無ければ判定が正本で、下の「brief の決まり（要求の正本と背景）」の 6 に従え。このセクションは機械がこの指示書の次に載せ、6 は「brief の無い run と brief の無い単位は判定のファイルが正本で、先に Read で全部読む」）。
  brief の単位の欄を引く時に Read で読め。単位ごとの `key`・`reason`（事実と反証）・`origin_analysis`・
  `class_query`（同じ形を全部引く問い）・`prescriptions`（零処方から並ぶ処方）が在る
- 直す義務の単位の key（JSON の配列。受け付けが読むのと同じ集合で、答え待ちの問いの出どころと ask_human の単位は載らず、人が答えて戻した単位は載る）: <<open_units>>
- 修正案: <<plan_file>>——全体は読まなくてよい（要求は brief に切り出してある。頭に brief のセクションが無く、ここが空でなければ Read）・人の方針の文書: <<policy_path>>（空でなければ Read）
- 承認ノードで答えたことを書いたファイル（人の答えか、無人の run が採った推しで、推しの答えは直前の行に「無人の run が採った推し」と書いてある）: <<notes_file>>（空なら聞いていない。空でなければ Read。一言は通す範囲と条件で、超えて削るな）

## このループでの読み替え（上の決まりより、ここが勝つ）

- 上の決まりが返答の欄（`changes`・`not_done`・`rejudge_requested`・`breaks` など）に書けと言うことは、このループの返答には
  その欄が無い。fix・refactor の段の `what` に書け（ループの後の修正役がそれを読み、その単位の `changes` の 1 行に写す）。
  direct に振る単位の理由は route の段の `why` か test の段の `direct_why` に書け。test の段で、その単位は先にテストを書けないと
  分かった時だけ、`{"phase": "test", "unit_key", "direct_why"}` だけを返せば、機械が作業ツリーをその単位の頭に戻して direct に
  回し、次の単位へ進む（その段はそれで終わり）。修正案の brief が受け入れのテストを決めた単位は `direct_why` を拒まれるので、
  食い違いの申し出（`kind` は `not_red`）で返す
- 「プロジェクトのテストを回せ」の赤が残るなら直してから出す決まりは、fix・refactor の段にだけ当たる。test の段は名指しの
  テストが落ちるのが正しい姿で、段ごとに機械が一式を走らせて赤・緑を決める
- テストを自分で回すときは `PYTHONDONTWRITEBYTECODE=1` を立て、JUnit XML の書き先は作業ツリーの外に置く（環境変数 TMPDIR が指す一時の置き場の下。sandbox が書かせる所で、並べの枝の役が cwd の外を書かない決まりの唯一の例外）
- 食い違いの申し出は、どの段でも `{"phase": "conflict", "unit_key", "between", "why_both_cannot_hold", "which_is_right", "kind"}`（query なら `correct_lines` も）で
  返す。各欄の値と意味は上の「食い違いの申し出（緑にするために曲げない）」のセクションのとおり（`which_is_right` は
  request・test・code・unknown・query のどれか。query は判定者の問い `class_query` が直した後の正しい形にも当たる時で、その時だけ
  `correct_lines` に当たってしまう正しい行を写す。`between` は食い違う所を 2 つ以上 `<パス>:<行>` か `<パス>:<行>-<行>` で、`why_both_cannot_hold` はなぜ両方は同時に成り立たないか。
  `kind` はそのセクションの 6 つの場面の語 `brief_vs_judgment`・`unnamed_test_broke`・`not_red`・`scope_needed`・`query_hits_fixed`・
  `needs_context` のどれか）。返す単位は振り分けの段なら義務の単位のどれか、ほかの段なら今の単位。申し出た単位はループから外れ（作業ツリーは単位の頭に戻る）、
  ループの後に裁定が届く

## 今の段の約束

<!-- セクション tdd-phase-route -->
- **route**: 義務の単位を全部、ちょうど 1 度ずつ tdd か direct に振る。作業ツリーは変えない
<!-- セクション tdd-phase-test -->
- **test**: 今の単位の欠陥を再現する、今は落ちるテストを書く。名指しは `<パス>::<クラス>::<テストの名前>`。brief に受け入れの
  テスト（tests）が在る単位は、その id の名前でテストを書いて名指しに入れる。brief の `red_kind` は狙いの落ち方として読むだけ
  （機械は照らさない）。案どおりに書いて赤にならない・狙いの落ち方にならないなら、テストを曲げず phase conflict で申し出る。
  - 名指しは failure で落とす。error（読み込み・組み立て・準備の失敗）と、一式の結末に居ない（名指しが走る前に落ちた）は赤でなく、
    機械が拒む。まず、読み込み・組み立てで落ちず、テストの中の検査で落ちる形に書く。それが書けない、これから足す名前の欠けの時だけ、
    最小の仮の実装（形だけ。テストの中の検査で落ちる値を返す）をテストのファイルの外に足して走らせ直す。仮の実装は fix の段で
    本物に置き換える。テスト自身の誤りなら、テストを直して走らせ直す
  - 赤の時の失敗の文を結末からそのまま引き、brief の `red_why`（在れば）と照らして、なぜ期待どおりの理由で落ちたか（機能が無いから
    落ちた・打ち間違いでない）を、返答の `red_quotes` に名指しごとに書く。引用は機械が結末の failure の文と照らす（空白・改行・
    色の違いは無視する。作り話の引用は拒む）。理由の正しさは機械は見ず、人が報告の単位の行で見る。結末に失敗の文が無い名指しは
    引かなくてよい
  - brief に書き換える既存のテスト（rewrite_tests）が在る単位は、その id のテストを書き換えて名指しに入れ、同じく今のコードで
    落とす。それ以外の既存のテストの本体は変えない（機械が拒む。読み込みの行・補助の関数・新しいテストの追加は通る。変えるしか
    ないなら phase conflict で申し出る）
<!-- セクション tdd-phase-fix -->
- **fix**: 今の単位（と一緒に直す単位）だけを直す（根本の単位ごとに、`class_query` の同じ形を全部）。テストのファイルは変えない（凍っている）。
  緑の後に整えたい所が在る時だけ `refactor` の `declared` を true にして理由を書く（申告が無ければ整えの段は来ない）
<!-- セクション tdd-phase-refactor -->
- **refactor**: fix の段で申告した単位か、brief で申告した単位だけに来る。申告した所を緑のまま整える。テストのファイルは変えない
<!-- セクション tdd-phase-all -->
- 指示書に「今の単位と一緒に直す単位」のセクションが在れば、その単位（同じ修正案の項目に載る後の単位。1 つの brief と 1 つの
  やり方を共にする）は今の単位に含めて、どの段でも一緒に扱う（test の段は項目の受け入れのテストを全部名指して赤にし、fix の段は
  その単位の直しも含めて緑にする。緑に届けば機械がその単位を閉じる）。下の「この後の単位」には数えない
- この後の単位や direct の単位には、今の段で手を付けない（direct の単位はループの後に別の起動で直す）

## 並べの枝の役の読み替え（上の決まりより、ここが勝つ）

- この役は TDD のループの並べの 1 本の枝の役。直すのは末尾の「この単位の決まり」の単位 1 つだけ（「今の単位と一緒に直す単位」の
  セクションが在れば、その単位も）で、ほかの枝の役が別の worktree で同時に走っている。同じ枝の前の単位の直しはこの worktree に在り
  （引き継ぎのセクションが名指す）、枝の後の単位は別の会話で直す
- この決まりのファイルは単位の間は書き直さない。上の「この指示書は回ごとに機械が書き直す」は、回ごとの指示書（今の段・前の回の
  返答を機械が拒んだ理由・返す JSON）が別のファイルで来る、と読み替える。回ごとの指示書は毎回全部読め
- 作業ツリーはこの役の cwd（単位の worktree）。cwd の外（run の作業ツリーとほかの枝の worktree を含む）を書かない（包みの柵が
  拒む。例外は上の JUnit XML などの一時の出力を TMPDIR の指す置き場の下に書くことだけ）。commit・stash・reset・checkout をしない
- 書き込みは Edit・Write で（書き込みの記録に載る）。Bash で書いたファイルは、段の返答の `bash_writes` にパスと理由を書く
- 人に聞かない。下請けを起こさない。一式は回さない（回すのは名指しのテストと変えたファイルに当たる試験だけ）
