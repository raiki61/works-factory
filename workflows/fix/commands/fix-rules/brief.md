## brief の決まり（要求の正本と背景）

brief は、事前審査と人の承認を通った修正案の 1 項目を、機械が切り出して凍結したファイル（役が書き換えても、次に読むのは
通った時の文に戻る）。この指示書の頭の「要求の正本（brief）」のセクションに絶対パスで並ぶ。
下で使う語: 「食い違いの申し出」は、この指示書の後ろのセクション「食い違いの申し出（緑にするために曲げない）」の形で返す
申し出（欄と `which_is_right`・`kind` の値はそのセクションに在る）。「裁定」は、その申し出を読むだけの裁定役が裁いた結果。
「判定のファイル」と「依頼のファイル」は、この指示書の「読む物」の判定のファイルと、頭の「依頼の文のファイル」。

1. **頭の「要求の正本（brief）」のセクションに並んだ brief が、要求の唯一の正本。** まず brief を Read で全部読み、そのとおりに
   直せ。修正案の全体は読まなくてよい。
2. **判定のファイルは背景。** brief の単位の `class_query`（同じ形を全部引く問い）・`origin_analysis`（出自）を引くのに読め。
   単位の切り方（unit）は判定どおり。何をどう直すかは brief。brief と判定が食い違えば brief が勝つ——止めずに brief
   どおり直す（判定に合わせて読み替えない）。brief そのものを誤りと見た時だけ 3 の申し出で返す。下の決まりの
   「同じ形を全部直せ」の範囲と brief の範囲が食い違っても、何をどこまで直すかは brief が勝つ。ただし受け付けの機械の
   確かめは brief があっても全部効く: `class_query` での欠陥の形の件数の数え直し・テストの凍結の確かめ・変更に当たる
   試験を選んで回すこと・最後に人へ見せる一覧への並び（4 の書き換えたテストも並ぶ）。brief の範囲が `class_query` の
   数え直しの求める範囲より狭く、範囲の外も直さないと閉じないなら、黙って狭めるな。範囲の外が要るなら、8 のとおり先に相談し
   （返答の `consult` の欄。許されれば直す）、相談のセクションが無い・聞けない・許されない時に、その単位は範囲の外が要ることを食い違いの申し出で返せ。
   `which_is_right` は、範囲の外が要るなら request（`kind` は `scope_needed`）。判定の問いが直した後の
   正しい形にも当たる（正しく直しても件数が減らない・`population` の問いが直さなくてよい物にも当たる。`population` の問いは、判定の `class_query` の `counts` が population の問いで、欠陥ではなく直す対象の母集団を数える）なら、食い違いの申し出の `which_is_right` を query（`correct_lines` 付き）にして返し（欄 `correct_lines` に問いが
   当たってしまう直した後の正しい行を写す）、`kind` は `query_hits_fixed`。
3. **brief が誤りだと思えば、自分で読み替えず、食い違いの申し出で返せ。** `between` に brief のファイルの行（頭に並んだ
   絶対パス）と、判定のファイルか依頼のファイルの行を並べる。`which_is_right` は、判定か依頼が正しいと見れば request、
   決められなければ unknown。`kind` は `brief_vs_judgment`（`between` に brief の行が要る。brief の無い単位では使えない）。
   裁定を受けた単位は、裁定の範囲で裁定が brief に勝つ（裁定を受けた単位とは、2 回目の起動で指示書の頭に名指された
   「食い違いの申し出への裁定を書いたファイル」に裁定が載る単位。範囲は裁定に書かれた所。裁定の外は brief のまま）。
4. **brief の `rewrite_tests` に名指した既存のテストだけは、書き換えてよい。** `rewrite_tests` の各行は `id`（書き換えるテスト）・
   `behavior`（縛る振る舞い）・`old`（今の期待）・`new`（書き換えた後の期待）で、その `id` のテストを `new` の期待に書き換える。依頼で変わる振る舞いを
   縛り直すためで、期待値を実装に合わせるためではない。名指しの外のテストは今どおり変えるな。書き換えたテストは
   最後の承認ノードに並ぶ。
5. **brief の `tests` は、先に決めた受け入れのテスト。** その名前で、書いた振る舞いを、書いた本物の経路で縛り、
   書いた形で赤にせよ。
6. **頭に「要求の正本（brief）」のセクションが無い run（修正案の無い run）と、brief の無い単位は、判定のファイルが正本。**
   そのときは判定のファイルを先に Read で全部読み、上の 1〜5 は当てない。
7. **修正の前に承認ノードで答えた条件（notes_file。人の答えか、無人の run が採った推し）は brief に勝つ。** 1〜5 より先に当てる。notes_file は「読む物」の「承認ノードで答えたことを書いたファイル」で、空なら条件は無く、7 は当てない。
   brief が条件を超えれば条件どおりに直し、超えた所は食い違いの申し出で返す（`between` に brief のファイルの行と
   notes_file の行を並べる。`which_is_right` は request（承認ノードで答えた条件の側が正しい）、`kind` は `brief_vs_judgment`）。条件は通す範囲で、超えて削るな。
8. **brief の `allowed_paths` の外と `out_of_scope` のファイルを変えるな。** `tests`・`rewrite_tests` の id のファイルは
   範囲に入る。範囲の外や `out_of_scope` に当たる物が要るなら、この指示書に「範囲の相談と事前の確かめ」のセクションが在れば、
   変える前にそのセクションのとおり、返答の `consult` の欄に頼みを書いて返して相談せよ（許された物は範囲に入る。`out_of_scope` に
   当たる物は修正案を書いた役が外した理由を考え直して決め、許せばその項目ではそのパスだけ `out_of_scope` から外れる。
   同じ会話の続きで直す。下請けは自分で相談せず、自分を起こした役に頼みを報告する）。セクションが無い・相談が聞けない（答えが refused・unavailable・invalid）・相談の答えが deny で範囲の中では依頼を満たせず、この役と修正案を書いた役の仕様の見立てが割れていると見る時は、変えずに食い違いの申し出で返せ
   （`which_is_right` は request、`kind` は `scope_needed`）。
   受け付けは差分を範囲・`files`（足す物・消す物の行。ファイルの新設・消し・移しも）・`tests` と照らし、外れは同じ brief のまま返る。裁定を受けた後に範囲へ
   足してよいのは、裁定の「範囲」（`limits`）に並べたパスだけ（`out_of_scope` には足せない）。
