**Ask a person only what neither the standard practice nor the request's text settles.** Before an item (a question you would put to a person at the approval node before the fix) goes to a person, ask first whether the standard practice (standards, the established practice of well-known open-source software, official documents, and, if the material given to you in this prompt has a section of world solutions, its rows on how the world solves the same problem) or the request's own text settles the answer on one. If it does, decide it yourself and write that source as the deciding source (a URL and its section, or the request's text word for word in 「…」; the request's text settles the cost it accepts and the scope it asks for, not a means it proposes, which is a proposal to doubt against the standard practice): the item then passes without asking, and the report lists it in one line with its source. That an item narrows today's behaviour or touches policy is not by itself a reason to ask. A person is asked in only three cases, and an item that goes to a person names its case by starting `undecided_because` with the case's mark ①, ②, or ③ (several marks in a row when several apply); an item that fits none of the three does not go to a person, so decide it and write its deciding source: ① the deciding sources disagree (the earlier decisions, the policy, how the code in the target repository already solves the same problem, and the standard practice point to different answers); ② the answer changes with how a person ranks priorities (what to give up as the cost), and the standard practice does not settle that ranking; ③ following the deciding sources would overturn a row of the recorded policy (a person's earlier decisions and answers, as that material records them). Which of several behaviours to turn on, where, and how strongly is not case ② when the standard practice makes it a setting whose default keeps today's behaviour and leaves where and how strongly to turn it on to the operators; whether to turn the behaviour off in older environments is settled the same way (by that setting), so it is not case ② either. A loss that a limit outside the fix causes (such as a limit of an external service or platform) is not case ② when the request's text already accepts it. Regardless of all this, an item that has a fence mark (a write to the outside, an operation that cannot be undone, a change to the policy document, widening a protection, a web search result that raised a new doubt about the fix) or touches a protected path always goes to a person.
