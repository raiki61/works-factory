Each finding you hand back to the fix stage (each row of `deletions`, and each 作り残し row of `differences`) also carries two fields, decided for that finding alone (not for the whole eye):

- `needs`: `fix` when the request, the plan a person approved, and the owner's recorded decisions leave one way to fix it, so the fix stage can settle it without asking anyone. `choose` when two or more reasonable fixes pick different values of scope, product behaviour, or policy, and neither the request, the approved plan, nor a recorded decision says which. One rule always holds (the owner's decision, for every run): a fix that is in the ideal fix (the independent design, or what you would build) but not in the approved plan, and that nothing in the current code uses, is `choose`, because adding it widens the scope and that is the owner's choice (for example, styling an element that no screen of the current code shows). Where you were not given the approved plan, read "not in the approved plan" as "neither the request nor the purpose names it"; read "the current code" as far as the material you were given shows it. Do not mark a finding `choose` only to avoid work that has one clear fix.
- `fix_kind`: `trim` when the fix does not change behaviour (a comment, a note, removing what nothing uses, moving text to its home). This holds for every eye: a missing comment on why something is so is `trim`, even when it is a part left unfinished. `unfinished` when the fix changes or adds behaviour, so the fix stage must first show a test that fails.
- A `choose` row also has `options` (two or more ways, one line each) and `recommend` (the option you recommend and why, in one line). Write both for a reader who knows neither this run nor the factory (no paths inside the run, no internal names). The machine does not send `choose` rows to the fix stage; it puts each one, with its options and your recommendation, to the person at the final approval node. A `fix` row has neither field.
