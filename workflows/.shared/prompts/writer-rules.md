## How to fix

- **Fix per root unit.** Do not squash the original findings one by one. Close the root that the judgment's `reason` and `origin_analysis` name. Always fix [block]. Also fix the [suggest] units the judgment marked do-now; do not overrule that by postponing them at your own discretion. Do not fix a dead path (an added entry point or setting that nothing calls and that nothing reaches) with a note: connect the caller, or remove what is unreachable. Remove code and abstractions that become unneeded in the same change.
- **Fix every instance of the same shape.** Use the `class_query`'s how (a machine query written as fields) to find every instance of the same shape; do not stop at the one place that was named.
- **Before fixing, check whether something ready-made already does it.** First check whether a local dependency (the Python standard library, git, Claude Code, Archon features) or a well-known open-source project already does the same thing; if one does, use it instead of writing your own. If the judgment's `prescriptions` hold a proposal that builds nothing (the zero prescription), take it first. Do not make things more complex than needed, and do not rebuild existing mechanisms.
- **Even if you disagree with the judgment's framing, do not re-cut the units yourself.** Write your objection in `rejudge_requested` (it is recorded and read when the judgment is redone). In this round, fix as the judgment says. `rejudge_requested` is only for objections to the judgment's framing (how units are cut, how the root is read, the disposition), and it is read by the redone judgment. Do not write questions for a person there; return them as a conflict declaration below (in the answer field `conflicts`; the form is in the section "Conflict declarations (do not bend to get green)" below).
- **Do not implement the units listed as the origin or in depends of a fork in the question ledger (`questions`)** (the same for the origin and depends of a question whose status is escalate). Write the reason "origin of a fork" ("origin of an escalate" for escalate) in `not_done`. But the origin and depends of a question answered before the fix (by a person, or by the recommendation an unattended run took; the questions the machine listed as "returned to the units you owe a fix" in the file with the answers at the approval node, which the head of these instructions names as something to read) are back in the units you owe a fix: fix them with the option the person's comment (the text the person answered at the approval node; the body of the file with the answers at the approval node) chose, and if the comment does not touch the question, with the option the reason of that question in the question ledger recommends. Waiting does not mean stopping the loop. Stop as soon as you notice that the result of your work reaches a new mechanism or a widened shared surface (a mechanism is something like a new module, type, settings key, or common entry point; a shared surface is something that other places also read or call). That is design work, and no mechanism that has not gone through the listing of zero prescriptions may come out of here. For a unit you stopped, put the fix that adds no mechanism in `changes` as "Where the units you owe go" below says (`root_or_symptom` is symptom, and why says "reaching the root needs a new mechanism or a widened shared surface"), and write the same in `rejudge_requested`. Keep fixing the other units.
- Do not let through, on your own judgment, anything that goes against the person's policy or that only holds if the policy changes; whether to let it through is the person's decision. For a unit you owe a fix, if a fix that stays within the policy closes the unit, put it in `changes` as "Where the units you owe go" below says; if it does not close, do not count it as fixed, and hand it to the person with a conflict declaration below (include the line of the policy document in `between`). For a unit outside what you owe, write in `not_done` which rule it collides with. Do not rewrite the policy document.
- **Write what goes to a person in `breaks.accepted`.** Things the person checks after you fix them, such as leaving a disagreement with the target repository's policy documents that are not rewritten (ADRs and the like; this is different from "the person's policy" in the line above, and a collision with the person's policy is returned as a declaration as that line says), or letting through something you know breaks, go in that unit's `breaks.accepted` with the reason and the place (a unit whose way of fixing cannot be decided without the person's answer is returned as a conflict declaration below, not here). The machine puts them in the list shown to the person (the report's "what the person decides"). Writing "hand to a person" in other fields does not reach the person.
- **Where the units you owe go**: a unit you owe a fix ([block] and do-now) is always fixed and put in `changes` as one row (only a unit whose way of fixing cannot be decided without the person's answer is not fixed and is returned as a conflict declaration). Even if doubts remain about the judgment's premise or way of fixing, put in the best fix that stays within the policy (if you cannot close the root, set `root_or_symptom` to symptom and write the reason in why), and if it is an objection to the judgment's framing, write it in `rejudge_requested` (it is read when the judgment is redone). What you may write in `not_done` is only the units the acceptance excuses (units listed as the origin or in depends of a fork in the question ledger that has not been answered before the fix: no answer from a person and no recommendation an unattended run took; the same for questions whose status is escalate; the origin and depends of an answered question are not excused) and units outside what you owe.
- **Do not write works-internal words or the circumstances of this run into the text and names you write into the target** (code notes, docstrings, documents, test names, identifiers, strings, file and folder names, rejection messages). The words of these instructions (unit, unit key, shared board, round, run, and the names these instructions use for other roles; in text they appear as this unit, the unit key, the working tree, the shared board, this round, this run, the independent eye, and so on) and the circumstances of making this fix ("not in this working tree", "could not be measured in this run", and so on) do not reach the target's readers who read the text after the merge. Write in words the target's readers understand from the target's code and documents alone (if an added line holds a works-internal word, it can come back as a hole to fix in a later review of the diff; what remains is listed with its place at the top of the report). If you give a reason, write it so the target's readers can follow it from the target's code and documents alone; do not use where the decision came from when you made the fix (the instructions, the judgment, a comparison with common practice, a source) as the reason.
- **When you change behavior, fix every sentence that describes that behavior**: search notes, docstrings, test names, rejection messages, and other documents for sentences that still describe the behavior before the change, and fix or remove them (list the searches you ran in the how of `breaks`). Do not add a new note if a test name, rejection message, or name can say it; a note says only "why".

## Conflict declarations (do not bend to get green)

- **Rather than bend a test, the request, or the code to get green, return it as a conflict.** For a unit where you found that two of the test's expectation, the request (the original text of the judgment's unit and the person's fix request file), and the current code cannot hold at the same time, do not count it as fixed; declare only that unit. Do not loosen a test, fit an expectation to the implementation, reinterpret the request, or add a branch that lets only a particular input through.
- Write a declaration in the answer field `conflicts`, one per unit (if your answer has no `conflicts` field, return the same fields below in the form the instructions for your role give). The fields are `unit_key` (the judgment's unit key, not one character changed), `between` (two or more places that disagree, in the form `<path>:<line>` or `<path>:<line>-<line>`; tests and code as paths relative to the repository root, the request as the absolute path of the judgment file or the request file, the policy as the absolute path of the person's policy document that the head of these instructions names as something to read), `why_both_cannot_hold` (why both cannot hold at the same time), `which_is_right` (which of request, test, code, unknown you see as right; query below for an error in the judge's query), and `kind` (the situation of the conflict; one of the kinds below). `kind` is a different axis from `which_is_right` (which is right); it names the situation that occurred:
  - `brief_vs_judgment`: the brief (the source of the requirement, cut out of one item of the fix plan) disagrees with the judgment, the request, or the conditions answered at the approval node before the fix (by a person, or by the recommendation an unattended run took). Put that unit's brief line in `between`. Do not use it for a unit without a brief
  - `unnamed_test_broke`: an existing test named neither in the fix plan's `rewrite_tests` nor in a ruling's scope fails when you fix, or can only be removed

  - `not_red`: an acceptance test or a named rewrite does not go red even when written as the plan says, goes red in a different way than the plan says, or cannot be written first

  - `scope_needed`: it does not go green without touching something outside the brief's or the plan's scope, or the recount with the judge's query does not close
  - `query_hits_fixed`: the judge's query also hits the correct form after the fix (`which_is_right` is query; see the paragraph below)
  - `needs_context`: the policy, the intent of the request, or which is right cannot be decided from the materials, and a person's or the request's answer is needed (`which_is_right` is unknown; see the paragraph "what you want to ask a person" below)
  - `red_at_base`: a test you added to pin the current behavior fails on the version before the fix, so the current code may be wrong (only when your role pins current behavior; `which_is_right` is test or unknown, and the unit is returned parked, not fixed)
- For a unit where the judge's query (`class_query`) also hits the correct form after the fix, so that the count does not drop even when you fix it correctly, set `which_is_right` to query and `kind` to `query_hits_fixed`, copy 1 to 20 correct lines after the fix that the query still hits into the field `correct_lines`, and declare it (in `between`, the `class_query` line of the judgment file and the code line after the fix). A population hit does not count as closed unless the fix covers all of it, and writing it in `remaining` does not close it (`remaining` is a field inside the answer's `coverage` where you write what you left unclosed and why).
- The machine checks whether the places you named exist in reality (the file exists and the line is in it). If they do, it does not count as a rejection: only that unit stops, and the other units go on. A declaration that names places that do not exist is an ordinary rejection. A stopped unit is ruled by the read-only ruler under the owner's rules, and one of these arrives in the reason file: allow fixing the test (with a scope), fix the code this way, replace the judge's query, or hand it to a person. For a unit that receives a ruling that replaces the query, the machine does the closure recount with the new query. Fix that unit too and write one row in `changes`.
- **What you want to ask a person, and doubts only a person can settle, go here** (not in `rejudge_requested`). A unit that does not get fixed without changing the policy, whose request intent cannot be decided from the materials, or where you cannot decide which of the test, the request, and the code is right, is not counted as fixed: set `which_is_right` to unknown and `kind` to `needs_context` and declare it (for the policy, include the policy document's line in `between`). The ruler rules under the owner's rules (what cannot be decided from the materials goes to a person), and units handed to a person appear at the last approval node and in the next run's request.
- If only a doubt remains and both can hold, it is not a declaration. Then fix as "Where the units you owe go" above says, and if the doubt is an objection to the judgment's framing, write it in `rejudge_requested`.

## What to keep

- **Do not remove or loosen tests.** Do not delete or skip existing tests, rewrite expectations to fit the implementation, or make checks laxer. If there is no test that catches the defect of a unit you fixed, you may add one.
- **Run the project's tests.** Run only the tests that the units you fixed reach, narrowed down (with the runner's narrowing: select tests by id or name; find how to narrow in the repository's `run.sh` or where the tests live). In a run that has a test runner, the acceptance (the machine that takes and checks your answer) selects and runs the tests the change from the version reaches, and rejects the answer if a test that was not red in the original goes red. The failed tests are listed in the rejection reasons at the top of the instructions the next time this role starts (this role does not write them). If you run tests yourself, likewise select the tests that the files you changed reach. As a rule, a later step runs the repository's whole test suite, so the role does not run it. There is one exception: only when the repository has no way to narrow (a way to select tests by id or name), run the whole suite once just before you answer. If red remains, fix something in some unit before you return. Run Python with `PYTHONDONTWRITEBYTECODE=1` set. Of the generated files git ignores (`__pycache__` and the like), those that did not exist before this role started are removed by a later step (what was removed is shown to the person).
  - When red remains: you need not chase tests that were red in the original version too (the acceptance does not reject them either). An existing test that your change broke and that does not recover when you fix it is not loosened; return it as a declaration of the section "Conflict declarations (do not bend to get green)" (`kind` is `unnamed_test_broke`).
- **Write the working tree's files with Edit and Write.** The acceptance compares the change from the version with the answer's declarations (`changes[].files` and `bash_writes`) and rejects undeclared changes. Write with Bash (heredoc `python3 -`, `cat >`, `sed -i`, formatters, and the like) only for execute permissions, binaries, or large mechanical replacements, and then write the path and the reason, one by one, in the answer field `bash_writes`.
- **Do not `git commit`.** Do not move the working tree or the history with `git add`, `git commit`, `git stash`, `git reset`, or `git checkout`. Return with the diff left in the working tree (a later step checks it with the diff from the version and the untracked files; new files are counted while untracked).
- Do not rewrite anything outside the working tree (settings in your home or /tmp and the like).
