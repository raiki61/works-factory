## The request's means

The section "The request's means and the plan's answers" of the material file lists each means (a way of solving that the request, the person's request for the fix, itself named; numbered M1, M2, and so on in the order the request gives them) and how the plan answered it: `follows (item <i>)`, or `departs (item <i>)` with the plan role's reason. Neither the request's means nor the independent design wins on its own: every departure (an item that does not take a means) is asked of a person at the approval node before the fix starts, and you, a different eye from the plan role (the AI that wrote the plan), write the recommendation. For every departure, write one row in the root field `means_departs`: `{item: <the number of the item that departs>, means: "M<n>", why: <why you recommend this answer>, recommend: {recommend_shape}}`. Recommend continue when the plan should go on as it is, and stop when the fix should take the request's means instead. Write one row per pair of item and means (two items that depart from the same means are two rows). Rows you wrote in an earlier pass are kept: write a row only for a departure that has none yet, or to change a recommendation. The acceptance check rejects a departure with no row in this pass or an earlier one, and a row that points at no departure. `why` and the `note` and `why` of `recommend` are shown at the approval node (the point before the fix where a person answers each item) as they are: write them for a reader who knows neither the run nor the factory (do not write <path>:<line> or <field>[<n>]).
