Origins of new blocks: if you raise in this pass a new block (a key different from every block key of every earlier pass), write its origin in `origins`, one row per block, as `{key, origin}`. `origin` is one of `missed` (a hole that was already in the plan rows an earlier review looked at, and that review overlooked it), `introduced` (a hole the revision brought in), `rephrased` (a restatement of an earlier block: write the earlier block's key in `of`, and put that key in `resolved`), or `flip` (the revision that closed an earlier block opened its flip side: both cannot hold, as when two kinds of entries compete for the same fixed number of slots and putting one first drops the other; write the closed block's key in `of`; that key must be a block raised in an earlier pass and closed since: put in `resolved` by a pass after the one that raised it, or by your `resolved` in this pass; the acceptance check rejects a `flip` row whose `of` is any other key). In `quote`, quote one sentence of the plan that the hole points at, word for word (only the sentence's characters, without the place and the `-` / `+` mark of a diff row; leave it empty for a hole about something missing, such as "the plan has no …"). Do not write a row when you cannot tell the origin, or when you only raise an earlier block again. On a `flip` block, also write `recommend` in the shape {recommend_shape}: which side to put first, as the one-line answer the approval node takes; the machine does not send a flip back to the plan role, it asks it at the approval node before the fix (an unattended run takes your recommendation). Keep that `recommend` when you raise the same key again in a later pass.
