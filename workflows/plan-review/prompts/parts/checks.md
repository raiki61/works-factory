## What to look at

1. **Copy** (kind=copy): does what is added copy, into another place, a rule, a type, a vocabulary, or a procedure that already has a canonical home? Read the repository to check.
2. **Entrance** (kind=entrance): besides the route that an added fence watches, is there another route into the same set? **Count every route into the set first**, and judge after that: a fence that closes only one entrance leaves the entrance it does not close as the next round's finding. **On an entrance hole, always write `no_add`** (the form that closes it without adding a fence or an entrance: delete, merge, or leave it to the world's tool); if that is impossible, write why. A finding that only says "add an entrance" plants the next round's finding in the entrance it adds (measured 2026-09-24: after a reference-form entrance was added as round 3's pre-review asked, round 4 raised "it keeps adding entrances").
3. **Contract drift** (kind=contract_drift): does a side that reads or writes what changes (prompt guidance, rejection texts, documents, tests, other places) stay behind without following the change?
4. **Dead path** (kind=dead_path): is what is added left in a form that nothing uses or reaches?
5. **Scope creep and minimality** (kind=scope_creep): does it add a mechanism that closing the unit does not need? Scope creep is a hole that widens beyond the purpose; minimality is a hole whose prescription is too large within the purpose. Make both kind=scope_creep, and start the `why` of a minimality hole with "{minimal_head}" to tell them apart. Raise it only when you can name a smaller prescription concretely, and write the prescription you named in `why`.
6. **Regression** (kind=regression): does it remove or narrow a capability that BASE had (the version after `BASE:` in the `Repository:` line: the version before this run started fixing)? The baseline of comparison is the section of the canonical rules named "移行退行の棚卸し（BASE 能力インベントリ）" (the inventory of the capabilities a migration loses): compare with BASE, not with an ideal. Take the inventory exactly as that section says (when it applies, how to list, and the form of the explicit answer), and write that explicit answer in the summary `reason`.
7. **Policy** (kind=policy): does it conflict with a row of the section "Recorded policy"? Code comments, docstrings, and test descriptions that are not in that list (the target's text) are not policy: if the plan leaves such text as it was, raise it under check 3 (kind=contract_drift, severity block, reach peripheral) and have the fix include rewriting that text.
8. **Precedent source** (kind=precedent): open the sources of the precedents that the plan adopts or aligns with, and check that each source exists and fits the unit's problem. The machine checks the shape of a source (the row exists, the field is not empty), but you are the only eye that checks its content, separate from whoever wrote it. If a source is missing or does not fit, write in `why` which row's source disagrees with what.

Holes of checks 6 and 7 are asked of a person by the run before the fix. **Neither you, nor the judge, nor the role that writes the fix decides whether a regression or a policy conflict is let through as a cost**: only list them.

In addition, if there is **an alternative that closes everything together, smaller** (delete, merge, adopt the world's solution), write it in `shrink`. `shrink` is an array with one row per alternative; a row has `key` (a short unique name), `alternative` (what the alternative is), and `why` (why it closes things smaller). If there is no alternative, make it an empty array.

## How to write the holes

- `faces` has one row per predicted hole. `key` is short and unique; `kind` is the kind= value of "What to look at" (exactly one of copy, entrance, contract_drift, dead_path, scope_creep, regression, policy, precedent); `where` is the place in the real thing (a file, a function, a field); `why` is the reasoning by which it becomes a hole.
- `severity`: `block` for a hole that, once written, becomes a [block] in the next round; `suggest` for anything else.
- `reach`: the harm you meet if the fix goes ahead without fixing the hole. A hole that meets one of these central definitions takes that value: `breaks_fix` (the fix breaks), `loses_behavior` (a behaviour that exists now is lost), `against_policy` (it goes against recorded policy), `forces_redesign` (a design choice that forces a redo, including a fence that misses a whole class of entrances). A hole that meets none of them is `peripheral`: stale explanatory text left behind, an omission in a list of rewrites, test material — it must be answered when fixing, and if it is left unfixed it is handed on past the fix and checked again after the fix, which is never skipped. In the first sentence of `why`, write the concrete harm that meets the definition (for `peripheral`, why it meets none of them).
- `no_add`: always on an entrance hole (kind=entrance); you need not write it on other holes. Write the remaining fields (`decided_by`, `fences`, `recommend`, and so on) only when the rules of this prompt ask for them.
- If you judge there is no hole, leave `faces` empty and write in `faces_none` what you checked that lets you say there is none.
- When the input is not enough (for example, a file you were told to read cannot be read: the "not enough" of the role definition), do not write that there is no hole. Leave `faces` and `shrink` empty, start both `faces_none` and `reason` with "{short_head}", and write what could not be read and what could not be checked.
- In `reason`, write the summary of this review. Also name there the "lookups not run because they need the target's names" from the rules for queries (this schema has no field just for them).
